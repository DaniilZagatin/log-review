# Скилл, инструменты и бизнес-контекст

Решение Codex и Claude от 26 октября 2026: один предметный скилл с разделами по стадиям, один оркестратор и детерминированные инструменты. Основной вход — код приложения и бизнес-описание. Готовые логи и выбранная инфраструктура Process Mining для первого прохода не требуются.

## Что получает модель

`guidance/process-observability/SKILL.md` — общий порядок и ограничения. Python явно загружает его и соответствующие references в системный запрос выбранной модели: GLM разбирает код, DeepSeek выполняет бизнес-стадии. Файл на диске сам по себе не активирует знания в API.

| Стадия | Загружаемая методика | Результат |
|---|---|---|
| Карта и необходимые факты | `map.md`, `coverage.md` | Границы, единица учёта, альтернативы, важные факты и их аналитическая цель |
| Проверка покрытия | Та же постановка фактов + результаты инструментов | По каждому факту — конкретные ключи, кандидаты эмиссии и неизвестные |
| Предложения | `coverage.md`, `instrumentation.md` | Разметить, соединить, обогатить, изменить место фиксации или добавить минимально необходимое |
| Метрики | `metrics.md`, `metric-formulas.md` | Пять направлений КГБ, рабочие формулы, зависимости и правила счёта |

ID разделов связываются с фактами, карточками и метриками в `guidance_links`. Неизвестный или не загруженный ID отклоняет предложение. Это проверка ссылки на метод, а не автоматическое доказательство правильности вывода. Активные файлы, их SHA-256 и маршруты сохраняются в `bundle.guidance`, входных хешах manifest и трейсе.

Logging/ClickStream описывают виды следов; СМД/Kafka — варианты источника или поставки. Они могут сочетаться. Эти справки подготовлены для будущего проектирования подключения, сейчас по умолчанию не загружаются и не задаются в основном CLI. Кодовые подсказки Kafka не активируют правила поставки автоматически. Отсутствие выбранной схемы не мешает карте и адресным рекомендациям.

## Что взято из пользовательских материалов

В `/Downloads/123` повторно сверены пять HTML: их хеши совпадают с SRC-001–005. Также использованы ранее предоставленные полные страницы подготовки, поиска данных и валидации (SRC-047–050). Полные источники сохранены в private, а скилл содержит переработанные идеи:

- Сначала бизнес-сценарий и ключевые события; найденные технические следы не определяют весь процесс.
- Отдельная разметка: техническое событие → бизнес-действие → операция → этап. Несколько записей могут описывать одну операцию.
- Нужны границы, единица учёта и вариативность. Отмена и отрицательный бизнес-исход не исчезают из-за отсутствия события в коде.
- Существующий столбец, запись состояния, сопоставление или обогащение могут быть достаточны без новой эмиссии.
- Отказ по бизнес-правилу и технический сбой различаются. Формальные названия метрик не дают формулы.
- Набор полей зависит от факта и способа получения; обновление и доставка — отдельные вопросы.

Полный перечень 21 поля и категории значимых событий из SRC-004 теперь передаются через общий `FACT-SOURCE-CATALOG`, до выбора канала. Это справочник необходимых фактов с условной применимостью, а не единая обязательная raw-схема. Пять направлений КГБ рассматриваются уже при постановке фактов; подробные определения и предложенные формулы — на стадии метрик. Проверка фактического текста четырёх запросов выполнена в синтетическом демо.

Портальная навигация, сроки подключения и контакты не перенесены как универсальные требования. `sources.json` содержит названия, ID, хеши/ссылки и статус оснований, без исходных документов. HTML остаются датированными снимками, DOCX — предложением, а не принятым контрактом пилота. Каталог рабочих формул — `docs/METRIC-CATALOG.md`, разбор исходных HTML — `docs/METRIC-SOURCE-CHECK.md`.

## Проверенные существующие навыки

Поиск выполнен по доступному локальному каталогу и трём направленным веб-запросам. Готовый предметный навык, который покрывал бы именно наш сценарий, в проверенном локальном каталоге не найден; это не утверждение об отсутствии такого навыка вообще.

| Навык | Полезная часть | Применение |
|---|---|---|
| `skill-scout` | Поиск и проверка перед созданием | Разработка пакета |
| `skill-creator` | Короткий вход, отдельные references, загрузка нужного | Формат предметного скилла |
| `agent-harness-construction` | Узкие типизированные инструменты и понятные результаты | Граница модели и инструментов |
| `codebase-onboarding` | Обзор стека, точек входа и конфигов | Идеи для навигации по коду; его генерация CLAUDE.md не нужна продукту |
| `eval-harness` | Проверяемые случаи и регрессии при изменении промптов | Разработка и будущие проверки качества GLM |

`regex-vs-llm-structured-text` просмотрен как кандидат для извлечения. Его обещания фиксированной точности и произвольные confidence-баллы не перенесены: регулярки и AST дают технические кандидаты, бизнес-смысл оценивается отдельно. Внешние community skills не устанавливались.

Официальная [спецификация Agent Skills](https://agentskills.io/specification) поддерживает структуру SKILL.md с отдельными ресурсами. [Руководство по интеграции](https://agentskills.io/client-implementation/adding-skills-support) описывает явную загрузку знаний хостом и передачу выбранного контента модели. Для нашего фиксированного конвейера из этого выбран небольшой загрузчик без реестра плагинов. Это наше инженерное решение.

Рекомендации Anthropic по [проектированию инструментов](https://www.anthropic.com/research/writing-tools-for-agents) полезны ограничением числа пересекающихся инструментов и проверкой на реалистичных задачах. В 0.1.0 реализован предметный pre-pass. В текущем workspace сохранены технический граф и планировщик небольших запросов; подключение одной генерации типизированных дополнительных чтений к CLI выполняется в R01. Неограниченный tool loop не добавляется.

## Поиск логирования

`discover_logging` работает с замороженным отфильтрованным текстом. Для Python использует AST без исполнения, для других языков — помеченные эвристики. Возвращает:

- места вызовов с диапазонами, callee, уровнем и методом извлечения;
- кандидаты литеральных/константных ключей отдельно от динамических;
- имена полей в месте вызова;
- кандидаты обёрток в том же Python-файле;
- подсказки конфигурации и поставки;
- пределы поиска, пропуски и fallback.

Вызов не доказывает включённый уровень, достижимость, commit или доставку. Поля вызова не доказывают схему получателя. Обёртки и явно добавленные `--log-call` не повышаются автоматически до подтверждённой эмиссии. Если новое поле/событие может дублировать существующее, карточка получает вопрос для проверки; это не автоматический запрет.

Сканер не решает, что логировать. Это решается цепочкой: бизнес-вопрос → необходимый факт → существующие основания → минимальная доработка → будущая проверка метрики.

## Идеи из DeepResearch backend

Локально проверен `/Users/jlocehok/ai-agent-deepresearch/backend`:

- `src/config/prompts.py:283`: чтение явно перечисленных Markdown с бизнес-правилами и включение в system prompt.
- `src/agent/memory_tools.py:37`: `ToolWrapper`, описание, JSON-схема и исполнитель.
- `src/agent/agent_base.py:407`: передача `tools` / `tool_choice` в модель; обработка `tool_calls` и возврат `role=tool` в цикл.

Это полезные механизмы API. В просмотренном backend не найден самостоятельный загрузчик SKILL.md/activate_skill. В нашем пилоте использован принцип явного подключения Markdown с дополнительными хешами, фазами и ограничением объёма. Код DeepResearch, SQL-инструменты, память, БД и его агентный runtime не переносились и не запускались.

## Что доказывают проверки

Offline-тесты проверяют механику, границы и отказ при ошибках. Они не доказывают, что живая GLM правильно интерпретирует бизнес-смысл. Для следующего фидбека нужны оценки на реальном коде: пропущенные этапы, ложные сопоставления, ненужные новые события и полезность метрик. При отсутствии исполнения численные значения остаются `null`; вместо причин задержек сохраняются вопросы для будущего измерения.

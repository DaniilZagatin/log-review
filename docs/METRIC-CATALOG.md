# Предлагаемый каталог метрик из полей бизнес-событий

Исследование: 26 октября 2026. Это рабочие определения для первого пилота; официальную банковскую методику можно позднее сопоставить по версиям. Сейчас задача агента — предложить конкретную формулу и минимальные факты/логи для неё. Расчёт значений и статистическая причинность в этот проход не входят.

## Как читать поля

21 поле SRC-004 уже покрыто runtime-справочником `FACT-SOURCE-CATALOG`. Наличие ключа в справочнике не означает, что он реализован в пилотной репе. `сase_id` в снимке начинается с кириллической «с»; имя нельзя молча заменять. Для формул ниже c — логическая идентичность экземпляра с пространством ключей процесса и проверяемыми межсистемными соединениями.

E(c) — события экземпляра после проверенного устранения повторной доставки; O(c) — отдельные выполнения бизнес-операций. Записи start/complete/экран/диагностика одного действия не становятся разными O. Часть метрик возможна только после явного сопоставления event → операция → роль события → выполнение; требуемая разметка входит в рекомендацию агента.

W — выбранный полуоткрытый период [a,b), T — момент отсечения наблюдения. Для потока начала и завершения отбор идёт соответственно по t_start и t_end. Для долей одна и та же C задаётся и числителю, и знаменателю. Предлагаемый базовый вариант долей исходов — C_closed с подтверждённым бизнес-завершением в W; история этих экземпляров должна быть получена полностью, даже если их начало раньше W. Это не та же когорта, что начатые в W. Правила late data, переоткрытия и пересмотра результатов сохраняются в определении, без выдуманных календарных дат. При знаменателе 0 — null, а не 0%.

## Каталог

| Метрика | Рабочая формула | Поля и условие |
|---|---|---|
| Входящий поток | N_start(W)=число уникальных c с бизнес-началом в W | case/process, event, date_time; известное событие начала |
| Завершённый поток | N_end(W)=число уникальных c с бизнес-завершением в W | terminal event, is_case_complete, case, time |
| Успешные завершения | 100×N_success(C_closed)/N_closed | is_case_success в согласованном терминальном исходе; промежуточный Success не подходит |
| Экземпляры с технической ошибкой | 100×число c∈C хотя бы с одной согласованной technical-ошибкой / N(C) | event_status+event_error_type+event; счёт уникальных c |
| Экземпляры с бизнес-ошибкой | Та же формула для business | Утверждённое различение ошибки и нормального отрицательного исхода |
| Отказы / отмены | 100×N_исход(C_closed)/N_closed | Разметка конкретных терминальных исходов; отдельно от ошибок |
| Прохождение выбранной операции A | 100×число c с выполнением A / N(C) | operation/event и явное правило выполнения |
| Длительность процесса | D(c)=t_end(c)−t_start(c); среднее ΣD/n, p50/p95 | Оба бизнес-события с поясом; правило повторных границ и валидности интервала |
| Длительность операции | D_A(o)=t_end(o)−t_start(o), среднее по выполнениям A | Две lifecycle-роли и однозначное pairing/grouping; operation недостаточно |
| Интервал между A и B | Δ=t_start(B)−t_end(A) на сопоставленных выполнениях | Доказанный порядок/передача; без него не называть ожиданием очереди |
| Экземпляры с повтором A | 100×число c с n_A(c)>1 / N(C) | n_A — число бизнес-выполнений после разметки, не сообщений |
| Дополнительные выполнения A | Σ_c max(n_A(c)−1,0) | Различение бизнес-повтора, технической попытки и повторной доставки |
| Успешно с первого прохода | 100×N_успех_без_доработки_повтора_ошибки(C_closed)/N_closed | Полная классификация существенных повторов/ошибок; отсутствие записей не доказывает first pass |
| Доля операций системы | 100×N_system_operations/N_classified_operations | employee_id действительно описывает исполнителя O; неизвестные участники отдельно |
| Передачи между участниками | H(c)=Σ_i 1[actor(o_i)≠actor(o_{i−1})]; среднее ΣH/n | Последовательные O, известные employee_id/role, надёжный порядок; параллельные ветки не линейризовать |

Среднее, медиана и p95 — разные представления одной длительности. Для воспроизводимого предложения p-quantile используется nearest-rank: отсортировать n значений, взять значение с индексом ceil(p×n), нумерация от 1. Это проектный выбор, не банковский норматив. При отрицательной/неполной паре длительность не заменяется нулём. Если известны только первое и последнее наблюдения, название — «наблюдаемый интервал», не полная длительность процесса.

Доли сценарных паттернов могут пересекаться: их сумма не обязана быть 100%. Для взаимоисключающих исходов нужен явный классификатор и правило при противоречивых terminal flags. Начатые и завершённые потоки не дают простой «процент завершения» через N_end(W)/N_start(W): это разные популяции.

## Что по этой схеме ещё не определить

- CSAT/CSI: нужны ответы клиентов, шкала и правила агрегации; client_id/message этого не дают.
- Стоимость/FTE: нужны фактические/нормативные трудозатраты, тарифы, правила атрибуции и календарь.
- SLA: нужен установленный срок и режим календаря; p95 не заменяет SLA.
- Полная доля ручного труда: employee_id позволяет классифицировать исполнителя только при подтверждённой семантике, но не измеряет трудозатраты.
- Ожидание vs активная работа: нужны отдельные границы работы и ожидания; разница соседних событий сама по себе не даёт это разложение.
- Доля обращений из обязательного набора: нужны события именно обращения/контакта и связь с экземпляром; нельзя подставлять count(event).

Эти направления остаются среди вопросов к входам и методике. Агент не должен придумывать для них числа или выдавать предложенную custom-формулу за утверждённый показатель КГБ.

## Первичные источники

- [Celonis CALC_THROUGHPUT](https://help.celonis.com/pql46/en/calc_throughput): настраиваемые начальное/конечное события, выбор первого/последнего появления и обработка несогласованных границ. Использован принцип явных границ, а не PQL как runtime-зависимость.
- [PM4Py Statistics](https://processintelligence.solutions/pm4py/examples/statistics/): повторное появление действия в одном экземпляре и интервальные данные для длительности работы. Здесь сначала требуется превращение технических записей в бизнес-выполнения; библиотечный счёт строк не переносится буквально.
- [UiPath Operational monitoring](https://docs.uipath.com/process-mining/automation-cloud/latest/user-guide/operational-monitoring-dashboard): длительности, частоты, first time right; конкретные правила их queue items не навязываются пилоту.
- [UiPath Automation potential](https://docs.uipath.com/process-mining/automation-cloud/latest/user-guide/simulating-automation-potential): различие автоматизированных событий, времени работы и входных данных стоимости. В нашем предложении автоматичность привязана к подтверждённому исполнителю операции.

Схема 21 поля и категории бизнес-событий — из предоставленного SRC-004; пять направлений КГБ и порядок сверки — SRC-047/SRC-050. Подробнее: `docs/METRIC-SOURCE-CHECK.md`. Исследование проверяет определения, не наличие полей в реальном приложении и не точность данных.

# Черновик материалов процесса: `export-onboarding`

Команда собирает из уже сохранённого запуска `analyze` или `demo` небольшой пакет для аналитика и разработчика. Модель не вызывается, целевая репа не читается, формулы и тексты не исполняются, каталог исходного запуска не изменяется. Это черновик по результатам анализа, а не официальный шаблон постановки на учёт: шаблон пока не предоставлен.

```bash
python3 -B run.py export-onboarding --run runs/pilot-01 --out runs/pilot-01-onboarding
```

На Windows: `py -3 -B run.py export-onboarding --run runs\pilot-01 --out runs\pilot-01-onboarding`.

Код выхода: **0** — все четыре стадии выполнены по полной выбранной области; **1** — пакет записан, но запуск частичный (стадия не завершена или `partial_input`); **2** — запуск или каталог назначения отклонён, пакет не создан. Противоречие между полным scope и неполным снимком/кодовым разбором отклоняется. В stdout печатается JSON: путь пакета, `status` (`all_stages_completed` / `partial`), `run_id`, список файлов и `sha256sums_sha256` — SHA-256 файла `SHA256SUMS`. Сохраните это значение отдельно, если нужно позже доказать, что не изменён и сам список хешей.

## Что проверяется до записи

- `--run` — существующий каталог, не symlink. Нужны обычные файлы `bundle.json`, `manifest.json`, `process_map.json`, `log_coverage.json`, `instrumentation_plan.json`, `metric_catalog.json`, `evidence.jsonl`; symlink и специальные файлы отклоняются, лимит 256 MiB на файл. Каталоги `--plan-only`, `discover-logging` и прерванные до сохранения результатов запуски не содержат `bundle.json` и отклоняются явно.
- JSON читается тем же строгим разбором, что и контракты: повторяющиеся ключи, `NaN`/`Infinity` и неизвестные поля отклоняются. Отдельные JSON-файлы и `evidence.jsonl` должны совпадать с `bundle.json`.
- Манифест и четыре артефакта проходят существующие контракты и проверку ссылок на evidence. `run_id` и входные хеши артефактов совпадают с манифестом; состояние стадии совпадает со статусом и блокерами артефакта.
- Идентичность снимка: `snapshot_id` пересчитывается по `repo/*` хешам манифеста; каждая ссылка на код должна принадлежать этому снимку и его файлу.
- Связи: факт → этап и ключи событий этого этапа; доработка → факт, зависимости, место в коде с соответствующим evidence; метрика → факты; все метрики, на которые ссылаются факты и доработки, есть в каталоге. Численное значение метрики отклоняется: текущий режим по исходникам их не рассчитывает.
- Атомарный запуск (R08): необязательные структурированные сведения операции (`details`: вход и ожидаемый результат по реализации, предусловие, условие завершения, тип эффекта, исходы, режимы продолжения/ожидания, внешние обращения, кодовые пояснения, вопросы) в `atomic_map.json` должны совпадать с типизированной копией в `process_map`, включая вложенные evidence; каждое их evidence разрешается в реестре этого снимка. Факты каждой принятой привязки события (`fact_ids`) — известные факты того же этапа, без повторов. Записи прежних запусков без `details` принимаются: у их операций сведений нет.
- `--out` — новый путь вне каталога запуска, родительский каталог уже существует. Существующий путь, путь внутрь запуска (в том числе через symlink родителя) и висячий symlink отклоняются.

Все файлы формируются в памяти и только затем записываются в новый каталог с эксклюзивным созданием. Если запись прервалась, удаляются только файлы, созданные этой командой, и пустой каталог; посторонние файлы не трогаются.

## Состав пакета

| Файл | Содержание |
|---|---|
| `process.md` | Назначение, границы, определение случая; фактическое состояние четырёх стадий и полноты области исходников; этапы с ролями/системами, состоянием «требуется» и наличием ссылок на код; операции внутри этапов, сценарии, переходы; перечень материалов; снимок исходников; открытые вопросы карты и незаполненные части определений метрик |
| `onboarding.json` | Манифест, четыре проверенных артефакта без изменений, evidence с локаторами, якорями и `raw_span_hash`, `source_snapshot`, `scope`, `partial_reasons`, `review_flags`, `guidance_links`, сводка технического разбора, хеши файлов исходного запуска |
| `events.csv` | Найденные сопоставления ключей событий и отдельно предложенные новые события |
| `logging-changes.csv` | Все карточки доработок логирования |
| `metrics.csv` | Определения метрик с формулами и необходимыми фактами |
| `SHA256SUMS` | SHA-256 остальных файлов пакета; проверка: `sha256sum -c SHA256SUMS` (Linux) или `shasum -a 256 -c SHA256SUMS` (macOS) в каталоге пакета |

Обязательный этап или операция без кода остаются в `process.md` с пометкой «ссылок на код нет — реализация не установлена» / «код: не указан» и в JSON с исходными идентификаторами. Если стадия не завершилась, её CSV **не создаётся** (пустая таблица выглядела бы как «доработок не нужно»); `process.md` называет причину. Если не получена карта, этапы не перечисляются, а показывается блокер; заглушка карты остаётся в JSON. Пакет повторяемый: одинаковый запуск даёт побайтно одинаковые файлы.

В пакет не копируются цитаты исходного кода (`safe_quote` в evidence заменён на `null`; найти фрагмент можно по пути, строкам и `raw_span_hash`), бизнес-текст, промпты, запросы/ответы моделей, `diagnostics.json`, трейс, полный инвентарь логирования и список исключённых путей. Технические записи разбора остаются в исходном запуске (`code_review.json`, `code_reduction.json`). Для разбора качества работы инструмента предназначен отдельный `feedback`.

## Колонки CSV

Заголовки — английские имена полей контрактов, чтобы строки можно было сопоставить с `onboarding.json`.

**`events.csv`.** `row_kind`: `mapped_key` — ключ из сопоставления карты, `proposed_new_event` — карточка `add_event`. Ключи сохраняют точное написание из карты (`event_key_status=from_process_map`); это само по себе не подтверждает наличие ключа в исходниках. Строка сохраняет, этап, операции этого этапа с тем же ключом, бизнес-действие, `mapping_operation`, роль в жизненном цикле, правило вхождения/группировки, факты, ссылки на код и evidence. `static_emit_in_cited_range` повторяет статическую проверку стадии покрытия: `found` — в цитированном диапазоне есть буквальный вызов логирования с этим ключом; `not_established` — не найден; `not_assessed` — инвентаря нет. Поле `existing_fields` содержит точные имена полей из соответствующих статических мест; пустой список означает, что поля не выписаны, а не доказанное отсутствие полей. Эти же строки словаря сохранены в `onboarding.json` как `event_dictionary`. `fact_link` показывает основание столбца `fact_ids`: `exact_site_binding` — в атомарном запуске это ровно факты принятой привязки этого места вызова (одинаковый ключ в другом месте другой операции чужих фактов не добавляет); `stage_and_event_key_candidate` — карта без атомарного учёта, факты подобраны по этапу и ключу и остаются кандидатами; `plan_card_fact` — факт карточки предложенного события. Это не доказывает выполнение, доставку или фиксацию результата. Предложенное событие — не найденное и не наблюдаемое: в карточке нет структурированного ключа, поэтому `event_key` пуст, `event_key_status=not_specified_in_plan`, а ссылка на карточку — `plan_card_id`. Ключи не извлекаются из текста описаний. Карточки `map_existing`, `join`, `enrich`, `add_field`, `move_emit`, `fix_delivery` новых событий не создают и есть только в `logging-changes.csv`.

**`logging-changes.csv`.** Действие и его русская подпись, факт и его смысл, этап, `operation_ids` — операции, к которым доработка относится через свой факт и точные привязки атомарной карты, `candidate_operation_ids` — только если точной связи нет: операции, чей код пересекается с местом доработки, или (карта без атомарного учёта) операции с тем же ключом события; это навигационные кандидаты, не установленная принадлежность. Одна карточка остаётся одной строкой даже для общего helper. Далее `location` (`anchored` / `location_unresolved`), место в коде, обоснование, семантика, поля строками `имя: смысл`, момент относительно транзакции, зависимости, метрики, план проверки, evidence.

**`metrics.csv`.** Назначение, полный текст формулы, единица счёта, когорта, окно, временная семантика, политики незавершённых случаев и поздних данных — пустая ячейка означает, что часть определения не задана. Далее необходимые факты (ID и смысл), их ключи событий и связанные доработки. Значений, готовности и блокеров здесь нет: технические состояния и все блокеры — в `onboarding.json`.

## Безопасное и обратимое кодирование ячеек

Файлы — UTF-8 с BOM (для кириллицы в Excel), разделитель запятая, кавычки и переводы строк по RFC 4180. В Excel удобнее открывать через «Данные → Из текстового/CSV-файла» с кодировкой UTF-8 и разделителем «запятая».

Чтобы таблица не исполнила формулу и не скрыла текст:

1. Если значение начинается с `=`, `+`, `-`, `@` (в том числе полноширинных), с апострофа, пробела/перевода строки/табуляции или управляющего/форматирующего символа, к нему добавляется один ведущий апостроф `'`. Обычные десятичные числа вроде `-5` и `-0.25` записываются как есть.
2. Значение с управляющими символами (кроме перевода строки и табуляции) или символами смены направления текста записывается как `'json:` и JSON-строка в ASCII.
3. Списки записываются по одному элементу на строку внутри ячейки; если элемент сам содержит перевод строки или скрытые символы, вся ячейка — `'json:` и JSON-массив. Пустая ячейка означает `null` или пустой список.

Обратное преобразование: ячейка, начинающаяся с `'json:`, — JSON после префикса; иначе снять ровно один ведущий апостроф, если он есть; для списков разделить по переводу строки. Это реализовано в `process_observability.onboarding_export.decode_cell(text, multiple=...)`. Точные значения и структуры всегда есть в `onboarding.json`; ячейка `fields` — представление словаря полей строками `имя: смысл`.

Markdown экранирует разметку, HTML и голые URL (`https\://`, `www\.`) — ссылки и теги из данных не становятся активными; единственные ссылки в `process.md` — на файлы самого пакета.

## Сравнение с ручной эталонной разметкой: `evaluate-map`

```bash
python3 -B run.py evaluate-map --run runs/pilot-01 --oracle oracle.json --out runs/pilot-01-evaluation.json
```

Запуск проверяется так же, как перед экспортом; модель, сеть и исходники не используются, существующий файл результата не перезаписывается. Эталон `operation-oracle/1`: `schema`, `id`, `authored_by: "human"`, `source_snapshot_id` (SHA-256 снимка), `scope` — что именно размечено, `operations[]` с `id`, `label`, `anchors[]` (`path`, `start_line`, `end_line`), необязательные `notes`. Результат `operation-evaluation/1` для каждой ожидаемой операции: `candidate_match` (ровно одна операция карты, не общая с другой ожидаемой), `ambiguous` (несколько операций карты), `collapsed` (одна операция карты пересекает несколько ожидаемых — возможная склейка), `missing`. Операции вне якорей перечислены в `unlabelled_operation_ids` без оценки. Для атомарной карты используются собственные ссылки операции (`model_refs`), иначе все её evidence.

Ограничения: совпадение — только пересечение строк, кандидат для человека; `semantic_verification` всегда `false`; число операций и названия не сравниваются; выводы действуют только для размеченной области. `authored_by` — заявление файла (`oracle_provenance: declared_human_not_verified`); совпадение `source_snapshot_id` не означает повторного чтения исходников. Результат привязан к `map_sha256` (карта, реестр evidence, выбор якорей) и `oracle_sha256`; `evaluation_is_current` возвращает `false` после переименования, смыслового изменения или сдвига цитаты. Чужой снимок ничего не оценивает (код выхода 1). Синтетический эталон тестов не является настоящей ручной оценкой.

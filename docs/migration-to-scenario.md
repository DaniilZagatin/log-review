# Переход к исследователю сценария — 26 октября 2026

По решению пользователя Белка переработана из инструмента оценки инициатив в одного исследователя выбранного сценария. Цель текущей версии — подробная карта атомарных операций через несколько АС.

Из старой Белки сохранены и отделены от прежнего пайплайна: чтение и поиск кода, статические экстракторы, модель фактов, клиент модели, журнал, опциональная трассировка Phoenix, безопасная публикация файлов, шрифты и визуальный стиль.

Из рабочего проекта удалены старые progress/matcher/critic/coherence/passport, обработка инициатив и ответов, Git-mirror целевых репозиториев, React-интерфейс, мониторинг Grafana, старые шаблоны, baseline reviewer и относящиеся к ним тесты/скрипты/документация. Это вывод прежнего продукта из эксплуатации, а не обновление эталона для прохождения проверок.

Перед удалением сохранён проверенный архив исходников:
`archive/legacy-code-before-cleanup-20261026.zip`.
Он содержит manifest и исключает секреты, окружение, сборки и отчёты. Архив не входит в Git. Пользовательские .env, существующие reports/Review_reports и .venv сохранены.

Git подключён к https://github.com/DaniilZagatin/log-review.git. Первый коммит исходников продолжает существующий Initial commit репозитория с README; архив служит локальной точкой восстановления старого исходного кода. Точный перечень удаления сохранён локально в archive/cleanup-manifest.json.

Текущие тесты покрывают новый runtime и переиспользуемые компоненты. Успешное синтетическое демо не подтверждает способность LLM восстановить полный реальный банковский сценарий: это требует отдельного экспертного сравнения.

## 27 октября 2026 — методология атомарных операций, схема 2.0

По новому решению пользователя каталогизация АС и принадлежность операций системам удалены. Вместо start/action/decision/fork/join/wait/end/external остаётся один вид operation. Начальные и последние операции задаются ссылками в scenario, без искусственных управляющих узлов. Связи на поле не имеют надписей; смысловое условие каждой исходящей ветви и следующая операция показаны в карточке исходного узла. Условия хранятся единожды в edges.

Явное внешнее взаимодействие — доказанное свойство операции. Имена функций, пути и кодовые параметры находятся в основаниях, названия операций сформулированы предметно. Архив Passport-anylize-v1 использован как образец языка, а не как эталон глубины: его иерархия КП/процесс/BBB и ограничения количества операций не возвращаются.

Переработаны задачи исследования, покрытие родительских функций дочерними действиями, адресные пробелы, конкретные маршрутные случаи и различение решения/рекомендации/команды/результата. Суммаризация получила собственный бюджет и режим; резервная память, один trace и отсутствие thinking в очереди сохранены. Старые отчёты читаются с пометкой прежней методологии без автоматического признания их атомарными.

## 27 октября 2026 — ревью промптов и инструментов

Системный промпт, промпт сжатия и описания инструментов переписаны как описание текущего порядка, без упоминаний прежней методологии, АС, удалённых видов узлов и полей. Из промпта убраны обязанности обвязки. Условия завершения собраны в один список, роли хранилищ памяти разведены. Описание evidence приводится один раз, поле quote, константные kind и межсистемные поля переходов убраны из схем инструментов; schema.py продолжает принимать их в старых данных. Правка по id передаёт только изменяемые поля. Обновление brief больше не сбрасывает смысловой обзор; правило о том, какие поля операции сбрасывают обзор, приведено в промпте в соответствие с кодом. Ошибки инструментов получили коды; в журнал добавлены cached_tokens и хеши промпта и инструментов. Подсказка при простое больше не подталкивает к finish. Сводка сжатия получила current_focus, failed_attempts и do_not_redo.

Понятие операции уточнено по журналу событий реального процесса: действия пользователя, действия системы и отдельно обработанные результаты по решению пользователя не делятся на группы — все они операции и узлы. Событие начала, которое фиксирует код, — обычная операция; в названии указывается контекст (экран, этап).

## 27 октября 2026 — по итогам прогона logs6

Прогон остановился на повторах: 21 отказ проверки маршрутов без адреса ошибки, 92 задачи на библиотечный Role.builder, пустой basis у всех переходов. Маршрутные случаи теперь проверяются целиком с перечнем номеров случаев, переходов и нужных строк; основания пройденных переходов собирает код. Встроенные роли (builder) получают задачу на своё определение в текущем файле; вызовы одной реализации объединяются в одну задачу с перечнем мест вызова. Новый объект без basis и code_explanations отклоняется сразу. Код и подробности отказа сохраняются в напоминаниях и в сообщении после сжатия; вход суммаризатора больше не ограничен 60 000 символов. Промпт требует отображать каждый шаг процесса отдельной операцией; ответ на сохранение операции содержит подсказки о вероятно крупной операции, названии с «и», outcome у операции с выбором и продолжении конечной операции без completion_condition.

## 28 октября 2026 — слияние с версией Рашида (R07)

После сохранения карты добавлен отдельный отчёт наблюдаемости процесса (`--observability`): каталог мест логирования, смысл записей по выданным строкам кода, контекст процесса и вопросы измерения, необходимые бизнес-факты и их покрытие по отдельным осям, минимальные доработки логирования, определения метрик без значений и комплект передачи разработчикам. Карта остаётся каноническим результатом, карточка операции не меняется. Банковские метрики и каталог полей из материалов Рашида стали необязательным профилем `bank-process-kpi`. Отчёт можно перестроить по сохранённой карте (`--from-map`). Журнал запуска получил дерево span с конечными статусами, счётчик длины reasoning больше не экспортируется.

Правила бизнес-языка Рашида перенесены в методику исследователя без отдельного редакторского этапа: формула названия «действие + предмет + уточнение», в описании — зачем нужна операция, технический статус переводится в предметный смысл только по прочитанному коду. План и решения: docs/integration-belka-rashid.md.

По итогам ревью: покрытие факта оценивается по одной записи целиком; принятые элементы переживают неудачное исправление; раздел отчёта, нарушивший контракт, отбрасывается без потери остальных; готовность метрик перечисляет все пробелы; локальный журнал хранит конечные статусы этапов и связывает вызовы модели со span. Бизнес-описание передаётся исследователю как требования и словарь. Для JVM распознаются структурированные аргументы и ключи MDC. Повторное построение отчёта использует проверенные принятые ответы; запрошенные метриками факты проходят один цикл согласования.

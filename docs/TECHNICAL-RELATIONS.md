# Технические связи (relations)

Технический разбор может сохранять связи между фрагментами кода, чтобы бизнес-разбор (атомарные страницы, см. [DIRECT-ATOMIC.md](DIRECT-ATOMIC.md)) использовал их и не открывал их заново. Связь — это навигация и предложение модели кода, а не исполнение, достижимость или бизнес-переход.

## Включение и идентичность

- `ReviewOptions.relations` (по умолчанию `False`). Если параметр выключен, контракт ответа, байты запросов, `ReviewOptions.to_dict()`, `run_context` и fingerprint остаются прежними: ключ `relations` даже не сериализуется. Поэтому прежние технические кэши и checkpoints используются под своей исходной идентичностью.
- Включённый параметр — это новая техническая идентичность: другой system prompt, другой brief (`relation_kinds`, `relation_resolutions`, `reply_schema.relations`, лимит `max_relations`, `RELATION_INSTRUCTIONS`) и другой fingerprint. Кэш, записанный без связей, такому запуску не подходит. Возобновление разбора с изменёнными опциями останавливается с `ReviewResumeError`: старые ответы к новому запросу не перепривязываются.
- System prompt worker: без связей отправляется исходный `CODE_REVIEW_SYSTEM` байт в байт («all four top-level arrays»). Со связями отправляется `CODE_REVIEW_RELATIONS_SYSTEM`: тот же текст, где явно названы пять массивов (`findings, interval_status, requests, unknowns, relations`), и одна заметка `RELATIONS_SYSTEM_NOTE` о строках связей. Противоречия «ровно четыре массива плюс пятый» в нём нет.
- CLI: `--technical-relations collect|off`. По умолчанию связи собираются в режиме `--map-mode atomic` и не собираются в `coarse-refine`. Чтобы через `--resume-from` переиспользовать технический разбор, записанный без связей, укажите `off`: тогда разбор используется под исходной идентичностью, а статус связей будет `not_collected`. Со значением по умолчанию такое возобновление отклоняется до вызова модели. Синтетический demo и его записанные ответы не меняются: он идёт прежним путём без связей.

## Контракт ответа worker

Если связи включены, в ответе обязателен верхний массив `relations` (пустой `[]`, если связей нет). Элементов не больше `MAX_RELATIONS_PER_TASK` (40).

| Поле | Значение |
|---|---|
| `id` | локальный ID ответа, уникальный в нём; хост заменяет его своим `cr-…` |
| `kind` | `call`, `dispatch`, `callback`, `branch`, `return`, `data_handoff`, `control_handoff` |
| `source` | REF строк, где связь записана |
| `target` | `symbol_id` (символ, показанный этому заданию), `ref` (диапазон внутри выданного текста) или `label` (как написано в тексте) |
| `resolution` | `resolved` — только с `symbol_id` из выданных символов задания или `ref` внутри выданного текста; `unresolved` и `external` — только с `label`, без ID и диапазона |
| `condition`, `data` | только если текст их показывает, иначе `null`; длина ограничена |
| `refs` | REF строк, которые показывают связь (вызов, регистрацию, условие) |

Проверка ответа (`review_execution._relations`) выполняется так же, как проверка находок: любая ошибка отклоняет весь ответ и получает один обычный repair.

| Код | Когда |
|---|---|
| `ref_outside_supplied` (и прежние коды REF) | источник, ссылка или диапазон цели выходят за выданный замороженный текст |
| `relation_target` | `resolved` без базы, проверяемой хостом (неизвестный локальный ID, нет ни `symbol_id`, ни `ref`); у `unresolved`/`external` есть ID или диапазон или нет `label` |
| `relation_kind` | неизвестный вид связи |
| `relation_fields` | лишние или пропущенные поля, повтор локального ID, слишком длинный текст |
| `relations` | превышен лимит связей на задание |

Принятые связи хранятся в результате технического разбора (`code_review.json → relations`) со статусом:

- `collected` — контракт запрашивал связи, и все принятые ответы их содержали;
- `partial` — часть заданий не завершилась; сохранено только принятое;
- `not_collected` — исходный контракт связей не запрашивал. Это и прежние кэши, и запуски с `off`; ничего не синтезируется.

У каждой связи есть `origin: worker_proposal`, `basis: model_proposal`, ID задания и интервалов, ID доказательств. ID хоста `cr-…` вычисляется из всех содержательных полей: задания, вида, источника, цели, разрешения, `condition`, `data` и ссылок. Поэтому альтернативы с другим условием, другими данными или другим разрешением остаются разными связями, и их ID не зависят от порядка строк ответа. Один раз сохраняется только точный дубликат (то же содержание, другой локальный `id`). Нечёткого сопоставления нет.

## Реестр `technical_relations.json`

`technical_relations.build_registry` строит реестр запуска из принятого разбора и статического графа кода (`technical-relations/1`):

- `worker` — связи worker. Цель всегда содержит все ключи (`symbol_id`, `ref`, `label`, `path`, `start_line`, `end_line`, `qualname`); путь и строки заполнены, если символ известен графу или указан `ref`;
- `host_static` — по одной строке на запись вызова статического графа (`kind: static_call`, `resolution` `resolved` или `unresolved`). Это только навигация. Строка хранит исходный `call_id` и колонку (`source.column`), и оба входят в её ID `hr-…`. Поэтому два вызова одного вызываемого на одной строке остаются двумя строками;
- `summary` — количество по происхождению, видам и разрешению; `registry_sha256` — хеш всего содержимого; привязка к `snapshot_id` и `review_run_fingerprint`.

Два происхождения никогда не смешиваются. При `not_collected` строк `worker` нет, а `host_static` есть.

- **Где используется.** `bundle.json → technical_relations` содержит привязку (`file`, `schema`, `registry_sha256`, `review_run_fingerprint`, `status`, счётчики), а `bundle.code_review.relations` — статус и количество. Атомарная запись (`atomic_map.code_led.technical_relations`) несёт ту же привязку.
- **Проверка при экспорте.** `check_registry` проверяет:
  - схему и собственный хеш, снимок и разбор (SHA-256), статус и текст `basis`;
  - полную вложенную форму каждой строки, отдельно для worker и host: точный набор ключей источника, цели и ссылок; безопасный относительный путь (без `..`, абсолютных путей и `\`); целые номера строк `1 <= start <= end` (bool не принимается); виды и разрешения из перечислений; цель `resolved` с проверяемой базой; `unresolved`/`external` только с `label`; у host-строки нет условия, данных, ссылок и задания;
  - уникальность ID строк;
  - отсутствие строк worker при `not_collected`;
  - сводку, пересчитанную по строкам.

  Ошибка называет точное место (например, `host_static[0].source.path`). Экспорт сверяет файл с привязкой в записи и bundle. Изменённый, чужой или некорректный реестр отклоняется, даже если его хеш пересчитан: собственный хеш ловит только случайные изменения и не является подписью.

## Использование на атомарных страницах

- Связи переводятся в единицы: цель связи — это самая маленькая единица, строки которой содержат диапазон цели. Разрешённые цели видов `call`, `dispatch`, `callback`, `data_handoff`, `control_handoff` и `static_call` добавляются к зависимостям единицы. Это только выбор исходников и порядок страниц.
- На странице у единицы до `RELATIONS_PER_UNIT` (8) строк связей: сначала worker, потом статические. Строка содержит происхождение, вид, разрешение, строки источника, цель, номер единицы или строки контекста цели и уже принятые операции цели. Остаток посчитан в `context_omissions.relations_omitted`.
- Связь, вызов или регистрация сами по себе не создают переход. Переход операций возникает только из ответа страницы с цитатами и основанием `source_condition`, `source_call` или `source_handoff`. Для `source_handoff` нужен буквальный контракт минимум в двух процитированных диапазонах. Цель `unresolved` или `external` ничего не говорит о поведении получателя.

## Ограничения

- Связи — предложения модели, проверенные только по выданному тексту и известным символам. Это не вызов во время выполнения и не бизнес-смысл.
- Статический граф не видит динамическую диспетчеризацию; связь `unresolved` остаётся неразрешённой.
- Сокращение разбора (`review_reduction`) связи не пересчитывает. Они живут в результате разбора, его checkpoints и реестре.
- При `not_collected` (прежние кэши) бизнес-разбор опирается только на статические вызовы. Это видно в статусе и не выдаётся за полный сбор.

# Белка: исследователь варианта сценария

Один агент исследует несколько директорий или ZIP с кодом и постепенно строит
сквозную карту конкретного варианта бизнес-сценария. Процесс может содержать
несколько сценариев; в одном запуске выбран один вариант. Вход — исходники и
краткое описание варианта. Обоснование мониторинга и образ результата не нужны.

## Запуск

Установка в окружение Python 3.11+: `python -m pip install -e .`.
Из корня этой папки в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pko.cli map-scenario `
  --scenario-text "Новая дебетовая карта действующему клиенту через мобильное приложение, до выпуска или отказа; перевыпуск исключён" `
  --source "D:\Исходники\Канал" `
  --source "D:\Исходники\ОбработкаЗаявок.zip" `
  --source "D:\Исходники\ВыпускКарт" `
  --out "scenario-map-out"
```

Вместо `--scenario-text` можно передать `--scenario-file scenario.txt` (UTF-8).
Описание — свободный текст; заранее перечислять все шаги и АС не требуется.
Каждый `--source` задаёт отдельную директорию или ZIP. Имена файлов разных
источников не смешиваются. Принадлежность к АС устанавливается исследованием,
а не именем папки. Ссылки и junction не обходятся; секреты и служебные каталоги
исключаются, значения секретов маскируются до анализа. Код источников не меняется.

Первый запуск использует прежнее подключение модели Белки. Отдельная настройка:

```text
PKO_SCENARIO_BASE_URL
PKO_SCENARIO_MODEL
PKO_SCENARIO_API_KEY
PKO_SCENARIO_CLIENT_CERT / PKO_SCENARIO_CLIENT_KEY
```

При изменении endpoint прежние ключи и сертификаты автоматически не передаются.
Флаги `--thinking` / `--no-thinking` управляют режимом модели. Для нового endpoint
по умолчанию не добавляются нестандартные параметры reasoning (кроме GLM).
Сами исходники отправляются только настроенному LLM-провайдеру, локально работает
обвязка инструментов. В аудите нет ключей или внутренних рассуждений модели.

Лимиты: `--max-steps 180`, `--max-seconds 1200`. Лимит времени мягкий: проверяется
между действиями; ожидание каждой сетевой операции ограничено остатком бюджета.
Медленный непрерывный ответ может превысить этот лимит. Автоматические
сетевые повторы этого агента выключены. При ошибке, лимите или прерывании
сохраняется частичный результат. Исследование не запускает загруженный код.

## Результат

- `scenario_map.html` — автономная карта в стиле прежнего HTML Белки: шрифт
  SB Sans, мятное поле, белые карточки, фиолетовый акцент, масштаб и карточка шага.
  Сверху — компактная сводка, остальную доступную область занимает карта.
  Подробности шага или перехода открываются по нажатию в закрываемой панели.
  Поле единое: шаги соединены плавными направленными линиями, АС указаны на узлах.
  Карточки раскрывают переходы, условия и пробелы. Полная карта должна быть связной;
  неподключённые фрагменты допускаются только как явно обозначенный частичный результат.
- `scenario_map.json` — сценарий, источники, системы, шаги, переходы, доказательные
  фрагменты, границы и состояние исследования.
- `scenario_map.checkpoint.json` — последняя сохранённая точка исследования
  (автоматическое возобновление пока не реализовано).
- `audit/run_*.txt` — журнал наблюдаемых вызовов и результатов инструментов.

Цвет и текст различают наблюдаемое в коде, вывод по коду и неустановленное.
Проверка цитаты доказывает её происхождение, а не истинность бизнес-интерпретации.
Неизвестные системы, пропущенные исходники и связи не подменяются догадками.
Завершение не означает проверку промышленной среды или полноту всех АС банка.

Коды выхода: 0 — исследование завершено; 2 — частичный результат; 1 — ошибка;
130 — прерывание с сохранением. Пробелы и предположения сохраняются явно.

## Устройство

Новое ядро — `backend/pko/scenario_map/`: sources (снимок материалов), schema
(карта и проверки), tools (изменение карты), agent (одна сессия), config
(подключение), runner (CLI/сохранение). Это компоненты одного агента, не этапы
нескольких LLM-сессий. Исследователь читает исходники и меняет карту в любом порядке.
Программные проверки возвращают ошибки инструментов для исправления.

Из Белки используются FileTree, экстракторы Python/Java/SQL и контрактов, ToolBox,
клиент модели, аудит, трассировка, публикация и оформление. Инструменты чтения
перенесены в `code_tools/`, экстракторы работают через независимый FileTree.
Старые progress/matcher/critic/coherence/passport_agent, ProgressModel и команды
удалены: их код доступен в локальном архиве, описанном в migration-to-scenario.md.

Глубина статического разбора зависит от языка; остальные файлы доступны через
чтение и поиск. Совпадение URL/имени события лишь повод для проверки. Для
наблюдаемого межсистемного перехода нужны основания обеих сторон и контракт.
Схема 1.2 хранит `groups` отдельно от `nodes`: `stage` (этап) и `operation`
(бизнес-операция с `parent_id` этапа). `node.group_id` ссылается на операцию.
У группы есть имя, цель/result и проверенные буквальные цитаты. Группа может
охватывать несколько АС и не создаёт переходов исполнения. Программные проверки
не доказывают правильность её бизнес-интерпретации.

Каждое атомарное действие к завершению должно иметь группу либо адресный пробел;
пустые группы и некорректная иерархия не принимаются. Удаление группы с действующими
ссылками отклоняется. Старый `node.parent_id` поддержан для совместимости, но
новая бизнес-группировка использует `group_id`.

В HTML выбор этапа в верхней панели выделяет и вписывает его узлы в область
видимости. Нажатие на узел выделяет все узлы той же бизнес-операции, сохраняя
остальные узлы на поле. Узел без группы выделяется самостоятельно.
Карточка действия показывает его группу. Развилки отображаются ромбами,
управляющие узлы имеют отдельные обозначения; все выходы решения требуют условий
или адресного пробела. `end.outcome`: success/refusal/failure/cancelled/unknown;
рендерер не угадывает исход по имени. Логирование в карту не включено.

## Проверка детализации

Начиная со схемы 1.1, `execution_reviews` хранит перечень атомарных действий с действием,
эффектом, точкой отказа и цитатами. Каждая известная операция action/decision/wait/external
требует своей записи и своего узла. Две операции нельзя присоединить к одному
крупному шагу. Начало, конец и управляющие fork/join не обязаны быть операциями.

Инструмент `review_execution` дополнительно требует пять проверок: ветви,
отказы, интеграции, изменения состояния, вычисления. `not_found` означает
«не найдено в обследованном фрагменте», а `unknown` требует адресного пробела.
Обзор становится неактуальным после изменения связанных узлов или переходов.

Код сверяет карту с составленным агентом перечнем, но не доказывает, что агент
обнаружил все операции в исходниках. В JSON это разделено через `detail_review`:
покрытие реестра проверяется, `semantic_completeness_verified` остаётся false.
Старые JSON без обзоров можно открыть с отметкой `legacy_unverified`.
Полный перечень 16 инструментов приведён в README.

## Проверка

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p "test_scenario_*.py"
.\.venv\Scripts\python.exe -B tests/run_tests.py
.\.venv\Scripts\python.exe -B scripts/demo_scenario_map.py
```

Демонстрация использует синтетический код трёх АС и заранее заданные ответы
модели; она проверяет сборку, а не качество LLM. Результат помечен «Учебный пример».
Семантическое качество нужно отдельно измерять на согласованной со специалистом
карте реального сценария: пропущенные шаги, ложные переходы, границы варианта.
Логирование бизнес-событий, рекомендации для дашбордов и чат в текущую версию
не входят.

# Белка: исследователь варианта сценария

Один агент исследует одну или несколько директорий/ZIP с кодом и постепенно
строит сквозную карту конкретного варианта бизнес-сценария. Сценарий может целиком
выполняться внутри одной АС либо включать переходы в другие АС. Количество АС
устанавливается по материалам, а не по числу источников; несколько АС не обязательны.
Процесс может содержать несколько сценариев; в одном запуске выбран один вариант.
Вход — исходники и краткое описание варианта. Обоснование мониторинга и образ
результата не нужны.

## Запуск

Установка в окружение Python 3.11+: `python -m pip install -e .`.
Из корня этой папки в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pko.cli map-scenario `
  --scenario-text "Новая дебетовая карта действующему клиенту через мобильное приложение, до выпуска или отказа; перевыпуск исключён" `
  --source "D:\Исходники\Канал" `
  --source "D:\Исходники\ОбработкаЗаявок.zip" `
  --source "D:\Исходники\ВыпускКарт" `
  --out "scenario-map-out"
```

Вместо `--scenario-text` можно передать `--scenario-file scenario.txt` (UTF-8).
Описание — свободный текст; заранее перечислять все шаги и АС не требуется.
Каждый `--source` задаёт отдельную директорию или ZIP. Имена файлов разных
источников не смешиваются. Принадлежность к АС устанавливается исследованием,
а не именем папки. Ссылки и junction не обходятся; секреты и служебные каталоги
исключаются, значения секретов маскируются до анализа. Код источников не меняется.

Первый запуск использует прежнее подключение модели Белки. Отдельная настройка:

```text
PKO_SCENARIO_BASE_URL
PKO_SCENARIO_MODEL
PKO_SCENARIO_API_KEY
PKO_SCENARIO_CLIENT_CERT / PKO_SCENARIO_CLIENT_KEY
```

При изменении endpoint прежние ключи и сертификаты автоматически не передаются.
Флаги `--thinking` / `--no-thinking` управляют режимом модели. Для нового endpoint
по умолчанию не добавляются нестандартные параметры reasoning (кроме GLM).
Сами исходники отправляются только настроенному LLM-провайдеру, локально работает
обвязка инструментов. В аудите нет ключей или внутренних рассуждений модели.

Лимиты: `--max-steps 180`, `--model-timeout 900` (15 минут ожидания модели),
`--max-seconds 7200` (2 часа на исследование). Для длинных очередей можно указать,
например, `--model-timeout 1800 --max-seconds 14400`. Лимит времени мягкий:
проверяется между действиями; ожидание каждой сетевой операции ограничено
минимумом model-timeout и остатка общего бюджета.
Медленный непрерывный ответ может превысить этот лимит. Временные сетевые ошибки,
таймауты, HTTP 408/429 и 5xx повторяются обвязкой: максимум четыре попытки текущего
запроса, паузы примерно 2/4/8 секунд с небольшим случайным разбросом. `Retry-After`
задаёт минимальную паузу; если она не помещается в оставшийся бюджет, сохраняется
частичный результат без нового запроса. Ожидание и запросы расходуют общий бюджет времени.
SDK-повторы выключены, повтор выполняется только в одном слое. История сохраняется,
уже выполненные инструменты не запускаются заново, перед ожиданием пишется checkpoint.
Постоянные ошибки (например, 400/401/403 или неверный формат ответа) не повторяются.
Попытки и ожидания видны в аудите и едином Phoenix trace. При исчерпании повторов,
лимите или прерывании сохраняется доступный результат. Исследование не запускает
загруженный код.

## Результат

- `scenario_map.html` — автономная карта в стиле прежнего HTML Белки: шрифт
  SB Sans, мятное поле, белые карточки, фиолетовый акцент, масштаб и карточка шага.
  Сверху — компактная сводка, остальную доступную область занимает карта.
  Подробности шага или перехода открываются по нажатию в закрываемой панели.
  Поле единое: шаги соединены плавными направленными линиями, АС указаны на узлах.
  Карточки раскрывают переходы, условия и пробелы. Полная карта должна быть связной;
  неподключённые фрагменты допускаются только как явно обозначенный частичный результат.
- `scenario_map.json` — сценарий, источники, системы, шаги, переходы, доказательные
  фрагменты, границы и состояние исследования.
- `scenario_map.checkpoint.json` — последняя сохранённая точка исследования
  (автоматическое возобновление пока не реализовано).
- `audit/run_*.txt` — журнал наблюдаемых вызовов и результатов инструментов.

Цвет и текст различают наблюдаемое в коде, вывод по коду и неустановленное.
Проверка цитаты доказывает её происхождение, а не истинность бизнес-интерпретации.
Неизвестные системы, пропущенные исходники и связи не подменяются догадками.
Завершение не означает проверку промышленной среды или полноту всех АС банка.

Коды выхода: 0 — исследование завершено; 2 — частичный результат; 1 — ошибка;
130 — прерывание с сохранением. Пробелы и предположения сохраняются явно.

## Устройство

Новое ядро — `backend/pko/scenario_map/`: sources (снимок материалов), schema
(карта и проверки), tools (изменение карты), agent (одна сессия), config
(подключение), runner (CLI/сохранение). Это компоненты одного агента, не этапы
нескольких LLM-сессий. Исследователь читает исходники и меняет карту в любом порядке.
Программные проверки возвращают ошибки инструментов для исправления.

Из Белки используются FileTree, экстракторы Python/Java/SQL и контрактов, ToolBox,
клиент модели, аудит, трассировка, публикация и оформление. Инструменты чтения
перенесены в `code_tools/`, экстракторы работают через независимый FileTree.
Старые progress/matcher/critic/coherence/passport_agent, ProgressModel и команды
удалены: их код доступен в локальном архиве, описанном в migration-to-scenario.md.

Глубина статического разбора зависит от языка; остальные файлы доступны через
чтение и поиск. Совпадение URL/имени события лишь повод для проверки. Для
наблюдаемого межсистемного перехода нужны основания обеих сторон и контракт.
Схема 1.4 хранит `groups` отдельно от `nodes`: только `stage` (этап).
`node.group_id` ссылается непосредственно на этап; вложенных групп нет.
У группы есть имя, цель/result и проверенные буквальные цитаты. Группа может
охватывать несколько АС и не создаёт переходов исполнения. Программные проверки
не доказывают правильность её бизнес-интерпретации.

Каждое атомарное действие к завершению должно иметь группу либо адресный пробел;
пустые группы и ссылки на несуществующие этапы не принимаются. Удаление группы с действующими
ссылками отклоняется. Старый `node.parent_id` поддержан для совместимости, но
новая бизнес-группировка использует `group_id`.

В HTML выбор этапа в верхней панели выделяет и вписывает его узлы в область
видимости. Нажатие на узел выделяет его и непосредственно связанные узлы,
сохраняя остальные узлы на поле. Карточка действия показывает его этап,
бизнес-описание и отдельное обоснование `basis`; технические цитаты раскрываются
по запросу. Рендерер поддерживает старые JSON с группами stage/operation.
Развилки отображаются ромбами,
управляющие узлы имеют отдельные обозначения; все выходы решения требуют условий
или адресного пробела. `end.outcome`: success/refusal/failure/cancelled/unknown;
рендерер не угадывает исход по имени. Логирование в карту не включено.

## АС и основания

АС — автоматизированная система с назначением, обрабатываемыми данными и
границей исполнения/интеграции. Названия и границы ищутся в README, конфигурации,
точках входа, развёртывании, клиентах API, очередях и контрактах. Каталог, класс,
микросервис или общий URL сами по себе не устанавливают принадлежность к АС.
Если официальное имя неизвестно, допускается описательное название с оговоркой.

У системы `implementation` разделяет наличие исследуемой реализации (`provided`),
только внешние упоминания/клиенты (`external`) и неустановленное (`unknown`).
`source_ids` указывают, где найдены основания; это не доказательство наличия
реализации. `basis` поясняет вывод. Доказанность существования системы отделена
от доступности её кода. Вызов API относится к вызывающей системе. Для `external`
нельзя принять `observed` внутреннее действие или межсистемный переход: нужны
реализация второй стороны либо явные `inferred`/`unknown` и границы знания.
Узлы внешней системы требуют адресного пробела. Они не требуют и не принимают
обзор `review_execution` недоступной реализации; в сводке детализации сохраняются
как `external_node_ids`, результат остаётся частичным. После получения кода
систему можно перевести в `provided` и исследовать её действия обычным образом.

Основания инструментов передаются как `path`, `line_start`, `line_end`. Код
подставляет `quote` из маскированных строк, уже выданных через `read_file`;
файл заново не открывается. Непрочитанный диапазон отклоняется. Старые вызовы
с явным `quote` поддержаны, но несовпадение текста остаётся ошибкой. Это убирает
ручное копирование цитат, сохраняя проверку их происхождения.

Названия действий формулируются как действие и объект. Описание кратко передаёт
цель, действие и результат; `basis` — публичное объяснение «факт → вывод → граница
знания». Создание объекта клиента не доказывает регистрацию клиента в системе,
упоминание обработчика — выполнение всей цепочки, отправка запроса — бизнес-эффект.
Смысл этих выводов остаётся предметом экспертной сверки.

## Проверка детализации

Начиная со схемы 1.1, `execution_reviews` хранит перечень атомарных действий с действием,
эффектом, точкой отказа и цитатами. Каждая известная операция action/decision/wait/external
требует своей записи и своего узла. Две операции нельзя присоединить к одному
крупному шагу. Начало, конец и управляющие fork/join не обязаны быть операциями.

Инструмент `review_execution` дополнительно требует пять проверок: ветви,
отказы, интеграции, изменения состояния, вычисления. `not_found` означает
«не найдено в обследованном фрагменте», а `unknown` требует адресного пробела.
Обзор становится неактуальным после изменения поведения, оснований или переходов.
Переименование, перенос в другой этап и редактирование `basis` не меняют его
актуальность; изменение описания, входов, выходов или условий требует обновления.

Код сверяет карту с составленным агентом перечнем, но не доказывает, что агент
обнаружил все операции в исходниках. В JSON это разделено через `detail_review`:
покрытие реестра проверяется, `semantic_completeness_verified` остаётся false.
Старые JSON без обзоров можно открыть с отметкой `legacy_unverified`.
Полный перечень 20 инструментов приведён в README.

## Контроль незавершённой работы и смысловая проверка

Схема 1.6 добавляет `research_tasks`: сохраняемый список обнаруженных функций,
промптов, ветвей и вложенных исполнителей. Он входит в JSON и checkpoint, доступен
через `inspect_map(section='research_tasks')`; открытые задачи видны также в
`frontier`. Явные Java-ссылки `.addChild(Class.method...)`,
`.systemPrompt(Class.field)` и `return Class.createAgent(...)` обнаруживаются
в реально выданных строках. Комментарии и строки маскируются при поиске этих
ссылок. Это ограниченные лексические подсказки, не полный анализ зависимостей;
остальную работу исследователь регистрирует через `save_research_task`.

Статусы задачи: `open`, `mapped`, `out_of_scope`, `gap`. Для `mapped` нужны
ID действий; автоматическая зависимость дополнительно требует прочитанного
объявления в файле реализации и пересечения с основаниями действия карты.
Одна регистрация исполнителя не считается раскрытием его исполнения. `gap`
ссылается на сохранённый пробел, `out_of_scope` объясняет исключение из варианта.
Открытые задачи, устаревшие ссылки и переполнение списка блокируют `finish`;
лимиты при этом сохраняют частичный результат. Девять ветвей диспетчера требуют
рассмотрения девяти зависимостей, а не одного общего узла «выполнить сценарий».
Семантическую достаточность такого рассмотрения проверяет агент и затем эксперт.

У узлов и связей обязательны публичное `basis` и, при известных основаниях,
`code_explanations`. Пояснение содержит `kind`, `symbol`, `explanation`, `evidence`.
Проверяются прочитанность, пересечение с основаниями объекта и наличие объявления
функции/поля. Поддерживаются имена Python/Java; при неподдержанной конструкции
используется `fragment` с пустым именем, для лямбды — `lambda`. Имя не угадывается.
В карточке: **app.py · submit()**, затем смысл функции в этом действии.
Цитаты раскрываются отдельно. Старые JSON без этих полей продолжают отображаться.

`end.effect_kind` различает `decision`, `recommendation`, `command`, `result`,
`unknown`. Рекомендация запустить процесс не подтверждает фактический возврат денег.
Конечный узел с неизвестным уровнем эффекта не проходит завершение. У любого
узла, кроме `fork`, несколько управляющих выходов требуют явных условий на каждом:
прохождение общего участка не должно терять категорию ранее выбранного маршрута.

Перед `finish` тот же агент вызывает `review_semantics`. Пять разделов —
`outcomes`, `order`, `routing`, `atomicity`, `dependencies` — содержат публичное
обоснование, прочитанные основания и ссылки на узлы/переходы/пробелы. Для
неустановленного требуется `uncertain` с gap; исходы охватывают все конечные узлы.
Обзор связан с текущим состоянием карты, сводки и задач. Последующие изменения
требуют обновления. Статус `model_reviewed_not_verified` прямо отличает оценку
модели от доказанной семантической корректности. Скрытые рассуждения не сохраняются.

Ошибка `review_execution` теперь возвращает `details.missing_evidence` с точными
непокрытыми path/line_start/line_end и ID узла. Исследователю не приходится
угадывать, какой файл добавить в область обзора. Обзоры рекомендуется сохранять
небольшими законченными фрагментами по мере построения карты.

После чтения новых диапазонов сводка `research_brief` требует актуализации перед
завершением. Сжатие сохраняет перечень задач вне диалога; в сводке явно отмечается,
показаны ли все открытые задачи, и указывается способ восстановления полного списка.
В аудите `research_configuration` фиксирует модель, режим, окно и лимиты;
`run_finished` сообщает `completed`/`partial`/`failed`. Сжатие и все шаги по-прежнему
входят в один корневой trace. Это не добавляет автоматического возобновления checkpoint.

Все линии HTML строятся кубическими кривыми: прямые направления, возвраты,
длинные переходы, параллельные связи и петли. Составные внешние маршруты имеют
общую касательную на стыках; сохраняются обход карточек, подписи и область нажатия.

## Память исследования и сжатие

Схема 1.5 добавляет две отдельные сводки. `research_brief` — сохраняемое агентом
общее понимание проекта и его связи с выбранным вариантом. `save_research_brief`
обязателен в цикле агента до первого узла/перехода: назначение и границы одной
или нескольких АС, связь описания со входом/сущностями/исходами, факты с цитатами,
`flow_hypothesis`, открытые вопросы и следующие проверки. Гипотеза не является
узлами или доказанным порядком исполнения. Код проверяет прочитанность оснований,
формат и размер (до 12000 символов без цитат), а не правильность интерпретации.
Обновление заменяет сводку целиком и повышает revision только при изменении.
Новые данные должны уточнять сводку и уже построенную карту; перед завершением
вопросы о неизвестных участках карты отражаются адресными gaps.

`context_summary` — автоматическая публичная сводка истории: связь проекта со
сценарием, выполненная работа, выводы, открытые вопросы, следующие действия и
ссылки. При размере диалога выше 85% его расчётного бюджета выполняется одна
попытка суммаризации через текущий настроенный Chat Completions endpoint без
инструментов. Запрос расходует общий бюджет времени; отдельных вложенных повторов
нет. Вход: предыдущая сводка, актуальное состояние и завершённые обмены текущего
контекста. Исходная системная инструкция и задание сохраняются отдельно без
пересказа. Скрытые рассуждения не передаются суммаризатору. Слишком длинные
публичные материалы сокращаются с явной отметкой; их оригиналы доступны в памяти
и аудите. Ответ принимается только как JSON заданной формы до 6000 символов;
ссылки проверяются по кешу read_file. Вызовы инструментов в ответе отвергаются.
Ошибки провайдера или валидации оставляют прежнюю сводку и включают обычное
восстановление из состояния. Замена диалога принимается только при уменьшении
размера и соблюдении бюджета. После неудачного уменьшения следующая плановая
попытка откладывается на четыре шага; превышение жёсткого бюджета требует проверки
сразу. Прерывание сохраняет частичный результат. Метаданные сводки явно сохраняют
число пропущенных обменов и сокращённых полей входа, а также полноту списка заметок.

Один запуск имеет один корневой трейс `scenario_map_run`. Обычные шаги, инструменты,
checkpoint, сжатие и его отдельный LLM-вызов находятся внутри этого же трейса.
У `compact_context` и `context_summary` сохраняется номер шага; дополнительные
вызовы учитываются в `run.context_summary_calls`, успешные сводки — в
`run.context_summaries`, резервные восстановления — в `run.context_summary_fallbacks`.

Обе сводки входят в checkpoint и итоговый JSON; `inspect_map` возвращает их
целиком в разделах `research_brief` и `context_summary`, без текстов цитат.
Сжатие сначала резервирует реестр графа, затем рабочую сводку проекта и сводку
истории, затем остальные метаданные и последние целые обмены. Если сводка не
помещается, сохраняются revision, `content_complete=false` и адрес восстановления.
Карта и рабочая сводка приоритетнее старого пересказа. Никакая сводка не создаёт
новых оснований и не заменяет проверку узлов и связей. Это переносимый механизм
для текущего клиента, не интеграция с OpenAI Responses `/compact`.

Ориентиры реализации: предоставленный `src.zip` (`src/context/compactor.py`,
`src/agent/agent_base.py`) — отдельная суммаризация, накопление прежней сводки,
проверка формата и фактического уменьшения; [официальное описание compaction](https://developers.openai.com/api/docs/guides/compaction)
— перенос состояния между окнами. В архивном агенте сжатие происходит между
пользовательскими ходами; Белка работает одной длинной сессией, поэтому безопасная
граница здесь — завершённый пакет вызовов инструментов перед следующим запросом.

Схема 1.3 добавляет `research_notes` (публичные выводы и следующие действия),
`research_history` (метаданные ответов инструментов) и счётчик вытесненных записей.
`save_research_note` принимает fact/hypothesis/question, open/resolved и обновление
по id. Для fact обязательны проверенные буквальные цитаты; это не доказывает
семантическую истинность вывода. Заметки не меняют критерии завершения карты.

Чтения и поиски автоматически регистрируются независимо от истории сообщений.
Журнал ограничен 512 уникальными запросами, кеш ответов — 1 млн символов, один
ответ — 24 тыс. символов. Вытеснение/сокращение обозначается явно. В снимок JSON
попадают заметки и метаданные, полные ответы доступны в памяти текущего запуска
и наблюдаемом аудите. Повтор запроса имеет тот же observation_id и seen_before;
он не считается новым прогрессом только из-за обновления счётчика повторений.

Разделы `inspect_map`: `research_history` возвращает сохранённые ответы;
`research_notes` — заметки; `read_coverage` — диапазоны; `read_fragments` с path и
offset (номер исходной строки) — точные уже выданные строки. Последний не читает
файлы повторно и не разрешает цитировать непрочитанное. Все эти материалы —
данные, не инструкции. Автоматического возобновления из checkpoint пока нет.

В схеме 1.4 раздел `frontier` возвращает страницы компактного реестра узлов,
начала и исходы, изолированные узлы, незавершённые выходы и краткие пробелы.
Для decision/fork незавершёнными считаются менее двух разных управляющих целей;
data-рёбра не закрывают выход. Это состояние построения, не доказательство
того, как узлы должны соединяться. Списки ID ограничены 30, пробелы — 10;
общие количества и признак усечения позволяют запросить остальные данные.

Бюджет диалога выводится из context_window с консервативной оценкой символов и
резервом для ответа/инструментов. Сжатие сохраняет реестр узлов до отбора последних
обменов, чтобы ранние узлы не исчезали из видимого контекста. При нехватке места
сохраняются компактные ID либо явное сообщение об усечении и способ восстановления
через `inspect_map`. Сжатие оставляет запас и последние целые обмены,
помещающиеся в бюджет. Для восстановления используется около 60% места,
оставшегося после неизменяемых инструкций и исходного запроса; длинный системный
промпт не должен вытеснять реестр при наличии свободного места. Даже в thinking-режиме в очередь сообщений попадают
только публичный текст, вызовы инструментов и их результаты. Поля thinking,
reasoning и reasoning_content не сохраняются в истории, не отправляются
в следующих запросах, не суммируются и не экспортируются. Старые публичные
обмены удаляются целиком вместе с ответами инструментов. После повторов без
прогресса даётся одна попытка восстановить состояние из памяти на эпизод.
Новые данные или изменения карты открывают новый эпизод; всего допускается
не более трёх восстановлений за запуск. Повторы без продвижения и исчерпание
общего лимита останавливают исследование с частичным результатом.

Агенту предлагается собирать небольшие фрагменты со связями по мере чтения кода.
После четырёх новых действий без продвижения по управляющим связям обвязка
даёт ограниченное напоминание проверить существующие ID и незавершённые выходы.
Это подсказка, не запрет на исследование и не требование выдумать стрелку;
неизвестные стыки фиксируются адресным пробелом. После трёх отклонённых вызовов
без нового результата агент получает конкретные ошибки и способ исправления,
даже если параметры ошибочных вызовов немного различаются.

## Проверка

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p "test_scenario_*.py"
.\.venv\Scripts\python.exe -B tests/run_tests.py
.\.venv\Scripts\python.exe -B scripts/demo_scenario_map.py
```

Демонстрация использует синтетический код трёх АС и заранее заданные ответы
модели; она проверяет сборку, а не качество LLM. Результат помечен «Учебный пример».
Семантическое качество нужно отдельно измерять на согласованной со специалистом
карте реального сценария: пропущенные шаги, ложные переходы, границы варианта.
Логирование бизнес-событий, рекомендации для дашбордов и чат в текущую версию
не входят.

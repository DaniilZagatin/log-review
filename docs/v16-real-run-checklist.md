# Проверка стабильности карты после исправлений

Этот пакет нужен для реальных запусков на ноутбуке с доступом к модели. Локальные тесты обвязки и синтетическое демо не доказывают полноту исследования исходников.

## Условия сравнения

1. Сделать 3–5 **новых исследований** в разных папках результата. Использовать одну сборку Белки, один набор исходников и один файл описания, без переформатирования между запусками.
2. Сохранить идентичность сборки, хеши описания и источников, конфигурацию модели, режим thinking, temperature, лимиты шагов/времени/токенов и параметры суммаризации. Сравнивать фактическую конфигурацию из audit/run.reproducibility, а не только имя модели в настройках.
3. Сохранить `scenario_map.json`, `scenario_map.html`, `map_hierarchy.json`, checkpoint и полный локальный audit каждого запуска. Секреты и `.env` не включать в пакет.
4. Продолжения через `--resume` учитывать отдельно от новых исследований. Группировку одной сохранённой карты также сравнивать отдельно: её разброс не является разбросом исследования.

## Смысловые контрольные случаи

Для каждого случая сверить точные прочитанные основания, найденные действия, привязку к карте и итоговые переходы. Названия и ID между прогонами могут различаться.

| Случай | Что должно сохраниться |
|---|---|
| Закрытие текущей задачи и создание ручной | Порядок `закрыть → создать`, если именно он указан в исследуемом исполнении. Дробление узла не переворачивает его. Отдельно проверить обычную и простую стратегии. |
| Пустой результат поиска | Обе альтернативы: стандартный платёж → отказ; другой предусмотренный кодом случай → ручная обработка. Условия входящих связей позволяют пустому результату достигнуть его обработчика. |
| Заполненность поля внутри ДРПА | Обе подтверждённые альтернативы остаются различимыми. Отсутствие значения не теряется внутри крупного узла. |
| Внешняя отправка, названная записью | Категория действия не скрывает подтверждённое внешнее обращение. Два разных обращения к одному адресату не исчезают при объединении или дроблении. |
| Резервный поиск, сравнение ФИО, устранение неоднозначности | Самостоятельные предметные действия сохраняют основания и отображение. Служебные преобразования без отдельного предметного результата не раздувают граф. |
| Обработчик исключения | Последовательность получения данных задачи, создания обращения и закрытия отражает прочитанное исполнение. Вызов до `try` не приписывается этому `catch` без основания. |
| Команда и фактический результат | Команда повторной обработки не объявляет кредит погашенным без доказательства результата. Общий технический финализатор сохраняет нейтральный исход, если обслуживает разные бизнес-ветки. |
| Уточнение первоначального вывода | Найденное ошибочно действие или отношение можно исправить с причиной и прочитанным основанием; нельзя молча потерять его при перепривязке узлов. |

Эти примеры относятся к исследованному П1679. Для другого проекта специалист задаёт аналогичные ожидания по его исходникам; специальные правила по именам этого проекта в агент не добавляются.

## Проверка завершения и восстановления

- На одну проблему допускаются **четыре адресные попытки исправления после исходного отказа**. Дубли диагностики одного ответа не расходуют несколько попыток.
- Посторонние изменения не обнуляют историю проблемы. При исчерпании попыток проблема остаётся адресной, независимые участки могут исследоваться, допустим честный `partial`.
- После изменения карты проверяется затронутый участок; агент не повторяет полный обзор из-за правки подписи.
- Отдельно проверить продолжение прерванного исследования и продолжение публикации после принятого `finish`. Во втором случае исследователь повторно не запускается.

## Проверка публикации

- `factual_summary` и основной текст `summary` соответствуют финальным узлам, связям, явным terminal IDs и заполненным `external_interactions`.
- Исходный текст `finish.summary` сохранён как `model_commentary` со статусом `model_commentary_not_verified`; в HTML он показан отдельно в сворачиваемом комментарии исследователя.
- Наличие цитат и отсутствие зарегистрированных пробелов не объявляются доказательством семантической полноты.
- Перестроение группировки не переписывает сохранённую подробную карту. Старые карты не получают новый профиль методологии автоматически.

## Таблица результатов

Для каждого запуска записать: статус и причину остановки; время; число запросов и отклонённых инструментов; число адресных исчерпаний; незавершённые обнаружения; результат каждого контрольного случая; число действий/связей; качество бизнес-операций.

Оценка улучшения — устойчивое сохранение подтверждённых действий, условий, порядка и исходов при приемлемых времени и числе исправлений. Число узлов, совпадение формулировок или одинаковая раскладка HTML сами по себе не являются критерием качества.

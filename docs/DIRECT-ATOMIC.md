# Прямые атомарные операции (режим `atomic`)

Реализация шагов D2–D4 [плана](../plans/direct-atomic-context.md). Это обычный режим `analyze` по исходникам. Прежний путь «грубая карта → scope → refine» остаётся и включается явно: `--map-mode coarse-refine`. В библиотеке значение по умолчанию `ReviewSettings.map_mode` по-прежнему `coarse_refine`. Синтетический demo идёт прежним путём с одним кодовым запросом и записанными ответами. Живое качество модели, полнота смысла и E2E этим срезом не проверены; независимая офлайн-приёмка Codex завершена; см. docs/RELEASE-R07.md.

## Поток

1. **Технический разбор, сводка и каталог** — без изменений. Запросы, checkpoints и `catalog_sha256` не зависят от режима карты.
2. **Индекс объявлений и единицы команд** — хост, без модели (`declaration_index.py`, модуль Codex):
   - разбирается исходный текст замороженного снимка (без import и исполнения);
   - якоря каталога внутри одного самого внутреннего объявления той же ревизии файла образуют одну проверенную единицу;
   - остальные якоря становятся отдельными tentative-единицами;
   - несовпадение ревизии отклоняется.
   Файлы: `declaration_index.json`, `command_units.json`; в bundle — `command_units` (идентичность и учёт).
   Языки и покрытие объявлений — см. раздел «Индекс объявлений Java и покрытие» ниже.

## Индекс объявлений Java и покрытие

Python разбирается через `ast`, вывод для Python не изменился.

**Как индексируется Java** (`java_declarations.py`, экстрактор `java_lexical/1`):

- Исходный текст снимка только лексически разбирается: ничего не компилируется, не импортируется и не исполняется.
- Комментарии, строки, символы и текстовые блоки маскируются.
- Скобки `(`, `[`, `{` должны быть сбалансированы.

**Что попадает в индекс:**

- классы, интерфейсы, перечисления, записи и типы аннотаций, включая вложенные;
- методы любой видимости и конструкторы, включая компактные конструкторы записей;
- блоки инициализации.

**Что хранится в каждой записи:**

- точные строки: от первой аннотации или модификатора до закрывающей скобки или `;`;
- SHA-256 фрагмента и родитель;
- видимость, модификаторы, имена аннотаций;
- `body` (`block` или `none`), число параметров и хеш типов параметров.

Перегрузки имеют разные ID, даже если стоят на одной строке. Текст, литералы и аргументы аннотаций не сохраняются.

**Чего не бывает объявлениями:**

- тела методов и инициализаторы полей: лямбды, вызовы и управляющие блоки;
- локальные и анонимные классы, тела констант перечислений.

Такие места остаются внутри своего члена. Их число записано в `folded_bodies`.

Вызовы Java не извлекаются (`calls: "not_extracted"`): связей по именам между Java-единицами нет.

**Статусы файла Java:**

| Статус | Когда | Объявления |
|---|---|---|
| `indexed` | всё распознано | все найденные |
| `partial` | есть нераспознанная конструкция | из распознанных сбалансированных областей |
| `parse_failed` | незакрытый комментарий или литерал, несбалансированная скобка, unicode-escape вне литерала, структурный или неверный unicode-escape где угодно | ни одного |

- При `partial` записываются диагностики: только код и строка, не больше 20, остальные посчитаны.
- При `parse_failed` записывается `error {type, line}` без текста.
- Якорь вне объявлений частичного файла становится tentative с причиной `parse_partial`.

**Unicode-escape (JLS 3.2/3.3).** Java переводит `\uXXXX` до распознавания комментариев и литералов, поэтому escape внутри комментария или строки может скрыть объявление. Индекс escape не переводит. Перед разбором каждый действующий escape проверяется: обратная косая черта после чётного числа обратных косых, одна или несколько `u`.

- Неверный escape делает файл `parse_failed` (`MalformedUnicodeEscape`): javac его тоже отвергает.
- Escape, который даёт перевод строки, `"`, `'`, `\`, `*` или `/`, делает файл `parse_failed` (`StructuralUnicodeEscape`).
- Любой другой escape внутри комментария или литерала границ не меняет, и файл индексируется. Вне литерала по-прежнему `UnicodeEscapeOutsideLiteral`.

Полной поддержки unicode-escape, как в компиляторе, нет. Политика записана в поле файла `unicode_escapes`.

Остальные языки остаются `unsupported_language`.

**Покрытие объявлений.** `declaration_index.declaration_coverage(catalog, index)` (`declaration-coverage/1`) — детерминированный перечень. Он перечисляет объявления, к которым не привязан ни один якорь кандидата или контекста, например:

- закрытый вспомогательный метод без находки;
- тип без единого якоря.

Также перечисляются файлы без полного перечня объявлений и число якорей в них. Полный перечень объявлений не означает полноты бизнес-кандидатов.

## Объявления без находок: работа хоста на атомарных страницах

В режиме `atomic` хост сохраняет `declaration_coverage.json` рядом с `command_units.json`. Документ содержит схему, снимок, хеши индекса, каталога и единиц и `coverage_sha256`. Технический разбор, его кэш и отпечатки при этом не меняются.

**Какие объявления становятся работой хоста.** Каждое вызываемое объявление с телом (функция, метод, конструктор, блок инициализации) в файле `indexed` или `partial`, к которому не привязан точно ни один якорь кандидата или контекста, становится ровно одной единицей хоста (`primary_units`):

- `origin: "declaration_inventory"`, `role: "declaration"`;
- ID `hdecl-…` из ID объявления, поэтому перегрузки и вложенные объявления раздельны;
- без кандидатов, находок и членов.

Точно представленное объявление второй единицы не получает. Пересечение без точной привязки (`overlap_only`) — не представление.

**Как единицы хоста проходят страницы:**

- В `atomic_map.unit_states` у них есть `origin` и `declaration_id`. В `atomic_map.candidates` их нет: кандидатов не выдумывается.
- Очередь: сначала кандидаты по находкам в прежнем порядке, затем единицы хоста в порядке индекса.
- Единица хоста, которую вызывает спланированная единица (только разрешённые уникальные вызовы того же файла, сейчас Python), попадает на страницу вызывающей как зависимость. Для Java связей по вызовам нет.
- Строка страницы: `origin`, `owner` (объемлющее объявление, только для навигации), `findings: []`, `declaration_supplied: "whole"`, `declaration_anchor` (начальные строки, `use: "structural_navigation_only"`), места логирования внутри объявления.
- Объявление выдаётся целиком. Если оно не помещается в границы запроса даже одно, оно откладывается с причиной, а не урезается.
- Сортировка (`triage`) не видит исходного кода, поэтому единицы хоста ей не передаются: они всегда идут на атомарную страницу.
- Решение принимает бизнес-модель по выданному коду: `realized`, `supporting`, `excluded`, `outside_process` или `unresolved`, с прежними правилами причин и вопросов. Исключений по имени или роли нет: очередь, слушатель и чтение не исключаются автоматически.
- Лимиты запросов, входа и ответа и одно исправление общие. Переполнение даёт `deferred` с причиной, ошибка — `request_failed`.
- Операция, реализованная единицей хоста, получает в `unit_evidence_ids` начальные строки её объявления, выданные на странице. Это структурный якорь для навигации, смыслом не проверен и эффекта не показывает. Эффекты держатся только на собственных `refs` модели, поэтому для длинного объявления эффект ниже якоря без `refs` не подтверждён.
- Строка о единицах хоста в `unknowns` считает раздельно:
  - найдено;
  - в отправленных модели запросах страниц (включая неудачные);
  - из сохранённых ответов;
  - решение получено;
  - отложено;
  - без решения из-за ошибки запроса.

  Найденное не выдаётся за отправленное. `process.md` экспорта показывает найденное и счётчики по состояниям.

**Открытая область.** `open_scope` перечисляет файлы исходного кода с неизвестным перечнем объявлений:

- язык без индекса объявлений;
- `partial` или `parse_failed` в любом языке с индексом, включая Python.

Каждый такой файл блокирующий: карта со статусом `partial` и причиной `declaration_inventory_unknown`, а не `complete`. Отказ парсера хоста (для Python — CPython хоста) показывает только, что хост не смог прочитать файл. О рантайме или диалекте анализируемой системы он ничего не говорит, поэтому перечень остаётся неизвестным. Ресурсы (SQL, XML, YAML, документация) объявлений не имеют и не перечисляются.

**Подсказки модели (validator /5; без изменений в /6).**

- Единица `declaration_inventory` решается по своему коду.
- Для каждого действия в `refs` цитируются точные выданные строки каждого отдельного эффекта. `declaration_anchor` — только навигация.
- Независимые запросы, поиски, изменения состояния и решения не склеиваются в общее «обработать», если код показывает их раздельно.
- Getter, преобразование или расчёт — не действие и не клик пользователя.
- Передача в очередь или другому компоненту может быть автоматическим действием процесса.

**Экспорт:**

- Пересчитывает `declaration_coverage` из сохранённых каталога и индекса и сверяет файл. Пересчитанная заново печать не помогает.
- Привязку `atomic_map.declaration_coverage` целиком выводит из проверенного документа: хеши, `primary_units` и `open_scope {files, blocking}`. Одинаковая ложная привязка в `bundle.json` и `atomic_map.json` отклоняется.
- Сверяет счётчики `summary.declaration_units*`.
- Сверяет состав журнала: кандидаты и единицы хоста.
- Запрещает `complete` при блокирующей открытой области.
- SHA-256 файла попадает в `source_run.files` пакета.
- Старые записи без привязки и без описания `declaration_completion` в настройках принимаются как раньше.

Перечень непроверенных объявлений не является оценкой смысловой полноты.

## Объявления только с контекстными якорями (validator /7)

Находка, не являющаяся сигналом действия (ошибка, идентификатор и т. п.), даёт якорь контекста. Это технический ярлык, а не решение. Раньше точно привязанный якорь контекста считался представлением объявления: тело такого метода не получало собственного решения, а на страницах появлялось только как общая строка контекста.

**Политика `context-callables/1`.** Свежий запуск записывает в `declaration_coverage.json` поле `policy` и список `context_units`. В него попадает каждая проверенная (`verified`) единица команд с ролью `context`, если её объявление — вызываемое с телом в файле `indexed` или `partial`. Порядок — порядок индекса.

- Единица остаётся той же: ID единицы команд (он же ID объявления `decl-…`), её находки и связи вызовов. Второй единицы `hdecl-…` не создаётся. `command_units.json` и каталог не меняются.
- Элемент `context_units` — только представление работы: ID, объявление, строки и `finding_ids` единицы. Кандидатов, членов и новых находок в нём нет.
- Типы, поля, абстрактные и прочие методы без тела, фрагменты `tentative` и файлы без полного перечня работы не дают. Объявление с якорем кандидата остаётся одной единицей кандидата. Вторая перегрузка без якоря остаётся единицей хоста со своим ID.

**На страницах:**

- В `atomic_map.unit_states` такая единица получает `origin: "context_anchor"`, `declaration_id` (равен ID единицы), `candidate_ids: []` и свои `finding_ids`. В `atomic_map.candidates` её нет.
- Очередь: сначала кандидаты в прежнем порядке, затем единицы хоста и контекста вместе в порядке индекса. Вызываемая из спланированной единицы (Python) ещё не решённая единица попадает на её страницу как зависимость. Решённая единица на следующих страницах — обычная строка `shared_context`: это контекст, а не второе решение.
- Строка страницы: `origin: "context_anchor"`, собственные находки, `declaration_supplied: "whole"`, места логирования внутри объявления (как у единиц хоста). Объявление выдаётся целиком даже длиннее `declaration_lines`; если оно не помещается в границы запроса и одно, оно откладывается (`unit_exceeds_request_budget`), а не урезается.
- Сортировка (`triage`) таких единиц не видит: решение по описанию находки не исключит тело.
- Решение — любое из пяти, по коду. Операция не навязывается: `supporting`, `excluded`, `outside_process` и `unresolved` операций не добавляют. Лимиты запросов, входа и ответа и одно исправление общие; переполнение — `deferred`, ошибка — `request_failed`, карта тогда `partial` или `failed`.
- Подсказка модели (одна новая строка `ATOMIC_SYSTEM`): единица `context_anchor` — вызываемое объявление, которое технический разбор отметил только как контекст; ярлык ничего не решает.
- Учёт отдельно от объявлений без находок: `summary.context_units` и `summary.context_units_by_state`; в `unknowns` своя строка «Объявления, которые технический разбор отметил только как контекст…» с теми же раздельными счётчиками (найдено, в попытках запросов, из сохранённых ответов, решено, отложено, без решения из-за ошибки). Строка и `summary.declaration_units` про объявления без находок их не считают. `process.md` экспорта показывает отдельную строку.

**Прежние записи и экспорт:**

- Документ без `policy` — прежний перечень (`direct-atomic-validator/5` и `/6`). `check_coverage` пересчитывает документ по той политике, которую он записал, поэтому старые `declaration_coverage.json` и записи проверяются по своим правилам и не перезаписываются. Неизвестная политика отклоняется.
- Привязка `atomic_map.declaration_coverage` свежего запуска дополнительно несёт `policy` и `context_units` и целиком выводится из пересчитанного документа. Описание `settings.declaration_completion.context_units` и привязка с `policy` бывают только вместе. Привязка без `policy` принимается только при валидаторе `/5` или `/6` и без единиц `context_anchor`, поэтому текущий запуск нельзя выдать за прежнюю политику, сменив только привязку, документ или описание.
- Экспорт сверяет каждую единицу `context_anchor` с `command_units.json` (ID, объявление, `finding_ids`), её отсутствие, переименование, чужие кандидаты или находки, а также счётчики `summary.context_units*`.
- Запись не подписана: полностью согласованную подделку всей записи под прежний валидатор (метка, журнал, запросы, сводка) экспорт сам по себе отличить от настоящего прежнего запуска не может.

Присутствие кода и точность цитат не доказывают смысл решения или исполнение кода.
3. **Сначала код (validator /9).** Каркаса этапов больше нет: запроса `TASK: map-skeleton` нет, и ответ прежнего каркаса никогда не переносится в новый поток. Стадия карты (`orientation_map`) — только хост, без вызова модели: она проверяет технические предпосылки и возвращает пустую рамку. Этапов, порядка этапов, фактов и операций до чтения кода не существует. Бизнес-текст — сгенерированный контекст: на страницах и в композиции он передаётся как `business_hypothesis` и никогда не создаёт действие, этап, переход или факт.
4. **Атомарные страницы** (`TASK: map-atomic`). Порядок работы (`work_order`): сначала единицы-входы (сигнал `entry_point` или нет вызывающих), за каждой — то, что она достигает через зависимости и разрешённые технические связи; затем весь остальной перечень. Достижимость только упорядочивает страницы и выбирает исходники; ребром она не становится. Каждая страница несёт:
   - первичные единицы и вызываемые ими кандидаты, общую таблицу контекста, точные места логирования;
   - технические связи вокруг единицы (`relations`, до 8 на единицу, остальные посчитаны; см. [TECHNICAL-RELATIONS.md](TECHNICAL-RELATIONS.md));
   - принятые операции прежних страниц (`known_operations`): последние 80 плюс до 80 принятых операций зависимостей, вызывающих и целей связей страницы; сколько не выдано и сколько из них релевантных — `context_omissions.known_operations` (`omitted`, `relevant_omitted`); строки контекста и единицы называют свои уже принятые операции номером (`accepted_operations`, `called_by_operations`);
   - предварительные рабочие группы (`working_groups`: номер, имя, короткий контракт) и бизнес-гипотезу.
   Модель возвращает действия с `group` (номер рабочей группы, номер новой группы из `new_groups` или `null`), `exit` (`terminal`, `continues`, `external_handoff`, `unknown`; последние два — с `exit_question`), учёт каждой выданной единицы, привязки мест логирования (без фактов) и переходы только с основанием в коде: `source_condition`, `source_call` или `source_handoff`. Переход всегда с цитатами; у `source_handoff` поле `contract` — буквальное имя очереди, темы, ключа реестра или callback, которое показывают минимум два разных процитированных диапазона. Действие может быть условием, ожиданием, повтором или результатом и не обязано иметь лог.
5. **Одна композиция** (`TASK: map-compose`, прежнее место композиции) после всех страниц: этапы из принятых действий (каждое действие ровно в одном этапе), факты на границах действий, статусы явно утверждённых обязательств, проверка гипотез бизнес-текста и — только при `--compose on` — сценарии. Порядок этапов модель не задаёт; см. «Этапы, факты и обязательства».
6. **Необязательная сортировка** (`TASK: map-triage`) — см. ниже.
7. **Сборка хостом**:
   - этапы, порядок этапов, факты, обязательства, граница карты и пробелы (`code_led`);
   - сверка привязок одного места вызова и residual; покрытие, доработки и метрики — прежние;
   - запись учёта — `atomic_map.json` (`atomic-map/2`, ключ `code_led` вместо `skeleton`) и `bundle.json → atomic_map`;
   - экспорт переносит её в `onboarding.json → atomic_accounting` и строго проверяет вложенный `code_led`. Записи `atomic-map/1` прежних запусков экспортируются по прежним правилам. Что проверяется:
     - точные ключи и типы каждой вложенной строки (рабочие группы, этапы, факты, пробелы, фрагменты, гипотезы, обязательства);
     - этапы: точное разбиение операций, рабочие группы — ровно по своим операциям, имена совпадают с картой;
     - граница карты (входы, конечные действия, связные фрагменты и их ID) и пробелы открытых выходов (ID, единицы, вопросы, уникальность) — пересчитываются из операций и переходов записи;
     - факты: этап, `mapping_indexes` (ровно привязки своих операций со своими ролями), ключи событий и требование — против `log_coverage`, а связи `fact_ids` в привязках — против фактов;
     - обязательства и их факты — против статусов композиции и настроек.

     Пробел `pending_local_work` проверяется только по форме и по тому, что его единицы действительно не решены: граф вызовов в запись не входит.

## Страницы и границы

| Граница | Значение по умолчанию | Где задаётся |
|---|---|---|
| Первичных единиц на странице | 10, максимум 128 | `--atomic-page-units`, `ReviewSettings.atomic_page_units` |
| Прямых зависимостей на первичную единицу | 8; остальные названы в `context_omitted` с адресом и `dependency_limit` | константа |
| Строк общей таблицы контекста | 40; превышение закрывает страницу раньше, контекст не выбрасывается | константа |
| Объявление выдаётся целиком | до 120 строк; иначе только диапазоны находок и мест логирования | константа |
| Вход страницы: цель / жёсткая граница | 40 000 / 80 000 | `ReviewSettings.atomic_input_tokens(_hard)`; потолок 1 000 000 |
| Планируемый ответ | 10 000 (оценка) | `ReviewSettings.atomic_answer_tokens` |
| Запросы бизнес-модели стадии карты | `--refine-max-requests` (16): атомарные страницы, triage и одна композиция; repair не считается | CLI |
| Известных операций на странице | последние 80 + до 80 релевантных; остаток посчитан в `context_omissions.known_operations` | константы `KNOWN_OPERATIONS`, `RELEVANT_OPERATIONS` |
| Технических связей на единицу | 8; остаток посчитан | константа `RELATIONS_PER_UNIT` |

- **Что считается.** Размер считается по полному запросу: system вместе с методикой и пользовательский JSON. К жёсткой границе добавляется резерв на единственный repair: доверенный текст repair и ограниченная обратная связь. Без локального токенизатора используется верхняя граница — байты UTF-8 (`token_estimate: utf8_bytes_upper_bound`). С `--business-tokenizer` используется локальный подсчёт (`tokenizer`). Показания сервера (usage) здесь не используются.
- **Байтовая граница строже.** Методика карты и промпт сами занимают порядка 30–40 тыс. байт. Поэтому без токенизатора страницы при цели 40 000 маленькие и их много. Значения не увеличиваются скрыто, бизнес-текст не сокращается. Размеры видны в `summary.input_tokens` (p50/p90/max).
- **Граница не вмещает даже пустую страницу.** Если system и обязательный контекст пустой страницы не помещаются в явную границу бизнес-запроса, ни один запрос не отправляется: все единицы получают `deferred` с `required_context_exceeds_request_budget`, причина записывается в `status_reasons`, а стадия карты в manifest становится `incomplete` с блокером «required business context exceeds its explicit budget». Последующие стадии не запускаются, запись `atomic_map.json` сохраняется (как прежняя проверка бюджета каркаса).
- **Одна первичная единица.** Страница с одной первичной единицей может использовать жёсткую границу. Если единица не помещается и одна, она получает собственную страницу только с диапазонами находок. Если не помещается и так — `deferred` с `unit_exceeds_request_budget` или `answer_exceeds_budget`. Текст никогда не обрезается.
- **Окно 1 млн.** Токенный бюджет из `--business-context-tokens` (вход + максимальный ответ профиля + оформление) — отдельная защитная проверка. Это не цель заполнения страницы.
- **Ответ.** Планируемый ответ = 300 + 450 на единицу + 150 на место логирования с ключом (R08: 450 вместо 300 — запас на необязательные сведения операций). Это только оценка для разбиения страниц: ограничение вывода и резервы профиля модели не меняются; граница 10 000 по умолчанию прежняя.
- **Отказы.** Каждый запрос получает не больше одного repair. После ошибки транспорта, настройки или бюджета остальные страницы не отправляются (`halted_after_<layer>_failure`). Отклонённая страница ничего не сохраняет в карту: её единицы получают `request_failed` с ID запроса.

## Состав страницы и учёт

- **Первичная единица** определяется по структуре: есть сигнал `entry_point` или нет вызывающих единиц-кандидатов. Имена и пути на это не влияют.
- **Вызываемые кандидаты** (ещё не учтённые) идут на страницу вызывающей единицы с ролью `supporting` и учитываются там. Уже учтённые и контекстные единицы показываются строкой общей таблицы: строка подаётся один раз, у неё есть `used_by`, выдаются только диапазоны находок.
- **Общий owner** (тот же класс) источники не добавляет.
- **Ровно одно решение.** Каждая выданная единица получает ровно одно решение:

  | Решение | Что указывается |
  |---|---|
  | `realized` | операции |
  | `supporting` | обслуживаемые единицы и причина |
  | `excluded` | код и причина |
  | `outside_process` | причина |
  | `unresolved` | вопрос |

- **Несколько операций одной единицы.** Одна единица может реализовать несколько операций, в том числе в разных рабочих группах. Повторное использование известной операции, общая операция или несколько операций требуют причины. Дубликатов выполнения не создаётся. Каждая новая операция должна быть реализована хотя бы одной выданной единицей (`operation_without_unit`).
- **Идентичность между страницами.** Известная операция выбирается только по номеру из `known_operations` текущей страницы; имена не сопоставляются нечётко, соединения не выдумываются. Переход к операции прежней страницы (`to_known`/`from_known`) допустим, только если она выдана на этой странице и переход процитирован; иначе `unknown_known_operation`.
- **Учёт кандидатов.** Каждый кандидат каталога ведёт к единице (`candidates → unit_id`). У каждой единицы-кандидата есть одно итоговое состояние: `accounted`, `triaged`, `deferred` с причиной или `request_failed`. Показ единицы в контексте не заменяет её учёт.
- **Ошибки ответа** получают единственный repair с точным полем:

  | Код | Когда |
  |---|---|
  | `unknown_unit`, `duplicate_unit`, `missing_units` | номер единицы неизвестен, повторён или пропущен |
  | `unknown_group`, `duplicate_group`, `unused_group` | номер группы неизвестен; новая группа повторяет имя; новая группа не использована |
  | `exit_without_question` | `external_handoff` или `unknown` без `exit_question` |
  | `operation_without_unit` | новую операцию не реализует ни одна выданная единица |
  | `disposition_fields` | поля не соответствуют решению |
  | `missing_reason` | нет обязательной причины |
  | `transition_basis` | переход без цитат |
  | `handoff_without_contract` | `source_handoff` без буквального контракта минимум в двух процитированных диапазонах |
  | `unknown_known_operation` | номер известной операции не выдан на этой странице |
  | `ref_outside_supplied` | цитата вне выданных строк; отсутствующие строки перечисляются |

  Остальные коды — прежние (`role_without_basis`, `operation_choice`, `self_transition` и др.). Ответ с прежними полями (`stage`, `facts` в привязке) отклоняется проверкой формы.

## События, факты и приоритеты

- **Привязка события** выбирает точное место логирования и операцию. Хост проверяет, что место вызова лежит внутри источников операции (`role_support`). К источникам относятся диапазоны её единиц, явные проверенные цитаты операции и `supporting`-единиц, явно обслуживающих их на той же странице. Сам показ постороннего helper в контексте не делает его источником результата операции.
- **Ключи фактов** берутся только из принятых привязок операций, на границе которых стоит факт, и только с ролями из его `lifecycle_roles` (`code_led.facts[*].mapping_indexes`). Покрытие засчитывает для факта только эти привязки и прежнюю сверку мест.
  - `duplicate`, `no_op`, `refusal` и `error` не подтверждают новый результат.
  - Запись о повторе подтверждает факт о повторе, если в его `lifecycle_roles` есть `duplicate`.
- **Прежние связи** (`--map-priors RUN_DIR`) — это event→operation из `process_map.json` раннего запуска. Каждая ищется по точному ключу среди статических мест: `single_site`, `multiple_sites` (все места сохраняются отдельно), `no_static_site` или `key_not_found`.
  - На странице такая связь показывается у места как `earlier_proposals`: метка, этап, роль, `evidence: "none"`, без номера известной операции.
  - В карту и покрытие она не попадает.
  - Расхождения роли или этапа с принятой привязкой записываются в `prior_diagnostics`.
  - Порядок страниц прежние связи сейчас не меняют.
- **Единицы без логов** остаются в очереди и в учёте (`summary.units_without_logs`).
- **Инициатор.** API-вызов не считается кликом: `user_interaction` только с цитатой обработчика взаимодействия.

## Сведения операции на той же странице (R08)

У каждой новой операции ответа страницы есть необязательный ключ `details` — его можно опустить или передать `null`. Отдельного запроса для повторной генерации операций нет: сведения приходят в том же небольшом атомарном ответе.

| Поле | Смысл |
|---|---|
| `input`, `expected_result` | Что код принимает и что он по реализации должен получить; не наблюдение |
| `precondition`, `completion_condition` | Проверка до эффекта; завершение процесса при названном результате |
| `effect_kind` | `decision` / `recommendation` / `command` (просит другую систему; исполнение у неё не показано) / `result` / `unknown` |
| `outcomes` | Различаемые кодом исходы: `success`, `refusal`, `failure`, `cancelled`, `deferred` |
| `continuation`, `join` | `choice`/`all` и `all`/`any` только при основании в коде; иначе `unknown`. Несколько переходов сами по себе ничего из этого не показывают |
| `external_interactions` | Явный вызов, сообщение или обратный вызов: `system`, `direction` (`request`/`send`/`receive`), `endpoint` или `contract`, необязательный `purpose`, `refs`. Исходящий запрос не показывает результат у получателя |
| `code_explanations` | `symbol`, пояснение на русском, `refs`; это интерпретация, не проверка |
| `questions` | Что код страницы решить не позволяет; значения не придумываются |
| `refs` | Строки, показывающие каждое заявленное текстовое поле, известный тип эффекта, исходы и режимы |

Проверки хоста (одна точная repair-обратная связь на запрос):

- `details_without_refs` — заявлено поле без `refs`.
- `ref_outside_supplied` — ссылка вне выданных строк, как и везде.
- `details_ref_outside_operation` — ссылка вне собственных источников действия: его `refs`, диапазоны реализующих его единиц и `supporting`-единиц, которые их обслуживают на этой странице. Код другого действия той же страницы и общий контекст сами по себе источником не являются.
- `external_without_refs`, `external_without_contract`.
- `explanation_without_refs`, `explanation_symbol_not_in_source` — имя (последний сегмент после `.`, `::`, `#`, без `()`) должно встречаться целым токеном в процитированном редактированном тексте. Это текстовая проверка, а не утверждение о привязке имени к объявлению (например, перегрузки Java).

Принятые сведения хранятся как `contracts.OperationDetails` в `ProcessOperation.details` и той же копией в `atomic_map.operations[*].details`; `refs` заменены идентификаторами реестра evidence. Вопросы попадают в `process_map.unknowns` строкой «Операция «…»: …». Проверенная цитата подтверждает только существование текста, не исполнение, доставку или результат у получателя.

Изменение формы, промпта и валидатора (`direct-atomic-validator/3`) меняет бизнес-идентичность и checkpoints атомарных страниц; технический разбор, его кэш и строгое синтетическое демо не меняются. В legacy-запросах пустое `details` не передаётся, байты прежних запросов сохраняются.

### Локальная перепроверка вспомогательных сведений после исправления

Ограниченный запасной путь только для атомарных страниц (`direct-atomic-validator/4`). Он включается, только если одновременно:

- первая попытка отклонена и получила обычную точную обратную связь;
- вторая (repair) попытка вернула корректный JSON;
- ответ не прошёл обычную строгую проверку с ошибкой `external_without_contract` ровно по пути `operations[i].details.external_interactions[j]` или `explanation_symbol_not_in_source` ровно по пути `operations[i].details.code_explanations[j].symbol`.

Как выполняется перепроверка:

- Хост убирает только этот элемент массива из **копии** ответа. Полученный ответ модели не меняется.
- В `details.questions` той же операции добавляется адресный вопрос хоста. Он попадает в `process_map.unknowns` как «Операция «…»: …», рядом появляется строка о локальной перепроверке страницы.
- Затем снова выполняется вся проверка формы и страницы: источники, доступность, учёт единиц, ID, этапы, факты, роли и переходы.
- Если следующая ошибка того же вида, убирается ещё один элемент, но не больше `MAX_AUXILIARY_OMISSIONS` (12) на страницу.
- Любая другая ошибка, лишняя квалифицирующая ошибка, ошибка транспорта, ресурса или HTTP, а также ответ без JSON оставляют страницу `rejected_after_repair`.

Чего перепроверка не делает:

- не вызывает модель ещё раз;
- не делает дополнительного repair;
- не меняет проверку источника, не принимает символ или контракт и не ищет нечёткие совпадения;
- не удаляет операцию, единицу, учёт, привязку, переход, обязательную ссылку или поле данных.

Происхождение записывается в запросе `atomic_map.requests[*]`:

- Обе попытки остаются `rejected` со своими хешами запроса и ответа.
- `outcome` = `accepted_after_local_revalidation`.
- `accepted` = `{attempt: 2, api_request_sha256 (repair-запрос), response_sha256 (производный ответ), derivation: "local_auxiliary_omission", raw_response_sha256 (полученный ответ)}`.
- `local_revalidation` (`atomic-local-revalidation/1`) хранит источник (`repair_response` или `checkpoint`), оба хеша и исключения: операция, поле, исходный индекс, код, исходный путь, SHA-256 элемента и вопрос. Там же лежат признак достижения предела, итог и последняя ошибка, если итог `rejected`.
- `atomic_map.summary.auxiliary_omissions` — число исключённых элементов в принятых производных ответах.
- При неудаче записываются `local_revalidation.outcome = "rejected"` и `accepted = null`.

Checkpoint производной страницы хранит:

- производный ответ;
- полученный repair-ответ;
- его хеш и хеш repair-запроса;
- исключения.

При `--resume-from` хеши сверяются, полученный ответ снова проверяется строго и производный ответ выводится заново. Исключения и хеш должны совпасть, иначе checkpoint не используется. Метка производного ответа без локальной записи тоже отклоняется. Если редактирование секретов изменило бы любой из ответов, checkpoint не сохраняется.

Экспорт проверяет:

- допустимые исходы;
- привязку хешей к второй попытке;
- соответствие кода, поля и пути;
- уникальность и предел исключений;
- счётчик.

Частичная карта остаётся частичной.

#### Место логирования без операции (validator /6)

Тот же путь после второй (repair) попытки может исключить ещё один вид пункта. Это ошибка `operation_choice` ровно по пути `event_mappings[i].new_operation`, и пункт должен быть безопасен. Безопасным он считается, только если одновременно:

- `new_operation` и `known_operation` оба `null`;
- `facts` — пустой список: заявленный факт относится к ядру, и такой пункт никогда не исключается;
- `site` — выданное на странице место с ключом события;
- роль, отличная от `unknown`, имеет `role_basis` и `refs`;
- каждая ссылка `refs` лежит в выданных строках (проверка на отдельном черновом реестре).

Как выполняется исключение:

- Хост убирает из **копии** ответа только этот пункт `event_mappings`. Цель и роль он не придумывает, по имени ничего не выводит, факт не закрывает, перечень мест логирования не меняет.
- В `unknowns` ответа добавляется адресный вопрос с ключом, `путь:строка` и ID места. Он попадает в `process_map.unknowns` и в отчёт.
- Если у того же места есть другая привязка с операцией, вопрос говорит, что исключён лишний пункт и другие привязки сохранены. Иначе — что запись осталась без привязки к операции.
- После каждого исключения выполняется полная проверка.
- Общий предел — `MAX_AUXILIARY_OMISSIONS` (12) вместе с деталями. При смешанном ответе исключения идут в порядке проверки: сначала детали операций, потом места.
- Исключение записывается в `local_revalidation.omissions` как `{field: "event_mappings", original_index, code: "operation_choice", path, item_sha256, site_id, question}`.
- В `settings.auxiliary_recovery.unassigned_sites` описано правило. Список `codes` прежний.

Строго отклоняются, как раньше:

- непустой `facts`, даже с существующим номером факта;
- невыданное место или место без ключа;
- обе цели заданы;
- роль без основания;
- ссылка вне выданных строк;
- переход без источника;
- ошибки единиц, учёта, этапов, номеров действий;
- любая другая ошибка.

Ошибка ядра, найденная только при повторной проверке после исключения, оставляет страницу `rejected_after_repair`, а запись `local_revalidation` получает итог `rejected` и последнюю ошибку.

Экспорт принимает такое исключение, только если в настройках записи есть `unassigned_sites`, `site_id` входит в `site_ids` того же запроса, путь соответствует исходному индексу, а вопрос не пуст. Старые записи только с исключениями деталей экспортируются как раньше. Replay checkpoint выводит исключение заново: подмена исключения, ID места, производного ответа или исходного ответа отключает checkpoint.

### Неприменимые nullable-поля учёта (validator /8)

В пункте `unit_accounting` с известным `disposition` и номером выданной единицы поле, которое при этом решении может быть только `null`, иногда пропущено: `exclusion` при решении не `excluded`, `question` при решении не `unresolved`. Это отсутствие представления, а не отсутствие решения, источника или идентичности.

- Политика `atomic-nullable-accounting/1` (`settings.wire_decoding`): хост подставляет `null` только в КОПИЮ ответа, затем выполняет полную проверку формы и страницы. Ответ как получен, его хеш, трасса и checkpoint не меняются; в checkpoint хранится исходный ответ, и повторное чтение применяет то же декодирование.
- Применяется только к пунктам с номером выданной единицы и только пока пунктов не больше, чем выданных единиц. Точные пути записываются в `requests[*].wire_decoding` (`policy`, `attempt`, `defaults`, `model_calls: 0`) и в событие трассы `direct_atomic.wire_defaults`; у отклонённой попытки — `wire_defaults`.
- Не подставляется ничего другого: пропущенные `unit`, `disposition`, `new_operations`, `known_operations`, `serves`, `reason`, `exclusion` у `excluded`, `question` у `unresolved` и любые ссылки, операции, факты и источники остаются ошибкой; присутствующие неверные значения, типы и противоречия тоже. Каждая выданная единица по-прежнему учитывается ровно один раз.
- Это не локальное исключение: бюджет из 12 исключений и единственное исправление не расходуются. Промпты и формы ответа не менялись, поэтому прежние точные запросы остаются сравнимыми.

### Повторное использование уже полученных ответов (`--resume-from`)

После nullable-wire исправления отдельно уточнены смысловые инструкции каркаса (в /9 эти правила фактов перенесены в композицию, `_FACT_RULES`) и доработок: назначение, человеческое начало и начало робота различаются; внешние объекты и внутренняя очередь не отождествляются; связь двух идентификаторов может быть самостоятельным требованием. Неподтверждённая связь не удаляет корректную ссылку на существующий emit. Эти изменения намеренно меняют хеши бизнес-запросов: более ранние ответы на другой промпт не переиспользуются; технический кэш от этого не меняется. Проверка формата и цитат не доказывает бизнес-смысл — нужна отдельная приёмка результата.

`business_replay.py` без вызова модели и сети ищет в каталоге прежнего запуска (`atomic_map.json`, `trace.jsonl`) ответ на ТОЧНО тот же запрос:

- **Каркаса нет (validator /9).** Код-ведомая карта не отправляет `map-skeleton`; читателя прежнего каркаса больше нет, и ответ каркаса никогда не переносится в новый поток. Промпт и состав атомарной страницы изменились, поэтому страница, записанная прежним запуском, имеет другие байты запроса и всегда даёт промах; попасть может только точно равный запрос.
- **Атомарная страница.** Если checkpoint текущей идентичности не найден, ищется ровно один запрос прежней записи `direct-atomic-validator/7` с тем же начальным SHA-256 запроса и равными полями `task`, `mode`, `shape_sha256`, `business_model_sha256`, `snapshot_id`, `catalog_sha256`, `units_sha256`, `coverage_sha256`. Берётся его итоговый принятый ответ либо итоговый ответ исправления запроса, отклонённого только из-за `missing_keys` по `exclusion`/`question` одного пункта `unit_accounting`. Ответ берётся из трассы: пара `model.request` → `model.response` с тем же этапом, задачей, ролью и попыткой, хеш запроса и хеш ответа равны записанным.
- Ответ проходит полную текущую проверку на ТЕКУЩЕЙ странице. Для настоящего прежнего исправляющего ответа (попытка 2) допускается та же ограниченная локальная обработка вспомогательных ошибок, что после живого исправления: не более12исключений и полная повторная проверка после каждого. Ошибка основного содержания, источников или превышение лимита — промах до настоящих попыток (`direct_atomic.checkpoint_rejected`, `recovered: true`): обе попытки остаются. Когда меняется точный запрос (например, после восстановления первой страницы у следующей появились известные операции), прежний ответ не подходит, и следует настоящий вызов.
- Запрос получает `outcome: accepted_from_checkpoint`; `accepted` указывает исходную попытку и её хеши (отклонённая попытка не выдаётся за прежний успех), `recovered` — источник: прежний запрос, его исход и итоговую ошибку, исходные хеши, SHA-256 трассы и номера событий, `revalidated_under`. Обычно checkpoint сохраняет исходный ответ. При локальном исключении вспомогательных элементов он сохраняет производный ответ, исходный ответ отдельно в `local_revalidation.raw_response`, оба хеша и точный список исключений. Следующее возобновление должно воспроизвести тот же результат. Файлы прежнего запуска не меняются.
- Неоднозначные (два совпадения), непарные, повреждённые, переупорядоченные, слишком большие (`MAX_TRACE_BYTES`, `MAX_EVENT_BYTES`) или символьные ссылки — промах. Ответы других этапов и ответы с ошибками JSON, `null`, длины или транспорта не используются.
- Локальные файлы не подписаны: попадание показывает только, что те же байты были записаны локально, а не подлинность ответа провайдера или смысл.

## Этапы, факты и обязательства (code-led)

- **Этапы** выводятся только из принятых действий. Одна композиция кладёт каждое принятое действие ровно в один этап (`empty_stage`, `operation_in_two_stages`, `missing_operations`); рабочие группы для неё лишь подсказка. ID этапа — `ast-…` хоста. Перегруппировка не меняет ID операций, их доказательства и привязки логов: меняется только `stage_id`.
- **Порядок этапов** задаёт только хост: переход этапов есть, только если принятый переход операций пересекает два этапа (`code_led.stages.stage_transitions` с ID переходов операций). Ответ модели порядок этапов не задаёт; неупорядоченная карта остаётся неупорядоченной.
- **Ссылки фактов на методику после исправления.** Если исправленный ответ композиции отклонён только из-за `facts[i].guidance_ids` (`unknown_guidance_id`, `missing_guidance_ids`, `wrong_type`, `null_not_allowed`), хост убирает недопустимые значения из КОПИИ ответа и снова выполняет полную проверку формы и композиции. Третьего вызова нет. Факт без оставшихся ссылок получает неустановленную атрибуцию, правило не придумывается. Оба отклонённых ответа остаются как получены. Запрос получает `accepted_after_local_revalidation`; `guidance_revalidation` (`compose-guidance-omission/1`) хранит хеши исходного и производного ответа, точные предупреждения и итог. Любая другая ошибка (этап, операции, обязательства) оставляет композицию отклонённой, и этапы остаются предварительными. Экспорт сверяет эту запись с попытками. Навигационные группы такой композиции отчёт (`operation_hierarchy`, вне области изменений) пока считает непривязанными.
- **Факты** композиции стоят на границах принятых действий своего этапа (`fact_stage_mismatch`, `fact_without_operations`); требование такого факта — `proposed`, а не утверждённое бизнес-требование. Роль `unknown` не может быть ролью факта (`FACT_ROLES`): запись неизвестной роли никогда не подтверждает факт. Экспорт отклоняет такую сохранённую строку. Если композиция не выполнена (лимит, отказ, бюджет), хост сохраняет рабочие группы как предварительные этапы (действия без группы — один этап `Действия без группы`, это не бизнес-этап), ставит по одному граничному факту на действие (`origin: host_boundary`) и помечает карту `partial` с `final_grouping_incomplete`. Каркас при этом не восстанавливается.
- **Утверждённые обязательства** (`--approved-obligations FILE`, `approved-obligations/1`): по одной непустой строке без `#` на обязательство, до 200 строк по 1000 символов; ID `obl-001…`, SHA-256 источника и списка. Они отделены от сгенерированного текста и входят в бизнес-идентичность. Композиция даёт каждому ровно один статус: `matched`, `partial` (с вопросом) или `not_found` (с вопросом); без композиции — `not_checked`. Обязательство без полного совпадения получает собственный факт (`origin: obligation`, требование `accepted` с `decision_id` = ID обязательства, без операций и ключей событий): оно остаётся требуемым, но не реализованным. Это сохраняется и тогда, когда результат страниц не применён к карте (`merge_rejected`). Принятые требования применимой или неизвестной области остаются в знаменателе сводки покрытия (`LogCoverage`); числитель 0, потому что наблюдений нет; неизвестные измерения видны в `unknown`. Новые обязательства из бизнес-текста не выводятся.
- **Гипотезы бизнес-текста** записываются в `code_led.hypotheses` со статусом `supported`, `contradicted`, `not_found` или `unclear` и номерами действий. Гипотеза не создаёт действие, этап, факт или порядок.
- **Граница карты** (`code_led.frontier`) считается хостом только из принятых действий и переходов: все входы (их может быть несколько), действия с `exit: terminal`, несвязанные фрагменты (`afr-…`). **Пробелы** (`code_led.gaps`, ID `agp-…`, с ID операций и единиц и вопросом): `open_continuation` (действие продолжается, а следующий шаг не принят), `unresolved_handoff` (неизвестный получатель), `unknown_continuation`, `pending_local_work` (вызываемый локальный код ещё не решён — это незавершённая работа, а не отсутствующий внешний источник). Хост не добавляет переходы ради связности. Пробелы делают карту `partial` (`open_gaps`) и попадают в `process_map.unknowns`.

## Сортировка, композиция и сценарии

При повторном использовании `known_operations` совпадение глагола или этапа не устанавливает идентичность действия. Модель должна проверить объект, исходную/целевую систему и границу эффекта, объяснив связь по выданному коду. Чтение внешнего входящего задания и чтение внутренней очереди, как и их отложение, не склеиваются автоматически. Wrapper может относиться к тому же действию при показанном вызове того же эффекта; неизвестная эквивалентность остаётся вопросом. Это смысловое требование, а не детерминированное доказательство хоста: отдельная приёмка результата обязательна.

- **`--triage auto|off|on`** (по умолчанию `auto`). `auto` запускает сортировку только тогда, когда офлайн-план страниц превышает остаток лимита запросов. Сортировка получает описания находок без исходного текста.
  - `outside_process`, `supporting` и `unresolved` окончательны (`triaged` с причиной или вопросом).
  - `atomic_review` переходит на атомарные страницы.
  - Операций и этапов сортировка не создаёт. Неудачная страница сортировки возвращает единицы в очередь.
- **Композиция** выполняется всегда, когда есть принятые действия и остался лимит: один запрос получает принятые действия (номер, имя, рабочая группа, инициатор, выход, единицы, принятые пары ключ события/роль), принятые переходы, утверждённые обязательства и гипотезу. Новых операций, кода и ссылок она не создаёт.
- **`--compose on|off`** (по умолчанию `off`) теперь управляет только сценариями (`scenarios_requested`): при `off` сценарии должны быть пустыми (`scenarios_not_requested`). Сценарий проходит по принятым действиям; его переходы — принятые переходы между ними. Обязательных сценариев из бизнес-текста больше нет (`atomic_map.required_scenarios` не пишется).

## Статусы и идентичность

- **Статусы `atomic_map.status`:**

  | Статус | Значение |
  |---|---|
  | `complete` | у всех единиц есть решение, ни один атомарный запрос не отклонён (`accepted_after_local_revalidation` считается принятым, исключения видны в unknowns), композиция принята и пробелов нет |
  | `partial` | есть принятые страницы и есть отложенные или неудачные (включая единицы хоста), блокирующая открытая область `declaration_inventory_unknown`, незавершённая группировка (`final_grouping_incomplete`) или пробелы (`open_gaps`) |
  | `failed` | ни одной принятой страницы |
  | `not_run` | технические предпосылки не выполнены |
  | `skipped_no_candidates` | кандидатов нет |

- **CLI.** `partial`, `failed` и `not_run` дают код выхода 1, даже если черновики последующих стадий готовы. Статусы сортировки и композиции записаны отдельно.
- **Идентичность бизнес-конфигурации** (`config_sha256`) включает режим, хеши трёх промптов (страница, сортировка, композиция) и форм ответа, версию валидатора (сейчас `direct-atomic-validator/9`), SHA-256 утверждённых обязательств, описание декодирования ответа (`wire_decoding`), описание локальной перепроверки (`auxiliary_recovery`, включая `unassigned_sites`) и учёта объявлений (`declaration_completion`, включая `context_units`), все границы, triage/compose и хеш прежних связей. У запуска coarse-refine хеш прежний. Технический `run_context` не меняется.
- **Checkpoints атомарных страниц.**
  - Принятый ответ сохраняется в `business_checkpoints/map-atomic/<identity>.json`. Идентичность складывается из задачи, SHA-256 полного первого запроса, хеша формы, версии валидатора, режима и настроек, а при наличии `declaration_coverage.json` — и его `coverage_sha256`.
  - При `--resume-from` ответ используется только при точном совпадении идентичности и после полной повторной проверки на той же странице (`accepted_from_checkpoint`, без вызова модели).
  - Композиция не сохраняется в checkpoint и при возобновлении запрашивается заново. Ответ грубой карты или прежнего каркаса не может стать ответом страницы или композиции.

## Ограничения

- Корректная форма страницы и полный учёт не доказывают смысловую верность решений. Ограничения технического разбора сохраняются.
- Числа границ — начальные гипотезы. Реальное число страниц и их размер на настоящем каталоге ещё измеряет Codex.
- Порядок страниц — от входов по зависимостям и разрешённым связям, затем остальной перечень по пути и строке. Прежние связи его не меняют. Достижимость — статическая навигация, не исполнение.
- Рабочие группы и этапы — предложения модели; композиция проверяет полноту и номера, но не смысл границ. Порядок этапов есть только там, где принятые переходы его показывают.
- Окно известных операций ограничено (80 + 80): операция, не попавшая в окно страницы, на ней не может быть целью перехода; это видно в `context_omissions.known_operations`, но не исправляется автоматически.
- В CLI нет флагов для 8/40/120/80 и коэффициентов оценки ответа: это константы `direct_atomic.py`.
- Сортировка не проверяется отдельно на большом пуле. Отчёт (Codex) пока не показывает `code_led` (пробелы, фрагменты, обязательства) отдельным видом: они видны через `process_map.unknowns`, `atomic_map.json` и экспорт.


## Независимые проверки R07

Кэш атомарных страниц связывает бизнес-профиль модели, снимок, каталог, единицы, точный запрос, настройки, DTO и SHA-256 валидатора. При неизвестной идентичности бизнес-модели повторное использование отключено. Загрузка кэша и priors не следует через символические ссылки. Экспорт сверяет вложенные операции/роли/попытки/счётчики, копии atomic_map, полный каталог, индекс и весь раздел кандидатов на единицы; подмена одной только формы ID недостаточна.

Офлайн-упаковка реального каталога Saleor:2767кандидатов →2579единиц-кандидатов. При официальном локальном tokenizer и исторических названиях этапов как fixture —226страниц без triage, вход p50 19809/p90 30062/max39143 текстовых токенов, ожидаемый ответ max6900. Это тест упаковки, не смысловой разбор и не серверный usage. Лимит16 не покроет весь этот каталог. Auto-triage может сократить очередь; непереданное остаётся deferred. Без tokenizer консервативный UTF-8 бюджет даёт1624страницы, поэтому для большого анализа полезен совместимый локальный счётчик.

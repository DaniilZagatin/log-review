# Атомарные действия: каталог, адресная выдача источников и учёт кандидатов

Реализация шагов A1–A3 [плана](../plans/atomic-operations.md). Срез работает в `analyze` (режим полного разбора репозитория) при явном `--map-mode coarse-refine`. Обычный режим CLI теперь — прямые атомарные операции без грубой карты: см. [DIRECT-ATOMIC.md](DIRECT-ATOMIC.md). Каталог ниже общий для обоих режимов. Флаги `--action-refinement` и `--refine-stage` относятся только к coarse-refine; с `--map-mode atomic` они отклоняются явно. Синтетический demo и прежний путь с одним кодовым запросом не меняются. Живое качество модели этим срезом не проверено.

## Поток данных

1. **Технический разбор** (GLM) — без изменений. Его checkpoints теперь привязаны только к тому тексту методики, который реально уходит в технический запрос (см. «Идентичность кеша»).
2. **Каталог кандидатов** `action_catalog.json` (`action-catalog/1`) строится хостом из полного списка проверенных находок и вопросов **до** сокращения, по замороженному снимку, графу кода и инвентарю логирования. Модель не вызывается.
3. **Сводка и грубая карта** — как раньше. В review-режиме привязка события может указать точный `operation_id` операции той же стадии; текстовая метка `operation` сохраняется. Роли расширены: `refusal`, `retry`, `duplicate`, `no_op`.
4. **Уточнение внутри стадии карты** (`--action-refinement on`, по умолчанию в CLI):
   - `TASK: map-scope` — модель относит пронумерованные хостом области кода (каталоги кандидатов, при переполнении — отдельные файлы) к стадиям грубой карты, исключает с причиной или оставляет нерешёнными с вопросом;
   - `TASK: map-refine` — для каждой выбранной стадии страницы кандидатов: полные описания находок, выбранные навигацией вспомогательные функции, пронумерованные места логирования и пронумерованные замороженные фрагменты. Модель возвращает атомарные операции, учёт каждого кандидата, роли событий и только обоснованные переходы.
5. Хост проверяет идентичность и полноту учёта, добавляет операции в карту (грубые операции не удаляются), затем считает residual, покрытие и последующие стадии. Итог учёта — `action_refinement.json` (`action-refinement/1`) и `bundle.json → action_refinement`; `export-onboarding` переносит его в `onboarding.json → action_accounting`.

## Каталог

- **Якорь** — самое внутреннее объявление графа, содержащее диапазон находки; если объявления нет — сам диапазон. Идентификатор `act-…` = путь, символ, диапазон и SHA-256 исходных строк. Изменение строк действия меняет его идентичность; порядок файлов и находок — нет.
- Находки группируются только при совпадении якоря. Добавить/изменить/удалить строку корзины и два адреса остаются разными кандидатами; несколько находок одного объявления сохраняются отдельно — модель может выделить разные эффекты одной команды.
- **Кандидат** — якорь хотя бы с одной находкой `entry_point`, `state_change`, `transaction_boundary`, `outcome` или `integration`. Вид находки — предложение кодовой модели, поэтому кандидат — сигнал навигации, а не установленное бизнес-действие. Подтверждение и отмена заказа без `entry_point` тоже становятся кандидатами.
- **Контекстные якоря** — проверки/ветви/логирование без сигнала. Они связываются с кандидатом через разрешённый статический вызов или общий класс и выдаются вместе с ним как «related».
- Навигация: число статических вызывающих мест и их символы. Вызываемый из другого кода helper остаётся кандидатом, но не объявляется внешней командой или кликом: инициатора каталог не определяет.
- Места логирования внутри диапазона якоря — возможные события, не доставленные записи.
- Явно сохраняются: отклонённые ссылки (вне снимка, вне файла, неверная форма), находки без допустимой ссылки, вопросы без диапазона, частично рассмотренные интервалы (`review_gaps`), неполнота технического разбора и число неуспешных заданий.
- Полные описания хранятся без обрезки. Файл маскируется до вычисления `catalog_sha256`; изменённый, чужой или старый по форме каталог отклоняется.

## Адресная выдача и бюджет

- Для кандидата выдаётся объявление целиком, если в нём не больше 200 строк; иначе — диапазоны его находок и места логирования. Добавляются диапазоны связанных проверок/вспомогательных функций. Текст — замаскированные строки замороженного снимка с номерами.
- Каждый запрос собирается целиком и измеряется точно: system с методикой + JSON + резерв на единственный repair не превышают `--business-request-chars`. Ничего не обрезается.
- Если кандидат не помещается даже один, сначала снимается его related-контекст (это отмечается), затем кандидат откладывается: `candidate_exceeds_request_budget`.
- Число запросов уточнения (scope + страницы; repair не считается) ограничено `--refine-max-requests` (по умолчанию 16). Остаток откладывается с `request_limit_reached` и списком ID. `--refine-stage` ограничивает уточнение стадиями по точному ID или фрагменту названия; остальные кандидаты получают `stage_not_selected`.
- После ошибки транспорта, конфигурации или бюджета (например, HTTP 429) новые страницы не отправляются: остаток — `halted_after_<layer>_failure`. Повтора и ожидания нет.
- Бизнес-текст передаётся в уточнение только целиком и только если помещается вместе с кандидатами; иначе он отмечен в `context_omissions`, а переход с основанием `business_text` в таком запросе отклоняется.
- Цитировать можно только фрагменты этого запроса (смежные можно соединять, промежуток с кодом — нет). Список всех ссылок каталога для цитирования не открывается.

## Учёт кандидатов

- Модель выбирает только выданные номера: кандидатов, областей, стадий, мест логирования, известных операций; новые операции адресуются позицией в ответе. ID создаёт хост.
- Каждый выданный кандидат ровно один раз: `realized` (одна или несколько операций), `excluded` (код + причина) или `unresolved` (вопрос). Объединение с другим кандидатом, разделение на несколько операций или присоединение к известной операции требуют причины. Квоты числа операций нет.
- Ошибки получают единственный repair с точным полем: `missing_candidates`/`missing_areas` с номерами, `duplicate_candidate`, `unknown_candidate` с допустимыми номерами, `ref_outside_supplied` с выданными и отсутствующими строками, `role_without_basis`, `interaction_without_source`, `transition_basis`, `basis_not_supplied` и др.
- Не выданные кандидаты получают состояние хоста (`deferred` с причиной), отказавшие запросы — `request_failed` с ID запроса. Грубая карта при этом остаётся, стадия карты завершена; статус уточнения `partial`/`failed` даёт код выхода 1 и частичный пакет экспорта.
- `complete` означает только, что каждый выданный кандидат получил явное решение. Смысл решения не проверяется; ограничения технического разбора сохраняются отдельно.

## Операции, переходы и сценарии

- Атомарные операции добавляются в стадию как обычные `ProcessOperation`; при `parent_operation` хост добавляет их в сценарии родительской грубой операции. Грубые операции и их связи не удаляются.
- Свидетельства операции: собственные ссылки модели и диапазоны находок учтённых кандидатов (взяты хостом только из выданных фрагментов, записаны раздельно).
- Переход между атомарными действиями допускается только с основанием: условие в выданном коде (с ссылкой) или выданный бизнес-текст. Независимые команды остаются без стрелок.
- Ожидаемое по бизнес-описанию действие без кода может остаться операцией без ссылок.
- `user_interaction` требует цитаты обработчика взаимодействия и объяснения. Расширение файла роли не задаёт ни в одну сторону.

## События и жизненный цикл

- Привязка события выбирает место логирования с литеральным ключом и точную операцию. Несколько записей одной команды — роли одной операции, не новые операции.
- Роли `request`, `start`, `result`, `refusal`, `error`, `retry`, `duplicate`, `no_op`, `ui`, `unknown`; любая роль, кроме `unknown`, требует `role_basis` и ссылки на различающее условие. Сомнение записывается в `ambiguity`.
- Хост добавляет `role_support`: место вызова внутри источников операции, вне их или не статический вызов. Это структурная проверка, а не подтверждение смысла роли.
- В запросе уточнения у каждого места логирования есть `earlier_mappings` — привязки грубой карты к этому месту. Модель может согласиться или явно разойтись с ними.

### Сверка привязок одного места вызова (исправление после проверки Codex)

Первая версия добавляла уточнённые привязки рядом с ранними, и ранняя привязка `result` с настоящей ссылкой оставалась чистой альтернативой: факт «новый возврат» закрывался, хотя уточнение того же места видело повтор (`duplicate`) или вызов вне операции. Одновременно `duplicate`/`no_op` исключались для любых фактов, и факт «получено повторное уведомление» не мог закрыться своей же записью.

- **Место вызова** — статический вызов с литеральным ключом: путь, строки, ключ. Две строки с одним ключом — разные места.
- Привязки к месту: ранняя (`role_support: not_assessed`) — все литеральные вызовы ключа, пересекающие её цитату (прежнее правило покрытия); уточнённая — только точный диапазон места, выданный хостом.
- Хост сверяет все привязки места (`reconcile_bindings`): разные роли, кроме `unknown`, или разные операции (атомарное действие равно своему `parent_operation`) — `contradicted`; если уточнённые привязки есть, но ни одна не внутри источников своей операции — `unsupported`. Каждая привязка получает `EventMapping.reconciliation` по худшему из своих мест. Ничего не удаляется и не переписывается; расхождение называется в unknowns карты.
- **Требование факта**: `RequiredFact.lifecycle_roles` — роли записей, которые прямо наблюдают этот факт (`result` для нового завершённого исхода, `duplicate` для повторного уведомления, `refusal`, `no_op` и т. д.). Предлагает модель грубой карты в review-режиме; ключ необязателен, недопустимое значение даёт единственный repair с точным путём.
- Покрытие: факт с ролями засчитывает только чистые места (`consistent` или `not_assessed`) с одной из своих ролей; каждый ключ факта нужен отдельно. Факт без ролей сохраняет прежнее статическое правило, если ни одно его место не уточнялось; если уточнялось — `unknown` с `requirement_undeclared`. Итог хоста — `RequiredFact.lifecycle_check` (`not_assessed`, `compatible`, `no_compatible_site`, `ambiguous`, `requirement_undeclared`); `found` возможен только при `not_assessed`/`compatible`.
- Подробности по местам и фактам — `bundle.json → coverage_lifecycle` (`coverage-lifecycle/1`), переносятся в `onboarding.json`; несогласованная запись отклоняется экспортом, отсутствие у старых запусков даёт null.
- Прежний путь (demo, один кодовый запрос) не размечает привязки: `reconciliation` остаётся `not_assessed`, а запросы доработок и метрик не содержат новых полей, пока у них значения по умолчанию. Поэтому байты этих запросов и replay demo не меняются; в сохранённых артефактах поля есть.
- Ограничения: уточнённая метка не считается истинной автоматически — при расхождении с ранней место не подтверждает ни новый результат, ни повтор, пока решение не уточнено. Отдельно стоящая ранняя привязка без уточнения остаётся доказательством прежнего уровня (текст вызова в цитате). Смысл роли и требования факта по-прежнему предлагает модель.

## Идентичность технического кеша

- Раньше в `run_context` технического обзора входил хеш всего пакета методики: правка только `map.md` отклоняла все технические checkpoints.
- Теперь контекст `stage-dependencies/1`: SHA-256 и ID технических разделов, реально встроенных в system исполнителя, протокол workflow и SHA-256 system редуктора. Исходники, граф, весь system исполнителя, модель, опции и версия инструмента сверяются как раньше.
- Старые прогоны с хешем всего пакета используются только при доказательстве `legacy-whole-guidance-pack/1`: все прочие поля binding равны, включая хеш полного system исполнителя со встроенным техническим текстом; хеш технического текста совпадает с переданным текстом; сохранённый `run_fingerprint` равен хешу собственного binding. Доказательство записывается в новый `review/run.json`, старые файлы не меняются, каждый ответ повторно проверяется на снимке. Failed-задания остаются failed.

## Что не сделано

- `map.md` не менялся: legacy demo воспроизводит ответы по точному хешу map-запроса, а `examples/synthetic/model-responses.json` вне этого среза. Правила атомарности находятся в промптах `MAP_REVIEW_SYSTEM`/`map-scope`/`map-refine`, их хеши входят в конфигурацию запуска.
- Иерархия «шаг → детали» и отдельная детализация стадии на графе (A4) не реализованы; атомарные операции пока показываются рядом с грубыми внутри областей стадий. Русские подписи новых ролей добавлены в отчёт.
- Ответы уточнения coarse-refine не кешируются: при `--resume-from` бизнес-стадии, включая уточнение, выполняются заново. В режиме atomic принятые атомарные страницы переиспользуются только по точной идентичности запроса ([DIRECT-ATOMIC.md](DIRECT-ATOMIC.md)).
- Живая оценка checkout (A5) не выполнялась.

## Перенос R06 и частичные результаты

Успешный scope с отложенными по лимиту страницами даёт partial и сохраняет каталог; транспортный отказ без принятого уточнения — failed. Экспорт проверяет типы настроек/scope/списков, ссылки на операции того же этапа и не принимает complete при отложенном/отклонённом учёте. Некорректные новые данные не считаются старым форматом. Старые запуски без новых полей поддерживаются.

# Достаточность инструментирования

### FACT-QUESTION — От вопроса к факту

Для каждого факта укажи, на какой бизнес-вопрос он отвечает и какую метрику поддерживает. Примеры: конец операции нужен для её длительности; результат решения — для доли исходов; границы попыток — для технических повторов. Не требуй новые поля, если цели они не меняют. Семейства вопросов: качество, длительность, затраты; контакты и удовлетворённость могут требовать других источников. Основание: SRC-047; проектный принцип.

### FACT-LIFECYCLE — Разные границы

Начало, запрос, назначение задачи, фактическое начало работы, подтверждённый результат и отмена описывают разные факты. Время назначения не даёт время начала ручной работы; попытка перед commit не доказывает сохранённый результат. Для длительности нужны соответствующие бизнес-границы; не обещай разложить ожидание и работу без них. Основание: SRC-047 и идеи предложения SRC-059, не принятого контракта; проектный принцип.

### FACT-IDENTITY — Связь и повторения

Ищи существующие идентификаторы и связи: экземпляр → выполнение операции → попытка. Несколько экранных или диагностических записей могут описывать одну операцию. Повтор вызова, возврат клиента и повторная доставка требуют разных правил. Если связь можно восстановить по существующей записи или соединению, предложи проверить её до добавления дублирующего ID. Основание: SRC-001, SRC-059; проектный принцип.

### FACT-SEMANTICS — Разметка и состояния

Технический ключ сопоставляется бизнес-действию, затем операции и этапу. Для факта укажи только относящиеся к нему event keys: событие начала не покрывает завершение. Отказ по бизнес-правилу может быть нормальным результатом; ошибка исполнения — другой исход. Не считай любой отказ дефектом. Отсутствие найденного вызова означает «не установлено в выбранной области», а не доказанную невозможность. Основание: SRC-001, SRC-048; проектный принцип.

Отдельно оцени наличие текста вызова, смысловую привязку, поля/соединения, границы результата и предполагаемый путь доставки. Возможности выполнения, фактическая поставка и качество данных проверяются позднее. Сравнивай факты, а не число logger-вызовов; не выводи процент полного покрытия из одних найденных кандидатов.

### FACT-SOURCE-CATALOG — Требования из переданного HTML о бизнес-событиях

SRC-004 (версия 12, 22.06.2026) даёт конкретный перечень значимых изменений. Используй его при разборе кода до выбора доставки. Ищи начало/конец операции и вызов/выход подпроцесса; назначение исполнителя; фактическое открытие/закрытие задачи сотрудником; получение/внесение сведений; решение и смену статуса; запрос подтверждения/уточнения; изменение условий; формирование маршрута; доставку результата; отказ клиента/отзыв заявки; связанную задачу смежной команды; переход из работы в ожидание. Сопоставляй эти категории с реальными операциями процесса. Не добавляй отсутствующие бизнес-действия только ради соответствия списку.

Все 21 поле снимка сгруппированы ниже. Это справочник того, какие факты можно восстановить, а не единая обязательная сырая схема для всех каналов:

- Источник, время и принадлежность: `guid` — система; `date_time` — время события с поясом; `process_id` — процесс.
- Экземпляр: `сase_id` — связь событий одного экземпляра; `case_description` — что является экземпляром. В первом имени снимок использует кириллическую «с»; примеры и таблица расходятся и по другим ключам. При привязке к реальному контракту сохраняй исходное имя и отмечай несовпадения, не нормализуй молча.
- Действие и результат: `operation` — бизнес-операция/группировка; `event` — значимое действие; `event_status` — результат; `event_status_description` — описание результата; `event_error_type` — техническая/бизнес-причина ошибки. Несколько технических записей не равны нескольким операциям или ошибочным экземплярам.
- Завершение: `is_case_complete` — терминальное событие успешного или неуспешного экземпляра; `is_case_success` — успешное предоставление результата. Успех текущего вызова не заменяет успех экземпляра. В снимке тип Boolean противоречит строковым примерам; фактический тип контракта надо подтвердить.
- Участники и получатель: `employee_id` — исполнитель (для системы в снимке указано System); `role` — роль; `client_id` — внешний получатель; `client_id_internal` — внутренний получатель. Учитывай условную применимость к типу процесса, существующие идентификаторы и обезличивание.
- Продукт: `product_instance_id` — экземпляр продукта; `product` — продукт/услуга. Не подменяй экземпляр процесса экземпляром продукта.
- Разрезы: `message` — содержательный комментарий; `channel` — канал выполнения; `details` — дополнительные атрибуты анализа. Не требуй произвольные comments/детали без бизнес-вопроса; не предлагай записывать конфиденциальные данные открытым текстом.

В исходнике обязательность ряда полей зависит от события/типа процесса. Примеры расходятся с таблицей по employee_id/user_id и описанию ошибки, а details имеет противоречие типа. Для выбранного Logging-формата нужен актуальный согласованный контракт; другой формат может дать эти же факты через разметку/обогащение/проверяемое соединение. Связывай каждое предложение с конкретным аналитическим вопросом и показывай способ переиспользовать существующие записи до добавления новых полей. Основание: SRC-004; текущая применимость снимка не подтверждена.

### FACT-METRIC-BASELINE — Проверить факты для пяти метрик до предложений по логированию

При построении карты и оценке событий держи в поле зрения пять направлений SRC-050: обращения по сценарию относительно экземпляров; процессный CSAT либо общебанковский CSI при его отсутствии; экземпляры с ошибками; отклонение длительности более долгих экземпляров от среднего; отклонение средней стоимости экземпляра от норматива. Для каждого направления установи будущие входы, связь со сценарием и источники вне приложения. Не своди качество к числу error-вызовов, стоимость к наличию исполнителя, а удовлетворённость к комментариям без методики. Полные определения и адресные неизвестные передаются стадии метрик через METRIC-KGB; отсутствие пригодных логов не удаляет направление из каталога. Основание: SRC-047, SRC-050.

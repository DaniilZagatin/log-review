# Предлагаемые формулы из полей бизнес-событий

### METRIC-FORMULAS — Выбрать и привязать подходящие метрики

Это рабочие определения для пилота, не утверждённая банковская методика. Выбирай полезные для найденного процесса метрики; адаптируй имена операций, события и поля к коду и карте. Схема описывает возможные поля, а не доказывает их наличие в приложении. В HTML нужны формула с объяснением каждого члена и необходимые факты, без вычисленных значений, readiness и пустых строк о периоде.

Обозначения: c — один экземпляр (case ID + процесс/пространство ключей); E(c) — его бизнес-события после проверенного устранения повторной доставки; O(c) — отдельные выполнения операций после явного pairing/grouping. Не отождествляй E и O. Для каждой дроби числитель и знаменатель используют одну когорту/фильтры; нулевой знаменатель даёт «нет значения», не 0%. Не суммируй проценты разных групп.

1. **Входящий объём.** N_start(W)=|{c: t_start(c)∈W}|. Поля: экземпляр, процесс, event и date_time. start — конкретное событие бизнес-начала; min timestamp при отсутствии начала даёт только первое наблюдение. Единица — экземпляр.
2. **Число завершённых.** N_end(W)=|{c: t_end(c)∈W}|. Конец подтверждён терминальным событием/is_case_complete. Единица — экземпляр. Входящий и завершённый поток могут быть разными когортами; не называй N_end(W)/N_start(W) долей завершения одной когорты.
3. **Доля успешных завершений.** 100×N_success(C_closed)/|C_closed|. Успех берётся из согласованного терминального исхода/is_case_success, а не из Success любой промежуточной записи. Поля: экземпляр, terminal event, оба флага завершения, время. Противоречивые/повторно открытые терминальные состояния требуют правила lifecycle.
4. **Экземпляры с техническими / бизнес-ошибками.** 100×|{c∈C: существует согласованное событие ошибки типа x}|/|C|, отдельно для каждого x. Поля: экземпляр, event_status, event_error_type, event. Несколько ошибок в одном c дают один ошибочный экземпляр. Бизнес-отказ считается ошибкой только по принятой классификации; нелогичное сочетание Success и error_type — вопрос к данным.
5. **Доля конкретного исхода или отмены.** 100×N_outcome(C_closed)/|C_closed|, если терминальные исходы однозначно определены. event и статус сопоставляются реальным бизнес-решениям; Error не означает автоматически отмену. Для прохождения операции A можно отдельно считать 100×|{c∈C:A∈O(c)}|/|C|.
6. **Длительность процесса.** D(c)=(t_end(c)−t_start(c))/60 в минутах для законченных c с обеими подтверждёнными границами. Назови события границ и правило выбора повторных границ. Статистики: mean(D)=ΣD/n; p50 и p95 по предложенному nearest-rank: отсортировать D, взять D[ceil(p×n)] (индексы от 1). Это рабочие статистики, не обязательная банковская метрика «отклонение длительности». Неполные/отрицательные интервалы не превращать в нулевые.
7. **Длительность операции.** D_A(o)=t_end(o)−t_start(o), агрегировать по отдельным выполнениям A. Нужны роли начала/конца и pairing/grouping; одно поле operation этого не даёт. **Интервал A→B:** Δ=t_start(B)−t_end(A) только для сопоставленных последовательных выполнений/явной передачи. Это межоперационный интервал; ожиданием очереди его можно назвать только при соответствующих границах. Параллельные ветки не соединять по ближайшей строке.
8. **Повторные выполнения.** R_A=100×|{c∈C:n_A(c)>1}|/|C|; дополнительные выполнения A =Σ_c max(n_A(c)−1,0). n_A считает O, не сообщения E. Если операция имеет только старт/конец без идентичности и возможны параллельные/повторные попытки, сначала установить pairing; не достраивать его произвольно. Техническая попытка, бизнес-доработка и повторная доставка — разные разрезы.
9. **Успешно с первого прохода.** FTR=100×N_success_without_rework_or_retry_or_classified_error(C_closed)/|C_closed|. Для выбранного процесса явно определи, какие события означают возврат/доработку/попытку/ошибку, и полноту их наблюдения. Отсутствующая запись не доказывает отсутствие повтора. Это предложенное определение, а не импорт правил UiPath queue items в бизнес-процесс.
10. **Доля операций, выполненных системой.** 100×N_system_operations/N_classified_operations по O(c). employee_id=System использовать только если поле действительно означает исполнителя бизнес-операции; вызывающий лог сервис не доказывает автоматическое выполнение. Не называй эту долю полной автономностью процесса или долей трудозатрат. Неизвестные исполнители учитываются отдельно, роли/employee_id/client_id не смешивать.
11. **Передачи между исполнителями/ролями.** H(c)=Σ_i 1[actor(o_i)≠actor(o_{i−1})] для подтверждённой последовательности выполнений с известным исполнителем; среднее ΣH/n. Поля: экземпляр, operation/event, employee_id/role, время, порядок. Параллельные ветки и равные timestamps без порядка не дают достоверную последовательность. Смена роли у одной операции не равна автоматически передаче.

Разрезы: процесс, сценарий, продукт, канал, система и роль — если есть осмысленная привязка и достаточный объём. Логовые номера клиентов/сотрудников не нужно выводить в бизнес-отчёте. Стоимость/FTE требуют тарифов и трудозатрат; удовлетворённость — оценок и методики; SLA — установленного норматива. Эти величины не выводятся из одного employee_id/date_time или текста message. Контакты можно считать при явной классификации входящих обращений, а не по числу любых событий.

Основание идей: официальные Celonis CALC_THROUGHPUT, PM4Py Statistics и UiPath Operational monitoring/Automation potential. Формулы и когорты выше — проектные предложения. Проверенные ссылки: docs/METRIC-CATALOG.md. Численные и причинные выводы требуют пригодных наблюдений.

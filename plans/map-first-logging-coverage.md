# Новый поток: готовая карта → логирование операций

Статус: итог совместного планирования Codex + Claude и независимого разбора замечаний, 29 октября 2026. Реализация начата по прямому поручению пользователя; итоговая приёмка ещё не завершена. Последнее уточнение человека: оба агента идут последовательно по одной репозитории; отдельные экспорт/перенос/восстановление снимка не нужны. Метрики бизнеса заморожены. Этот проект заменяет прежний обязательный цикл из четырёх стадий для нового пути.

## 1. Граница ответственности

Первый агент строит карту. Второй принимает готовые операции с их точными ID, названиями, входами/результатами, переходами, группировкой, цитатами, задачами и ограничениями. Читает ту же репозиторию и продолжает работу с имеющимися путями/контекстом. Не перестраивает граф, не генерирует второй каталог операций, не пытается повторно разобрать весь код моделью.

Результат второго — отдельное дополнение к карте: найденные записи, привязки к операциям, состояния покрытия, процент, адресные доработки. Исходные операции/переходы/цитаты остаются прежними. Ошибку или слишком широкую операцию карты фиксируем адресным вопросом первому агенту, без скрытой подмены графа.

## 2. Поток

```mermaid
flowchart LR
  R["Та же репозитория и контекст чтения"] --> A["Первый агент: готовая карта"]
  A --> B["Второй агент: логи и привязки"]
  R --> B
  B --> C["Код: состояния и процент"]
  C --> D["Адресные доработки и отчёт"]
```

`Готовая карта + тот же код → каталог мест записи → адресная смысловая привязка → расчёт покрытия кодом → предложения по пробелам → HTML/JSON/CSV`.

1. **Приём карты.** Прочитать опубликованный `scenario_map.json`, необязательный `map_hierarchy.json` и переданный контекст репозитории. Проверить формат/ID/ссылки, сохранить исходные ограничения. Checkpoint без опубликованного результата не выдавать за готовую карту. Бизнес-описание и новый проектный технический разбор второму агенту не нужны: контекст уже есть в карте.
2. **Инвентаризация.** Детерминированно найти кандидаты логирования в том же выбранном коде. Переиспользовать уже найденные первым агентом места/обёртки и индекс чтения. Статический поиск по коду допустим целиком: он дешёвый и не является повторным LLM-исследованием. Реестр не ограничивается первыми 80/300 местами. Все ограничения детектора и непереданные участки сохраняются.
3. **Привязка.** Пакет содержит одну операцию или небольшой связанный набор, её смысл/цитаты и релевантные кандидаты. Модель при необходимости адресно читает вызывающий код/обёртку/контекст ошибки. Определяет, какую операцию и какую фазу отражает запись. Пересечение строк и одинаковый event key дают кандидата, а не готовую привязку.
4. **Покрытие.** Код проверяет ID/цитаты/реальные места записи/конфликты, учитывает принятые семантические решения и считает состояния/процент. Не поручать модели арифметику. Один результат на каждую входную операцию; непросмотренная операция остаётся в знаменателе.
5. **Доработки.** Для известных пробелов предложить минимальное достаточное изменение с источником. Для непроверенной операции сначала адресная задача проверки; отсутствие ответа модели не означает отсутствие логов. Предложение не повышает покрытие существующего кода.
6. **Представление.** Та же карта с отдельным слоем покрытия; полезные существующие бизнес-записи, доработки и счётчики. Несопоставленные/технические кандидаты сохраняются в полном реестре.

Не вводить новую БД, сервис, веб-приложение, самостоятельный многоагентный runtime или отдельный каркас исследований. Один простой последовательный оркестратор второго этапа, детерминированные инструменты и LLM для смысла.

### Что первый агент уже сохраняет и что можно дописать в экспорт

Уточнение 29 октября после проверки исходников первого агента: для работы второго уже есть карта и та же репозитория. Дополнительное сохранение результатов первого нужно для переиспользования сделанной работы, а не для передачи снимка или доказательства, что репозитории одинаковы.

Уже публикуются `scenario_map.json`, `scenario_map.checkpoint.json`, HTML, при включённой группировке `map_hierarchy.json` и `audit/`. В JSON есть операции/переходы/цитаты, исследовательский контекст, задачи, проверки и ограничения. `read_coverage` содержит прочитанные диапазоны, но не их полный текст; `research_history` — метаданные ограниченной памяти, а не сохранённые ответы инструментов. При этом сами наблюдаемые ответы инструментов уже записываются как `scenario_tool` в audit: утверждать, что все они теряются после процесса, неверно. Это журнал исследования, не готовый компактный вход второго этапа; ошибка записи журнала должна оставаться явной.

Минимальное дополнение — детерминированно сохранять рядом с картой:

| Предлагаемый файл | Содержание из уже имеющихся объектов | Польза второму этапу |
|---|---|---|
| `code_context.json` | Допущенный список файлов, существующие структурированные находки `workspace.extraction.facts`, ошибки разбора и ограничения экстракторов | Не повторять уже выполненную статическую экстракцию; адресно искать места записи и контекст вызовов там, где данные есть |
| `read_fragments.jsonl` | Уже выданные исследователю маскированные строки из `MapState._reads`: путь, номера строк и текст, с сохранением разрывов | Сразу использовать прочитанный код; недостающие участки читать из той же репозитории |

Сохраняется фактический набор находок экстракторов: он не объявляется полным графом вызовов или каталогом логов. Статистика экстракторов не является покрытием бизнес-операций. Фрагменты не дополняются непрочитанными строками; их наличие не доказывает смысловую полноту. Публичные результаты search/who_calls/show_facts можно при необходимости выделять из уже существующего audit в отдельный машинный файл; полный модельный диалог для этого не нужен. Обрезанные/вытесненные/отсутствующие данные помечаются явно, не восстанавливаются догадкой.

Это изменение только публикации: на границе завершения `run_agent`, пока доступен `MapState`, получить отделённые данные и записать их существующим `write_outputs`. Не менять промпты, инструменты исследования, критерии завершения, последовательность и количество модельных вызовов или содержимое исходной карты/иерархии. Экспортировать только разрешённые поля через существующие границы допуска/маскирования; не сериализовать workspace целиком, исходники целиком, секретные настройки, скрытые рассуждения или сырые модельные сообщения. Для partial-результата сохранять честный статус и имеющиеся данные. Контекст не передаётся целиком в каждый модельный запрос второго этапа: он служит локальным источником адресных пакетов.

Это необязательное расширение S0, а не отдельная стадия исследования или блокирующее требование к старым картам. Приёмка расширения: на одинаковых recorded replies прежние модельные запросы и результат карты/иерархии не меняются; дополнительных API-вызовов нет; экспорт точно отражает прочитанные строки/существующие находки и ограничения. Расширение реализовано и независимо проверено:27 focused,4 отдельных отрицательных контроля,500 full с двумя обусловленными платформой/необязательной зависимостью пропусками; модельные запросы и прежняя карта/иерархия неизменны на recorded fixture. Это не живой смысловой E2E.

## 3. Что значит «операция залогирована»

Минимальное правило относится к смыслу самой операции карты: по найденной записи/проверяемой группе записей можно установить факт и существенный результат именно этой операции. Отдельный object/case/attempt ID полезен для дальнейшего анализа, но его отсутствие само по себе не понижает покрытие: это не приёмка готовности Process Mining. Для операции «Отправить запрос» нужен факт отправки, для «Применить изменение» одного начала запроса мало. Не требуем подтверждения погашения кредита от узкой операции чтения данных. Не требуем универсального case_id, длительности, outbox или PM-ready схемы от каждой записи.

| Состояние | Смысл |
|---|---|
| Залогирована | Есть обоснованная привязка, покрывающая согласованный минимальный сигнал этой операции |
| Частично | Есть связанная запись, но только начало/запрос/ошибка либо не хватает смысла/корреляции/момента |
| Не залогирована | После предусмотренного поиска подходящая запись не найдена в проверенном коде |
| Не проверена | Поиск/чтение/интерпретация не завершены, обёртка не разрешена, обязательный контекст недоступен или есть конфликт |

Если без контекста/дискриминатора общий лог невозможно отличить от соседней операции, это проблема привязки. Но сырой case_id не обязателен: допустим проверяемый контекст вызова/имеющиеся поля/join.

Минимальный сигнал фиксируется отдельно в `OperationLogging` по полям карты (`description`, `output`, `completion_condition`, `effect_kind`, `outcome`) и нужным цитатам до сопоставления кандидатов; это не ещё один обязательный модельный запрос. Менять его под найденный лог нельзя. Если смысл результата не установлен, остаётся адресный вопрос по операции. Роли понимаются относительно операции: запись после отправки может подтверждать операцию отправки, но не применение изменения у получателя. Код проверяет совместимость заявленных классов исхода/ролей и ссылки на основания, не объявляя такую проверку доказательством бизнес-смысла.

Если карта прямо задаёт несколько самостоятельных исходов самой операции, покрываем их общей записью со значением исхода или соответствующими отдельными записями. Если запись есть только для части этих исходов — состояние «Частично»; модель не выбирает удобный «главный успех». Новые требования ко всем возможным техническим исключениям не выдумываются. Исходящая стрелка сама по себе не равна отдельному исходу операции.

Политика фиксируется в отчёте простой фразой и версией, не разрастается в каталог бизнес-метрик. Код не принимает self-verified флаги. Цитата проверяет текст, независимая приёмка — адекватность смысла. Наличие места записи не доказывает включённость уровня логирования, исполнение и доставку. Основной показатель подписан «Покрытие операций логами по коду».

Ошибки/повторы/no-op могут правильно покрывать операцию, которая сама означает ошибку/повтор/no-op. Запрещено только превращать их в доказательство нового успешного эффекта другой операции.

### Минимум поиска перед выводом об отсутствии

Код ведёт небольшой checklist операции: (1) её опорные диапазоны и содержащие функции; (2) найденные места записи в этих файлах; (3) прямой контекст вызовов через имеющиеся search/who_calls/read, способный пояснить запись; (4) реализация или подтверждённый контракт встретившихся wrappers. Это адресное расширение существующего чтения, не новый полный семантический разбор кода. Вне переданной repo/доступного исходного контекста поиск не обещает полноты.

Границы числа чтений/вызовов/кандидатов задаются конфигом и явно учитываются. Модель не может объявить выполненным пункт, по которому инструмент не выдал текст. Обрезанный релевантный контекст, неразрешённый wrapper, непрочитанный существенный файл или конфликт не дают сделать вывод «логов нет».

`P` и `U` допустимы только после этого завершённого минимума. Если виден только запрос/ошибка, но ещё не проверен контекст, где может быть достаточная запись, итог — `X` с пояснением «частичная запись найдена, поиск не завершён». Иначе нижняя граница процента оказалась бы ложной. Для `C` нужен полный контекст конкретного положительного основания, но не доказательство отсутствия всех других логов в repo. Недоступная внешняя библиотека сама по себе не требует бесконечного поиска: граница доступного кода и смысл заявленной операции указываются явно.

## 4. Процент непокрытых

`N` — число всех атомарных операций входной карты в выбранном сценарии. Группы/бизнес-блоки не считаются дополнительно. Второй агент не исключает неудобные операции; изменение области задаёт человек или новый результат первого агента.

`C` — залогированы; `P` — частично; `U` — не залогированы; `X` — не проверены. `N = C + P + U + X`.

Основной показатель — операции без достаточного покрытия:

- Когда `X = 0`: `100 × (P + U) / N`.
- Когда `X > 0`: честный диапазон `100 × (P + U) / N … 100 × (P + U + X) / N` с явным количеством непроверенных.
- `N = 0`: процент отсутствует, «В карте нет операций».
- Точный расчёт хранится отдельно от отображения. При диапазоне нижнюю границу округлять вниз, верхнюю вверх; при полном анализе показывать одно округлённое число. Нельзя получить два разных числа только из округления при `X = 0`.

Дополнительно показать разбиение на четыре состояния, чтобы «нет ни одной подходящей записи» не смешивалось с «есть только начало/ошибка». Если нужен узкий показатель полного отсутствия записей, он вычисляется отдельно как `U / N`; его нельзя незаметно подменять основным.

Искусственный пример: из10операций6залогированы,2частично,1безлогов,1непроверена. Основной показатель30–40%; не «40% точно не залогировано» и не процент только по9проверенным. Для частичной карты это покрытие известных операций карты, не всего процесса/репозитории и не реальных исполнений. Зафиксированный знаменатель не меняется при исчерпании бюджета или сбое.

## 5. Привязки и полный реестр

- Различать физическое место emit и контекст вызова wrapper: одна физическая запись может иметь несколько обоснованных invocation-привязок. Ключ такой привязки — `(operation_id, site_id, invocation_ref)`; invocation_ref содержит место вызова (путь/строки/колонка) и свидетельство передачи аргумента/маршрута. Реестр считает физические места отдельно от invocation-связей, а знаменатель — только операции. Точная идентичность: путь, строки/колонка, callee; event key не уникален сам по себе.
- `event_key` может быть динамическим или отсутствовать: буквальный ключ не обязателен, если смысл записи и её происхождение установлены по коду.
- Одна запись может относиться к нескольким операциям только с конкретным контекстом каждого использования. Общий helper, поле или соседняя строка недостаточны.
- Логи вне цитат первого агента можно найти и прочитать во втором, сохраняя обычные проверяемые source refs.
- Нужны роли записи: запрос, начало, локальный результат, ответ получателя, ошибка, повтор/duplicate, no-op. Отдельно сохраняется предел того, что она доказывает. Уровень error сам по себе не исключает покрытие операции отказа/обработки ошибки; порядок строк сам по себе не доказывает commit.
- Configured call name, bare emit/publish и указанный моделью новый идиом — кандидаты; до выяснения назначения/обёртки не считать их автоматически логированием. Существующий адаптер/договорённый контракт может подтвердить emit, без требования обязательно иметь стандартный logger.
- Идентичность объекта/попытки можно получить имеющимися полями/контекстом/проверяемым join; новый сырой ID не назначается автоматически.
- Полный реестр хранит mapped, supporting/technical, unmapped, pending. Основная вкладка показывает полезные бизнес-привязки, остальное доступно по счётчику/ссылке. Ничего не пропадает ради красивого процента.
- Java/Kotlin и нестандартные wrappers — явный риск текущего детектора. Добавлять общий механизм разрешения обёрток и тесты, без словаря имён под один репозиторий.

## 6. Контракты второго этапа

Небольшие самостоятельные структуры, не старый обязательный `ProcessMap`/`RequiredFact` с методиками метрик:

- `MapView`: read-only ссылка на исходную карту и её операции, переходы, группы, ограничения; ID не переписываются.
- `LogSite`: точное место, callee, найденный текст/ключ, видимые поля, ограничение распознавания.
- `LogBinding`: operation_id, site_id, роль, что подтверждает, условия/правило связи с объектом, source refs, семантическое обоснование/конфликт.
- `OperationLogging`: operation_id, минимальная ожидаемая запись, состояние, найденные bindings, конкретные недостающие части и предел поиска.
- `LoggingChange`: operation_ids, действие, что/зачем, имеющаяся запись или предлагаемое событие, поля/происхождение, точное место в коде, момент записи, зависимости и тест проверки.
- `ReviewTask`: что ещё проверить по операции/обёртке; отдельная сущность, не поддельная доработка.
- `CoverageSummary`: четыре счётчика, фиксированный знаменатель, формула/диапазон, список учтённых operation_ids.

JSON — главный результат. Текст/HTML/CSV производятся из него детерминированно. Оба агента используют существующий общий доступ к текстам/одинаковую политику маскирования; второй агент не создаёт другой импорт кода. Обычная проверка каждой использованной цитаты сохраняется: несовпадение делает затронутую операцию `X` с адресным feedback, а не поводом заново строить всю карту или останавливать полезные результаты остальных операций. Хеши прочитанных файлов уже входят в основания. Входные тексты не должны повторно маскироваться несовместимым способом.

Для reuse достаточно существующего механизма точной привязки: operation_id + hash фактического пакета (поля операции/нужные соседи/цитаты/кандидаты) + hashes прочитанных файлов + версии политики/детектора/промпта + fingerprint фактической конфигурации модельного запроса. При несовпадении решение проверяется заново; нерассмотренные операции — X. Сохранённые ответы снова проходят текущие валидаторы. Финальная сверка конфликтов выполняется по всем пакетам, поэтому две порции не могут независимо закрепить несовместимые трактовки одного `(site, invocation)`. Перезапуск доработок не строит карту заново. Это обычная корректность кэша, не отдельная инфраструктура передачи исходников.

## 7. Доработки

Порядок предпочтения: `map_existing` → `join`/`enrich` → `add_field` → `add_event`/`move_emit`. `fix_delivery` допустим только при фактических доказательствах сбоя доставки; в первом варианте без runtime-логов не предлагать его из отсутствия записей.

На карточке: операция; чего нельзя понять; существующий лог; что добавить/изменить; зачем; доступные поля или проверяемое соединение; место/функция/строки; до/после какого действия/commit фиксировать; как проверить. Событие/поля помечаются как предлагаемые. ID нового объекта нельзя требовать на ошибке, которая произошла до его создания. Требуется PII-минимизация.

Новый event key/константа/способ генерации поля могут предлагаться и не обязаны уже встречаться в исходниках. Для существующего значения/выражения нужно показать доступность в месте записи; недоступный ID нельзя объявлять имеющимся.

Несколько пробелов можно закрыть одной общей доработкой wrapper с явным списком операций и условий; отдельные независимые действия не объединяются ради меньшего числа карточек. Совпадения anchor/action недостаточно для слияния: условия, смысл и поля должны быть совместимы. Для каждой непокрытой/частичной операции есть доработка или объяснение адресного ограничения. Принятая доработка не считается уже внедрённой.

## 8. Переиспользование и изменение архитектуры

| Часть | Решение |
|---|---|
| Готовая карта/иерархия/цитаты/исследовательский контекст первого агента | Использовать напрямую; источник операций и смысла |
| Текущий код/доступ к исходникам | Тот же контекст последовательного запуска; без snapshot export/transfer |
| `log_discovery.py` | Переиспользовать детектор/ID/ограничения; полный реестр, адресно усилить wrappers и языки |
| Проверки source refs, redaction, безопасные file boundaries | Переиспользовать существующие утилиты |
| Lifecycle/reconciliation идеи | Перенести в компактные bindings; не переносить весь старый DTO/renderer bundle |
| Действия instrumentation и проверки зависимостей | Переиспользовать смысл/валидаторы, переписать вход вокруг операции вместо metric/fact/stage каталогов |
| LLM transport, бюджеты, trace | Переиспользовать самостоятельный адаптер/инструменты с текущими ограничениями; не менять ключи/историю |
| Один repair и точная привязка сохранённых ответов | Перенести проверенные механизмы в новый маленький pipeline; не тянуть `_Run` и atomic-page формат ради reuse |
| CSV escaping/checksums/export helpers | Переиспользовать утилиты; новый экспорт не обязан проходить старую четырёхстадийную схему |
| `code_review`/`review_execution`/`review_reduction`, action catalog, `direct_atomic`, refinement/compose | В новом пути не запускать: это повторяло бы работу первого агента |
| `workflow.run_analysis` как единый монолит | Заменить для нового пути небольшим logging pipeline; не маскировать импорт под генерацию карты |
| Метрики и runtime-профили | Не запускать, не делать обязательными DTO/промптами/вкладками; старые результаты не менять |
| HTML карты первого агента | Сохранить представление; дополнять доверенным renderer/слоем данных, не исполнять входной HTML при анализе |

Адресный read/search/who_calls адаптер использует существующий контекст и инструменты первого агента; отдельный полный `code_index`/call-graph проход не является обязательной новой стадией.

Методы `fit/cite/propose` связаны с `_Run` и старым evidence/header: не обещать их прямое копирование. Существующий model guard/DTO тоже завязан на прежние типы — для нового контракта нужен отдельный небольшой валидатор. `RepoSnapshot.to_context()` с прежними ограничениями инвентаризации в этом пути не использовать.

Новые небольшие модули: `map_input.py`, `logging_contracts.py`, `logging_review.py`, `operation_coverage.py`, `logging_changes.py`, `logging_report.py`; экспорт — адаптация утилит. Не создавать по отдельному агенту на каждый модуль. Старый путь после принятия нового убрать из основной команды/поставки; исторические результаты и архивы сохранить.

## 9. Запуск и UX

Целевой вход: `review-logging --map scenario-map-out/scenario_map.json --repo <тот_же_каталог> --out logging-review-out`. Если первый агент вызывается в общем процессе, эти же данные передаются объектом контекста; никакого второго импорта исходников через новые протоколы.

Три раздела: **Карта**, **Логирование**, **Доработки**. Метрики скрыты. Карта получает отдельный явно выбранный режим «Цвет: покрытие логами», не смешанный с прежним цветом бизнес-исхода, и фильтр по operation_id: залогирована / частично / не залогирована / не проверена. Детализация и переходы принадлежат первому агенту. Основной процент, четыре счётчика и область анализа — над картой/в таблице. Группы агрегируют уникальные дочерние операции. Несовместимая с ревизией карты иерархия отключается с пояснением; плоская карта продолжает работать, N не меняется.

В «Логировании»: операция, существующая запись, когда/что она подтверждает, данные, ссылка на код. Не возвращать непонятные колонки applicability/quality со сплошным unknown. В «Доработках»: операция, проблема, решение, поля, код и проверка. Из строки — переход к точной операции карты. Полный технический/несопоставленный реестр — отдельно. Входной source HTML не исполняется; представление строит доверенный код из JSON.

## 10. Шаги реализации и приёмка

1. **Тонкий вертикальный срез.** Приём готовой карты + той же repo; полный инвентарь; один operation binding; статусы/процент; одна доработка; JSON. Карта/ID неизменны, ни одного вызова map-generation/technical re-analysis/metrics. Начать с собственных Python/Java fixtures.
2. **Полнота и смысл.** Адресный поиск wrappers/callers/ошибок, полный реестр, обязательный результат каждой операции, конфликты, пакетирование и честный partial/resume. Содержательная проверка реального результата на одной существующей карте.
3. **Понятный отчёт.** Раскраска/фильтр карты, две таблицы, исходники/поля, экспорт/SHA; визуальная проверка при доступном браузере. UI не меняет бизнес-переходы.
4. **Удаление дубля и поставка.** Новый основной путь, обновлённые инструкция/конфиг/FULL ZIP, чистая проверка на новой repo. Старые архивы/прогоны не перезаписывать. Метрики остаются выключены.

Модельные пакеты ограничены и могут объединять несколько связанных операций; нет обязательного отдельного вызова на каждый модуль. Для невалидного ответа — один адресный repair. После него допустимо исключать только явно вспомогательные невалидные поля с предупреждением; обязательные IDs/источники/смысловые зависимости не подделывать и не чинить fuzzy-сопоставлением. Статус/процент, присланные моделью, не являются результатом расчёта.

Зависимости и поверхности работы:

| Шаг | Зависит от | Основные файлы | Инвариант и выход |
|---|---|---|---|
| S0: вход | Готовый результат первого агента | `map_input.py`, `logging_contracts.py`, `cli.py` | Прямой MapView/RepoContext; все operation IDs сохранены; host-only N без map/metric вызовов |
| S1: каталог и привязка | S0 | `log_discovery.py`, `logging_review.py`, адаптер существующих read/search/who_calls | Все найденные кандидаты учтены; одна source-bound привязка и конкретные ограничения; проверены Python/Java wrappers |
| S2: покрытие и доработки | S1 | `operation_coverage.py`, `logging_changes.py` | C+P+U+X=N; честный диапазон; каждый пробел адресован, рекомендации не повышают текущее C |
| S3: отчёт/экспорт | S2 | `logging_report.py`, адаптация безопасных CSV/SHA helpers, доверенного map renderer | Карта не меняет смысл; три раздела; реестр не теряется; один содержательно проверенный результат и переносимость на другом репозитории |
| S4: основной путь/поставка | Принятые S0–S3 и взаимное ревью | CLI/документация/конфиг/безопасный full packager | Новый основной запуск работает без старого map/reduction/metrics цикла и ручной подгонки; clean FULL ZIP, старые артефакты неизменны |

Во всех шагах: код Claude независимо проверяет Codex; изменения Codex — read-only Claude с English brief и раздельным владением. Тесты проверяют поведение, не только форму JSON; синтетика не заменяет смысловой разбор реального отчёта.

Обязательные контроли:
- Две операции используют один ключ в разных местах: не получают чужой лог автоматически.
- Общий wrapper: отдельно доказаны конкретные вызывающие операции/поля.
- Только начало или exception: не зелёный результат; событие повтора не новое выполнение.
- Операция отказа/обработки ошибки может быть C по своей error-записи; та же запись не делает C другую успешную операцию.
- Configured name, публикующий бизнес-команду вместо журнала, остаётся кандидатом до выяснения назначения.
- Запись до commit не доказывает committed result; при необходимости предлагается move_emit с конкретным основанием.
- Самостоятельная операция без logger остаётся в знаменателе и получает адресную доработку.
- Неподдержанный/непрочитанный контекст, сбой модели, исчерпанный бюджет: X, а не «нет логов»; исходные операции не исчезают.
- Наличие record с нужным ключом не означает пригодную корреляцию; обоснованный join допускается без нового сырого поля.
- Сначала найден существующий бизнес-лог: не предлагать дубликат add_event.
- Ноль операций; все покрыты; все без логов; частичное покрытие; неизвестные; группировки не удваивают N; формулы считают кодом.
- В карте/цитате ошибка: адресный feedback, без изменения первого результата.
- Прерывание/возобновление даёт тот же учёт и результат, что непрерывный запуск, и не делает повторные модельные вызовы для точно совместимых принятых решений.
- Повторный запуск/новая карта: чужие ID не наследуют старую привязку; точные актуальные решения можно переиспользовать.
- Принятая карточка не увеличивает текущий C; данных исполнения/доставки не придумывать.
- Новый вход не запускает технический GLM, построение/уточнение/compose карты или бизнес-метрики; не читает входной HTML как исполняемый код.
- В отчёте понятны реальные записи/пробелы/поля/код; все источники и непросмотренные кандидаты доступны. JSON/CSV/HTML/SHA согласованы.

## 11. Решения, которые не усложняют первый выпуск

Runtime-логи, проверка доставки, анализ реальных частот/времён и формальные бизнес-метрики — отдельный последующий объём. Для нынешней задачи нужны места логирования по коду. Процент покрытия — простая статистика второго этапа, а не возвращение замороженного каталога бизнес-метрик.

Не строить source-transfer инфраструктуру, новый исследователь карты, нормативную схему всех логов, несколько семантических критиков или универсальный вычислитель. Сначала доказать на реальной карте, что операции правильно связаны с имеющимися записями и получают полезные доработки.

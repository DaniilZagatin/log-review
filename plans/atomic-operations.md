## Независимая проверка Codex для R06

На отдельных источниках воспроизведён обход уточнённой роли ранней привязкой; после исправления новый возврат и отмена заказа не считаются найденными по дублю/освобождению средств корзины. Чистый результат другого места с тем же ключом сохраняет покрытие, факт о повторе поддерживается соответствующей записью. Это проверки проводки на синтетике, не гарантия смыслового решения живой модели.

Строгий demo/export используют прежние записанные ответы, без их замены. Дополнительно проверяются повреждённые настройки/scope/ссылки action-accounting и попытка объявить complete при отложенных кандидатах. Превышение лимита после успешного scope даёт partial; транспортный отказ без принятого уточнения остаётся failed. Полные/clean результаты и хеши переносимого архива фиксируются в verification sidecar R06.

Replay на неизменных PUBLIC Saleor checkpoints:307technical+536summary,0API,6failedfollowups сохранены,8857leaves/digest/старые файлы неизменны. Использован именно исторический planner: для отличающегося текущего task request reuse не подтверждён. Семь выбранных команд Add/Delete/Update/shipping/billing/Confirm/Cancel имеют отдельные якоря; это не проверка всех бизнес-операций каталога.

## A1. Сохранить каталог отдельных действий — реализовано, ожидает проверки

**Файлы:** новый `src/process_observability/action_catalog.py`, отдельные тесты; точечное подключение в `workflow.py`.

**Вход:** уже сохранённые находки, замороженный снимок/граф и logging inventory. Не повторять GLM-обзор. Кандидаты — точки входа, команды, подтверждённые обработчики взаимодействий, автоматические действия/решения и изменения состояния. Не ограничиваться видом `entry_point`: отдельная мутация может быть описана находками других типов. Эвристика и семантическое предложение не становятся доказанным фактом.

**Выход:** каталог со стабильными code-owned ID, исходными finding IDs, символами, диапазонами/снимком и возможными связанными log sites. Все важные сведения остаются на диске; группировка по символу не должна молча склеивать разные эффекты или режимы одной команды.

**Инварианты:** не исполнять целевое приложение; не добавлять «один logger = одна операция»; не выводить UI из имени API; не считать граф вызовов процессом. Источники проверяются на снимке, секреты маскируются до извлечения диапазона.

**Приёмка:** Add/Update/Delete корзины и оба адреса представлены отдельно; OrderConfirm/OrderCancel обнаруживаются и без entry_point-находки; helper не объявляется внешней командой. Нужные действия без найденного кода остаются предложениями.

## A2. Адресно передавать источники и уточнять карту — реализовано, ожидает проверки

**Зависимость:** A1. **Файлы:** небольшой модуль извлечения кандидатов/источников; `workflow.py`; map-guidance после проверки идентичности кеша.

Сводка задаёт обзор, каталог — конкретные действия. Для выбранного этапа/сценария оркестратор выдаёт исходные описания кандидатов и нужные проверенные диапазоны в ограниченном запросе. Поиск и чтение — детерминированные инструменты; LLM решает смысл, применимость и группировку. Для ещё не выданных деталей есть явный остаток/постраничная выдача. Нет молчаливого выбора первых N, обрезки строк или разрешения цитировать весь реестр без чтения.

Уточнение входит внутрь стадии карты. Начать с checkout, затем применять к насыщенным этапам. Не перерабатывать весь технический каталог ради одного уточнения. Между независимыми API не придумывать последовательность. Отказы и повторы привязывать к конкретной операции и условиям.

**Приёмка:** >8действий одного раздела получают собственные источники при извлечении; ссылки создания заказа не подменяются read-resolver. Законный дополнительный helper/commit-источник допускается после явного чтения и привязки к действию. В бизнес-запросе только фактически выданные refs.

## A3. Сверка кандидатов и событий — реализовано, ожидает проверки

**Зависимость:** A2. **Файлы:** `workflow.py`, совместимые расширения `contracts.py` либо отдельный внутренний артефакт `action_mapping.json`; покрытие и тесты.

Каждый поданный кандидат выбранной области получает: operation IDs; обоснованное объединение; исключение с причиной; либо нерешённый вопрос. Неподанный кандидат помечается хостом отдельно. Код проверяет идентичность и полноту учёта, но не объявляет смысл решения правильным только по заполненной таблице. IDs генерирует/сопоставляет код, модель выбирает из предоставленных локальных номеров.

Связать события с конкретными действиями и их границами: намерение/запрос, начало, результат, отказ, ошибка, повтор/дубль, отсутствие действия. Последние не закрывают факт нового успешного результата. Одно событие может требовать различающих полей/источников; одного имени ключа недостаточно. Сначала использовать имеющиеся поля/joins, затем предлагать новые логи.

**Приёмка:** нельзя потерять Add/Delete/Update без объяснения; несколько lifecycle-сообщений одной команды не превращаются в несколько действий; дубли возврата и освобождение средств по корзине не измеряют новый возврат и отмену заказа. Старые артефакты загружаются, ошибки схемы получают точное пояснение в единственном repair. Квоты числа операций нет.

## A4. Подробная карта остаётся читаемой — не начато (Codex, файлы отчёта)

**Зависимости:** A2/A3. **Файлы:** сначала существующие `scenario_graph.py`/`compact_report.py`; расширять DTO и иерархию только при необходимости.

Первую детализацию можно показать существующими узлами внутри областей этапов. Для большого количества действий — обзор бизнес-шагов и раскрываемая детализация выбранного шага/этапа. Пользовательские действия и работа системы различаются; технические API/поля остаются в карточке источника, не в бизнес-подписях.

Сохранить цвет стрелок/переключателей, обычный вид выбранного сценария, серые прозрачные остальные сценарии и перенос релевантных операций выше. Не скрывать остальные сценарии автоматически. Неизвестный порядок не заменять декоративными стрелками.

**Приёмка:** 40–100действий с ветками/повторами, все режимы сценариев, полный русский текст, проверка шрифта/CSP/консоли, геометрии подписей/стрелок и сохранности действий в экспорте. Отдельный UI-тест только при наличии соответствующего клиентского источника; расширение файла само по себе ничего не доказывает.

## A5. Сохранность продолжения и один ограниченный живой тест — historical replay проверен; живой тест не выполнен

**Зависимости:** A1–A4. Отделение технической идентичности реализовано (см. контрольную точку); его нужно подтвердить offline-replay. Живой тест checkout можно ограничить `--refine-stage <фрагмент названия>` и `--refine-max-requests`. Перед правкой guidance отделить технические входы кеша от бизнес-правил либо подготовить проверяемую миграцию: сейчас хеш всего пакета инвалидирует технический обзор даже при неизменном техническом промпте. Старые failed не превращать в success. Кеш не переименовывать и fingerprint не подделывать.

Offline-проверка должна показать0новых технических/редукционных вызовов на валидных реальных checkpoints. Старая бизнес-карта после изменения правил не считается новой; frozen run14 остаётся неизменным.

Следующая живая оценка — сначала только checkout на прежнем техническом каталоге. Заранее сверить эталон независимых действий, адресов, промокодов, вариантов доставки и отдельных автоматических исходов. Проверить конкретные якоря и отсутствие выдуманного порядка/кликов. Небольшая фикстура проверяет проводку данных, не качество живой модели. Этот обзор нового платного запуска не выполняет.

## Отдельное эксплуатационное исправление

HTTP429: сохранять безопасные сведения об ограничении/Retry-After/request ID, различать транспортную попытку и JSON-repair. Проверить ограниченное ожидание/повтор, сохранение завершённых бизнес-стадий и возобновление без их ненужного повторения. Общий тайм-аут и новый автоматический платный запуск этим планом не вводятся. Не повторять бесконечно и не обнулять неизвестные денежные резервы.

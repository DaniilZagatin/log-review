## Требуемое поведение

Небольшой каркас этапов и требований → проверенные единицы команд → малые адресные пакеты → атомарные операции с этапами и наблюдаемыми фактами → карта и покрытие → доработки → определения метрик.

Каркас содержит этапы, границы, переходы верхнего уровня и требуемые факты с lifecycle-ролями. Крупные операции, сценарии и event mappings на этом шаге не генерируются. Атомарная пачка назначает этап каждой предлагаемой операции один раз. Необязательная последующая композиция получает уже принятые операции и переходы и предлагает сценарии/группы для отображения; она не создаёт операции и не приписывает новый код.

При этом обязательные сценарии, прямо заданные бизнесом, сохраняются в реестре требований с источником независимо от композиции. Если их последовательность по атомарным операциям ещё не установлена, они остаются явно unresolved/incomplete. Выключенная композиция или пустой список собранных сценариев не должны скрывать обязательный сценарий из отчёта.

Не генерировать сначала большие операции, чтобы затем повторно переделывать их в атомарные. Группы наподобие «Управление корзиной» допустимы для навигации над готовыми действиями. Они не являются ещё одним обязательным семантическим проходом.

Существующие связи логов с крупными операциями используются как подсказки поиска, с происхождением и проверкой конкретного emit site. Кандидаты без логов остаются в общем учёте. Из исходников backend нельзя вывести наличие UI-клика: действие остаётся API-командой/автоматической обработкой, пока нет источника взаимодействия.

## Что установлено на run17

Из 2 767 кандидатов модель назначила 1 230 уникальных кандидатов этапам и исключила 1 537 как outside_process. Назначение целых областей породило 3 356 пар кандидат–этап. Например, все 87 кандидатов `saleor/plugins` получили все шесть этапов.

Первая страница checkout: 426 кандидатов, 831 704 токена входа. Внутри — 1 889 связанных карточек при 226 уникальных anchors; 1 710 связей возникли по общему owner и лишь 179 по статическому вызову. Дедупликация только описательных карточек в отдельном offline-измерении уменьшила этот раздел с 1 909 403 до 741 537 символов, на 61,16%. Таблица source excerpts при этом не менялась. Это измерение размера, не успешный модельный ответ.

На трёх проверенных публичных файлах исходный Python парсится, а после анонимизации возникает IndentationError. Поэтому одна команда представлена несколькими finding_ref-фрагментами. Технический граф run17 и его кеш задним числом не меняются.

Все 74 существующие связи event → operation имеют operation_id, но не имеют evidence_ids. Они полезны как priors для поиска мест записи, а не как доказанная семантика операции.

Сам run17 частичный: начальная карта/покрытие есть, атомарное уточнение и доработки не приняты, метрики не запускались. Его API-сбои отдельно описаны в `.local/saleor-pilot/MORNING-RESULT.md` и не подменяются этим планом.

## D1. Проверенные единицы команд

Зависимость: неизменный snapshot/catalog. Предполагаемые файлы: новый модуль единиц команд, `action_catalog.py`, тесты каталога. Не менять технический граф, старые checkpoints, результаты review/reduction.

Единица содержит host declaration ID, path, file revision/hash, qualified declaration и точные диапазоны, список всех исходных candidate IDs/findings и навигационные связи. Фрагменты объединяются только после проверки принадлежности одной декларации. Одинаковый символ из ответа модели без такой проверки даёт лишь спорную группу, не подтверждённую идентичность.

Структурные сведения извлекаются безопасным разбором текста до анонимизации либо отдельным индексом с прежней версией исходника. Это допускается только для разрешённого набора источников; текущая проверка касается публичного Saleor. Никакого выполнения/import целевой программы и передачи неанонимизированного текста модели. Выдаваемые цитаты остаются редактированными, с исходными номерами строк. Дыры между диапазонами не становятся переданным кодом. При несовпадении file hash данные изменившегося файла не используются под прежним snapshot: требуется новая проверенная версия. Tentative-единица применяется к неоднозначной декларации в том же frozen тексте, а не легализует новую ревизию.

Критерии выхода: раздельные Add/Delete/Update и shipping/billing; один проверенный метод с несколькими фрагментами даёт одну единицу с полным списком членов. Перегрузки, вложенные/одноимённые декларации, неверный symbol и раздельные диапазоны не склеиваются по имени. Все исходные ID сохранены.

## D2. Каркас этапов и якоря существующих логов

Зависимость: D1 и бизнес-требования. Предполагаемые файлы: модуль адресного контекста, `workflow.py`, DTO и их тесты.

Каркас задаёт этапы, границы, сущности, обязательные результаты/ветки и общий смысл экземпляра. Он не содержит обязательной предварительной карты крупных операций. Прежнюю карту можно использовать как явно помеченный исторический prior. Изменённый prompt не получает старый ответ под видом точного checkpoint hit.

Для каждой связи event → operation:

1. По точному ключу найти реальные места записи в frozen snapshot.
2. Сохранить все совпадения; одинаковый event_key в разных emit sites не означает один смысл.
3. Найти содержащие обработчики/единицы команд и их проверенные прямые зависимости.
4. Использовать прежнюю операцию/этап для порядка поиска и выбора контекста. Противоречащий код не переопределяется старой связью.

Полный короткий business.md пилота передаётся каждой пачке. Все шесть коротких контрактов этапов тоже доступны, чтобы модель могла обоснованно выбрать этап или несколько самостоятельных эффектов. Папка, graph edge и имя только помогают поиску.

Критерии выхода: ложная старая связь чтение-заказа → создание-заказа не становится истиной; одинаковые ключи событий сохраняют неоднозначность; все no-log кандидаты остаются в очереди. Общие helpers и самостоятельные операции различаются.

## D3. Малые пачки сразу выдают атомарные операции

Зависимости: D1–D2. Предполагаемые файлы: `action_refinement.py` либо новый модуль прямой сборки, `workflow.py`, `contracts.py`, `cli.py`, тесты workflow/контрактов.

Пачки группируются по проверенной команде, предметному контексту и связям; prior этапа помогает порядку, но не копирует всю папку во все этапы. Модель сразу возвращает атомарные операции со stage_id, предложенные наблюдаемые факты, lifecycle-привязки событий и полный учёт каждой выданной единицы. Один канонический command может иметь несколько обоснованных самостоятельных эффектов в разных этапах; его выполнение от этого не размножается.

Отдельный лёгкий routing/triage-проход — только для измеренно неоднозначного/большого пула, когда он помогает выбрать источники и сокращает последующий контекст. Он решает atomic_review/supporting/outside_process/unresolved, не создаёт операции и не закрепляет этап повторно. Не делать его обязательной второй генерацией бизнес-карты. Негативный старый prior не вычёркивает кандидата: без triage тот проходит атомарную пачку либо остаётся явно unresolved/deferred.

Начальные гипотезы бюджетов: примерно 10 основных единиц на пачку, жёсткая граница 16; до 8 supporting-зависимостей на основную единицу и до 40 anchors в общей таблице; целевой вход 40 тыс. токенов, верхняя граница 80 тыс.; планируемый JSON-ответ до 10 тыс. токенов. Значения надо измерить на настоящем каталоге. Лимиты зависимостей оставляют явные omissions; без существенного непереданного условия смысл действия/результата остаётся unresolved. Доступное окно 1 млн — защитный максимум, не цель заполнения. Размер пачки ограничивается числом задач, входом и ожидаемым выходом одновременно. `low` не считается численным потолком reasoning. Число будущих вызовов и ускорение пока не измерены.

Источники пачки:

- Собственные entry/command/outcome диапазоны каждой команды и её места записи.
- Необходимые прямые вызовы, проверки, изменения состояния и транзакционные границы; candidate-role зависимость тоже может быть контекстом.
- Общая таблица helpers/описаний по точному anchor ID, ссылки на неё из команд; source excerpts объединяются только при разрешённой непрерывности.
- Общий owner сам по себе не добавляет весь класс. Высокий fan-in — сигнал экономной подачи, не доказательство неприменимости.
- Недостающая существенная зависимость остаётся явно not_supplied/unresolved с причиной и адресом для отдельного ограниченного чтения. Текст не обрезается.

Большая команда получает отдельную страницу либо явный deferred при превышении границы; все её ID и непрочитанные части сохраняются. Ошибка страницы не становится успехом. Единственный repair и строгие schema/source/identity проверки сохраняются.

## D4. Сборка, факты и последующие стадии

Зависимость: D3. Предполагаемые файлы: workflow/DTO, `onboarding_export.py`, отображение состояния, тесты сохранённых результатов.

Host собирает принятые атомарные операции по стабильным идентификаторам, хранит связи единица → действие → этап → emit site → факт. Повторное имя не означает одинаковую операцию; одно событие не означает самостоятельное действие. Обработка refund-duplicate не закрывает факт нового возврата, освобождение средств checkout не становится отменой заказа.

Факты покрытия опираются на итоговую атомарную модель, бизнес-требования и проверенные lifecycle-связи. Обязательные этапы/ветки без найденной реализации остаются явно видимыми. Межстраничные переходы требуют основания в коде/бизнес-требовании; порядок файлов и статический граф не создают бизнес-последовательность.

После сборки идут покрытие, доработки и определения метрик. Предложения записей не дают наблюдаемых численных результатов. Качество и полнота каждой стадии отражаются отдельно; транспортные сбои run17 не исчезают от нового алгоритма упаковки. Политика продолжения после output exhaustion и независимость определения метрик от отказа доработок — отдельные проверяемые решения, без слепого retry и подделки принятого ответа.

Для безопасной совместимости вводится явный режим `atomic`, пока старые результаты и fixtures читаются прежним способом. После offline-приёмки целевой обычный CLI использует прямые атомарные операции; наличие legacy-режима не должно оставлять крупную карту обязательным шагом. Режим, prompt/DTO/validator hashes, stage contracts и бюджеты входят в идентичность бизнес-запросов. Прежний coarse-map ответ не считается точным cache hit нового skeleton-запроса.

## Конкретный первый пакет

Пять основных единиц: CheckoutLinesAdd, CheckoutLinesUpdate, CheckoutLinesDelete, CheckoutShippingAddressUpdate, CheckoutBillingAddressUpdate. После проверки деклараций их фрагменты сохраняются членами соответствующей единицы. Ожидаемый смысл — пять разных API-действий checkout; это проверяемый пример, а не утверждение о пяти UI-кликах.

Рядом передаются только нужные get_checkout/fetch_checkout_info/проверки/запись/события, если их реальный код или проверенные связи доступны. Общие helpers представлены один раз. Обновление количества, использующее общий helper добавления, не становится тем же пользовательским намерением.

CheckoutComplete и создание заказа могут дать разные обоснованные эффекты в checkout/order, с одной канонической командой и проверенными связями. Payload builders get_external_notification_payload и _get_extracted_payload_input по изученным excerpts — supporting-контекст, не самостоятельные бизнес-действия. Одного наличия trigger_notifications тоже недостаточно для доказательства отдельного инициированного выполнения.

## Приёмка и сохранность

- Полный реестр: каждый candidate ID имеет явную судьбу; helpers/context appearances считаются отдельно от самостоятельных действий, исключение и deferred имеют причины.
- Source provenance: path/revision/span и границы фактически переданных excerpts; нет склейки через пропуск кода или fuzzy ID repair.
- Реальный offline replay: те же 307 technical / 536 summaries, 6 старых failed, неизменные 8 857 leaves/digest, ноль новых technical/reduction calls. Новые бизнес-запросы честно меняют свою идентичность.
- Измерения: единицы команд против фрагментов; решения против повторных появлений контекста; duplication ratio; p50/p90/max входа/планируемого выхода; число и причины oversized/deferred. Это учёт и нагрузка, не доказательство semantic recall.
- Небольшой явно размеченный oracle: Add/Delete/Update, два адреса, создание/подтверждение/отмена заказа, исполнение/отмена исполнения, checkout funds release, refund duplicate и payload helpers. Отдельные проверки на ложное outside_process и нужные действия без логов.
- Focused/full offline, строгий legacy demo/export/hash и negative controls. Живой тест требует отдельного обычного одобрения и новых каталогов. Synthetic/скриптовые ответы не становятся источником live continuation.
- Исходники и результаты старых запусков, R06 и прежние ZIP неизменны. Никаких целевых execute/import, private reads/transfers, корпоративной сети, commit/push/deploy или global memory.

# Наблюдаемость операций готовой бизнес-карты

Первый агент строит карту. Этот агент последовательно на той же репозитории **находит существующие логи, сопоставляет их с операциями, считает покрытие и предлагает адресные доработки**. Метрики бизнеса заморожены. Карта, её ID и переходы не перестраиваются.

```bash
python3 -B run.py review-logging --map /path/to/scenario_map.json --repo /path/to/same-repo --inventory-only --out output/inventory-01
python3 -B run.py review-logging --map /path/to/scenario_map.json --repo /path/to/same-repo --config /path/to/profile.json --out output/logging-01
python3 -B run.py export-logging --run output/logging-01 --out output/export-01
```

Первый вызов без модели, остальные разрешённые модельные запросы используют только бизнес-профиль. Результат — JSON, автономный HTML с разделами «Карта / Логирование / Доработки», CSV и SHA256SUMS. Дополнительные артефакты первого агента используются как локальный контекст, не отправляются целиком в каждый запрос.

# Агент наблюдаемости бизнес-процесса — самостоятельная поставка R08

Полный исходный код для распаковки в **пустой каталог**. Старая версия 0.1.0 и патчи R01–R06 не нужны. Требуется Python 3.11+. Основной CLI использует стандартную библиотеку; Claude CLI, Node.js, БД и сервер для отчёта не нужны.

Четыре результата: карта процесса, существующие бизнес-логи, адресные доработки логирования и определения метрик. Обычный `analyze` строит короткий каркас этапов, затем сразу атомарные действия небольшими пачками. Исходники целевого приложения читаются как текст и не исполняются.

В отчёте можно переключать «Процесс → Этапы → Операции», сохраняя все исходные данные без повторного анализа. Карточка операции показывает бизнес-смысл, способ запуска, вход/результат по реализации, связанные записи и доработки, условия переходов, вопросы и полный код. Метаданные запрашиваются вместе с действием; неизвестное остаётся вопросом. Связь по одному ключу лога или пересечению кода обозначается кандидатом, а не доказанной принадлежностью.

python3 -B run.py status
python3 -B run.py demo --out output/demo-01

## Анализ своих исходников

Скопируйте `config/model.example.json` в отдельный локальный профиль и укажите разрешённые URL, модели и имя переменной окружения с ключом. Шаблон содержит заведомо нерабочие адреса `.invalid`. Ключи и сертификаты в архив не входят. Передавайте профиль явно через `--config`.

```bash
python3 -B run.py analyze --repo /path/to/application --include '*.py' --out output/plan-01 --plan-only
python3 -B run.py check-model --config /path/to/local-model.json --role all
python3 -B run.py analyze --config /path/to/local-model.json --repo /path/to/application --include '*.py' --business-file /path/to/business.md --goal 'Процесс обработки заказа' --map-mode atomic --compose on --refine-max-requests 200 --out output/pilot-01
python3 -B run.py export-onboarding --run output/pilot-01 --out output/export-pilot-01
```

`check-model` делает небольшие платные запросы и проверяет подключение, а не качество бизнес-разбора. `analyze` отправляет выбранный код настроенным моделям. Бизнес-описания, приватные конфигурации, сертификаты, реальные логи и ответы пилота не включены. Индекс объявлений поддерживает Python и Java: для Java замените `--include '*.py'` на `--include '*.java'`; для смешанной репы повторите флаг. Неподдерживаемый или неразобранный исходник остаётся явным ограничением. Целевое приложение не запускается и не импортируется.

Стандартные `logger`/`log` вызовы распознаются автоматически. Для собственного wrapper задайте, например, `--log-call audit` или `--log-call TaskService.logging`; править код агента не требуется. Это находит место вызова, а не доказывает доставку записи.

Размер пачек ограничен числом задач и входом/ожидаемым ответом. Лимит дополнительных запросов по умолчанию16; оставшиеся кандидаты сохраняются как deferred. Для большой репозитории это **не полный смысловой обзор**. `--triage auto` может предварительно отсортировать кандидатов; `--refine-max-requests` меняет предел до1000. `--compose on` запрашивает сборку сценариев; без неё сценарии остаются явно не собранными.

Необязательный точный локальный счётчик токенов: установите зависимость `tokenizers` и передайте совместимый файл данных через `--business-tokenizer` вместе с `--business-context-tokens`. Без него используется консервативная верхняя оценка UTF-8; серверное потребление токенов она не измеряет.

## Параметры провайдера и временные ограничения частоты

Обычный профиль OpenAI-compatible endpoint сохраняет прежний запрос. Для endpoint, который поддерживает расширения, в конфигурации каждой роли можно явно задать `extra_body` и `rate_limit_retries`. Например, фрагмент **бизнес-роли** для OpenRouter:

```json
{
  "base_url": "https://openrouter.ai/api/v1",
  "model": "SET_SUPPORTED_MODEL_ID",
  "api_key_env": "LLM_API_KEY",
  "thinking": null,
  "max_output_tokens": 131072,
  "extra_body": {
    "reasoning": {"effort": "low", "exclude": true},
    "provider": {
      "sort": "throughput",
      "allow_fallbacks": true,
      "require_parameters": true
    },
    "response_format": {"type": "json_object"}
  },
  "rate_limit_retries": 2
}
```

Внешний объект профиля по-прежнему содержит роли `code` и `business`. Укажите реально доступную модель и поддерживаемые ею параметры. `low` не гарантирует определённого численного предела рассуждений; reasoning и ответ могут делить выходной бюджет. Эти поля описаны в [документации reasoning](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens) и [маршрутизации](https://openrouter.ai/docs/guides/routing/provider-selection). Не передавайте расширения неподдерживающему endpoint. `extra_body` допускает только объекты `reasoning`, `provider`, `response_format`, без ключей доступа и переопределения основных сообщений/модели/лимита. Его изменение меняет identity запросов и совместимость кеша.

Повторы по умолчанию выключены. `rate_limit_retries: 2` означает максимум три отдельных транспортных вызова только при HTTP429 с ожиданиями30 и90секунд; допустимо от0 до3повторов (третье ожидание270секунд). Каждый вызов проходит транспорт и отражается отдельным `api.transport_attempt`; внешняя система учёта должна резервировать каждый вызов, а не один раз на всю группу. Не включайте одновременно ещё один повторяющий слой обёртки. HTTP200 с пустым, обрезанным или неверным ответом, другие статусы и сетевые исключения этим механизмом не повторяются. Семантический JSON-repair остаётся отдельным единственным исправляющим запросом. Параметры повторов не дают нового денежного бюджета: согласуйте лимит расходов и учтите все попытки.

Для продолжения используйте новый `--out` и `--resume-from output/pilot-01`. Технические ответы переиспользуются только при совпадающих источниках, запросах и профиле; изменение бизнес-смысла не делает старую карту пригодной автоматически. Каркас этапов запрашивается заново, поэтому совпадение всех атомарных страниц не гарантируется. Проверяйте фактические cache hits, ошибки, deferred и ограничения результата.

# Размер атомарных пачек

Для большого репозитория можно явно увеличить пачку через обычный CLI:
`--business-request-chars 4000000 --atomic-page-units 64 --atomic-answer-tokens 40000 --atomic-input-tokens 160000 --atomic-input-tokens-hard 800000 --refine-max-requests 300`.
Это параметры общего планировщика, а не настройка под конкретный проект. По умолчанию остаются 10 единиц,
оценка ответа 10000 и вход 40000/80000. Верхние пределы — 128 единиц и 1000 запросов; проверка полного
контекста, резерв исправляющего запроса и строгая проверка каждой единицы продолжают действовать.
Оценка ответа управляет упаковкой и ограничивается `max_output_tokens` профиля; запрошенное и эффективное
значения записываются в trace. Она не меняет выходной лимит провайдера; рассуждения также расходуют этот лимит.
Большая пачка снижает число
вызовов, но может чаще требовать исправления; это не обещание времени или смысловой полноты.

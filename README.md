# Белка — исследователь сценария

**Первая версия агента: построение карт процессов по исходному коду.** Текущий
функциональный объём ограничен подробной картой одного выбранного варианта
сценария процесса, включая переходы между несколькими АС, ветвления, возвраты
и циклы.

Белка восстанавливает **один выбранный вариант бизнес-сценария** по коду нескольких АС. На входе — краткое описание и директории/ZIP с исходниками. На выходе — подробный связный граф атомарных действий, переходов между АС и явно обозначенных неизвестных участков.

Анализ бизнес-логов, оценка полноты логирования, рекомендации по его доработке,
подготовка PM-ready данных, рекомендации для дашбордов и подключение к Process
Mining в первую версию не входят. Аудит и Phoenix служат для наблюдения за
работой самого агента; они не являются анализом логирования исследуемого процесса.

## Быстрый запуск

Python 3.11+. В PowerShell из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
# Настройте подключение модели в .env по .env.example.
.\.venv\Scripts\python.exe -m pko.cli map-scenario `
  --scenario-text "Новая дебетовая карта действующему клиенту, от заявки до выпуска либо отказа; перевыпуск исключён" `
  --source "D:\Исходники\Канал" `
  --source "D:\Исходники\Заявки.zip" `
  --source "D:\Исходники\Выпуск" `
  --out "scenario-map-out"
```

Вместо текста можно использовать `--scenario-file scenario.txt`. Папка не приравнивается к АС: их соответствие устанавливает агент. Образ результата и обоснование постановки на мониторинг не требуются.

## Как устроен запуск

1. Обвязка создаёт безопасные снимки источников и извлекает статические факты.
2. Один агент ищет вход выбранного варианта, читает код и прослеживает его выполнение через системы.
3. По мере исследования агент добавляет атомарные действия и связи, проверяет ветви, отказы, интеграции, изменения состояния и вычисления.
4. Программные проверки возвращают ошибки для исправления: цитаты должны происходить из прочитанных строк, ссылки — существовать, граф — удовлетворять правилам связности.
5. После завершения либо остановки по лимиту сохраняются карта, данные и журнал.

Это одна итеративная сессия, а не четыре последовательно запускаемых агента. Код источников не изменяется и не исполняется. Прочитанные фрагменты передаются настроенному провайдеру модели.

## Инструменты агента

| Назначение | Инструменты |
|---|---|
| Найти и прочитать код | `list_files`, `search`, `read_file` |
| Найти вызовы и факты | `who_calls`, `show_facts` |
| Зафиксировать границы | `set_scope` |
| Собрать граф | `upsert_system`, `upsert_step`, `upsert_transition` |
| Задать этапы и бизнес-операции | `upsert_group` |
| Зафиксировать пробелы и рассмотренные источники | `add_gap`, `review_source` |
| Проверить перечень атомарных действий | `review_execution` |
| Просмотреть/исправить карту, завершить | `inspect_map`, `remove_element`, `finish` |

`who_calls` и `show_facts` опираются на статический разбор поддерживаемых конструкций. Они не являются полным графом вызовов всех языков. Результат поиска сам по себе не заменяет чтение основания.

Атомарное действие — отдельная работа с проверяемым эффектом или самостоятельной точкой отказа: проверка, чтение, расчёт, запись, отправка, приём, обработка ошибки. Она не равна автоматически функции или строке кода. Каждое найденное действие отображается отдельным узлом.

## Результат

- `scenario_map.html` — автономная HTML-карта: краткая шапка со счётчиками справа, единое поле, выбор этапа, плавные стрелки, масштаб и подробности по нажатию.
- `scenario_map.json` — граф, системы, этапы и бизнес-операции, перечень действий, цитаты и пробелы.
- `scenario_map.checkpoint.json` — последняя сохранённая точка; автоматического возобновления пока нет.
- `audit/run_*.txt` — наблюдаемые действия и результаты проверок. Внутренние рассуждения провайдера не экспортируются.

Карта использует уровни **этап → бизнес-операция → атомарное действие**. Группы
имеют цель и основания, могут пересекать АС и не подменяют граф исполнения.
Панель выбора этапа над картой выделяет его действия и вписывает
их в область видимости. Выбор узла выделяет всю его бизнес-операцию, включая
действия в других АС; все действия остаются на едином поле.
Условия показаны ромбами, начало и исходы — округлёнными узлами. Ожидание,
параллельное разделение/синхронизация и внешние участки имеют свои обозначения.
Исходы различаются явно: успех, бизнес-отказ, технический сбой, отмена или
неустановленный исход. Правила доступны в «Обозначениях», карточки показывают
принадлежность действий к этапам и операциям.

`completed` означает прохождение структурных проверок и покрытие составленного агентом перечня операций. **Это не доказательство, что модель обнаружила все операции или верно истолковала их бизнес-смысл.** Для подтверждения качества нужна сверка с экспертной картой реального сценария.

Неизвестное не выдаётся за отсутствие реализации. При недостатке материалов получается `partial` с причинами. Лимиты по умолчанию: 180 шагов модели, 900 секунд (15 минут) ожидания модели и 7200 секунд (2 часа) общего мягкого бюджета. Анализ логирования процесса, рекомендации для дашбордов и пользовательский чат пока не реализованы.

Для длинных очередей параметры можно увеличить, например добавить к команде
`map-scenario`: `--model-timeout 1800 --max-seconds 14400` — 30 минут ожидания
модели и 4 часа на исследование. Ожидание каждой сетевой операции ограничивается
остатком общего бюджета. HTTPX использует таймаут отдельных операций ввода-вывода;
это не жёсткий предел длительности ответа, непрерывно поступающего частями.

При временной ошибке соединения, таймауте, HTTP 408/429 или 5xx агент повторяет
текущий запрос модели: всего до четырёх попыток с паузами примерно 2, 4 и 8 секунд.
Учитывается `Retry-After` сервера; ожидание входит в общий лимит исследования.
Если указанная пауза не помещается в оставшееся время, сохраняется частичный
результат без преждевременного запроса. История и карта сохраняются, выполненные
инструменты не повторяются.
Перед ожиданием записывается checkpoint. Ошибки доступа, неверный запрос и
неподходящий формат ответа не повторяются автоматически. Если связь не восстановилась,
сохраняются доступный результат и причина остановки. После перезапуска процесса
автоматическое продолжение из checkpoint пока не поддерживается.

## Трассировка Phoenix

Установите `requirements-phoenix.txt`, запустите доступный сервер Phoenix и задайте
`PKO_PHOENIX_ENABLED=true`, `PKO_PHOENIX_ENDPOINT=http://localhost:6006/v1/traces`
и `PKO_PHOENIX_PROJECT=belka-scenario`. Пакет экспортёра не устанавливает сервер.

Один запуск `map-scenario` создаёт один trace: подготовка источников, исследователь,
его шаги, запросы и ответы модели, вызовы инструментов с результатами, сокращение
контекста, контрольные сохранения, формирование HTML и запись результатов.
Каждая попытка обращения к модели и ожидание перед повтором также входят в этот
trace. Успешно восстановленный шаг не помечается ошибкой; неудачная попытка видна отдельно.
В корневом span сохраняются итоговый статус и размер карты; ошибки отмечаются
отдельно. Отклонённые вызовы инструментов тоже видны. `run.trace_id` в JSON и
checkpoint связывает результат с Phoenix, `run.id` — с локальным аудитом.

Перед возвратом результата выполняется отправка накопленных span’ов. Если Phoenix
выключен или недоступен при старте, исследование продолжается с локальным аудитом,
а `run.trace_id` остаётся пустым. Сбой доставки может оставить trace неполным.
Секреты маскируются, внутренние рассуждения модели не экспортируются.

Полный набор тестов при установленных Phoenix-зависимостях включает реальную
OTLP-доставку на локальный тестовый приёмник: проверяется единый trace, родительские
связи, отсутствие дубликатов, завершающий span, отклонённые инструменты и ошибка
модели. Это проверка транспорта и обвязки, а не доступности вашего сервера Phoenix.

## Проверка и демонстрация

```powershell
.\.venv\Scripts\python.exe -B tests/run_tests.py
.\.venv\Scripts\python.exe -B scripts/demo_scenario_map.py
```

Для Unix: `make test` или `make test-report`. Отчёт проверки пишется в `reports/`. Тесты интерфейса с исполнением JavaScript требуют Node.js; при его отсутствии соответствующая проверка явно пропускается.

Дополнительная проверка интерфейса при доступных Playwright и Microsoft Edge:

```powershell
node scripts/check_scenario_map_ui.cjs reports/scenario-demo/scenario_map.html reports/ui-check
```

Проверяются настольный и узкие экраны, отсутствие наложений узлов, навигация
по группам, компактная шапка, открытие переходов с клавиатуры и масштаб.
Playwright используется только для проверки и не входит в зависимости агента.

Демо использует учебный код трёх АС и заранее заданные ответы модели. Оно проверяет сборку карты, а не семантическое качество LLM.

Подробности: [архитектура и ограничения](docs/scenario-researcher.md), [история очистки](docs/migration-to-scenario.md). Настройки подключения — [.env.example](.env.example). Старый режим оценки инициатив, GO/PIVOT и паспорт клиентского пути выведены из эксплуатации.

# Белка — исследователь атомарных операций

Белка восстанавливает один выбранный вариант бизнес-сценария по краткому описанию и исходникам из директорий/ZIP. Методология 2.0: каждый узел — атомарная операция с понятным предметным названием и проверяемым основанием в коде. Связи показывают продолжение исполнения и не имеют подписей.

Если из операции выходит несколько связей, её карточка объясняет смысловое условие каждого перехода и называет следующую операцию. Проверки, расчёты, ожидания, записи и внешние запросы имеют одинаковый вид. Нет отдельных управляющих узлов и классификации автоматизированных систем; явное внешнее взаимодействие показывается в карточке операции.

## Быстрый запуск

Python 3.11+. В PowerShell из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
# Настройте подключение модели по .env.example.
.\.venv\Scripts\python.exe -m pko.cli map-scenario `
  --scenario-text "Новая дебетовая карта действующему клиенту, от заявки до выпуска либо отказа; перевыпуск исключён" `
  --source "D:\Исходники\Канал" `
  --source "D:\Исходники\Заявки.zip" `
  --source "D:\Исходники\Выпуск" `
  --out "scenario-map-out"
```

Вместо текста можно использовать `--scenario-file scenario.txt`. Код источников не запускается и не изменяется; секреты исключаются или маскируются. Прочитанные материалы передаются только настроенному провайдеру модели.

Подключение задаётся через `PKO_SCENARIO_BASE_URL`, `PKO_SCENARIO_MODEL`, `PKO_SCENARIO_API_KEY` и при необходимости парные клиентские сертификаты. Если переопределений нет, используется существующее подключение Белки; новый endpoint не получает прежние ключи автоматически.

Лимиты: `--max-steps 180`, `--max-seconds 7200`, `--model-timeout 900`. `--thinking` / `--no-thinking` управляют исследованием. У суммаризации отдельные `--summary-max-tokens 8192` и `--summary-mode standard|inherit`; стандартный режим выключает уже настроенный провайдерский thinking-флаг, если он поддержан используемой конфигурацией. Скрытые рассуждения не сохраняются в очереди, сводке или аудите.

## Как работает агент

1. Создаёт безопасные снимки материалов, ищет вход выбранного варианта и исследует код.
2. До первой операции сохраняет понимание проекта, связь со сценарием, гипотезу процесса и открытые вопросы.
3. Разбирает небольшие участки исполнения до самостоятельных операций и сохраняет подтверждённые продолжения.
4. Исследует вложенных исполнителей и локальные промпты, ведёт задачи и адресные пробелы независимо от диалога.
5. Проверяет покрытие операций, маршруты и конкретные входные случаи; сохраняет результат либо честный partial при неизвестном или лимите.

Одна функция может содержать несколько операций; служебные строки не обязаны становиться узлами. Число операций не задано. Подготовка рекомендации не считается совершённым действием, а отправка запроса — подтверждённым эффектом получателя.

## Инструменты

| Назначение | Инструменты |
|---|---|
| Чтение и поиск | `list_files`, `search`, `read_file`, `who_calls`, `show_facts` |
| Границы и понимание проекта | `set_scope`, `save_research_brief` |
| Операции и продолжения | `upsert_step`, `upsert_transition` |
| Необязательные этапы навигации | `upsert_group` |
| Незавершённая работа и основания | `save_research_task`, `save_research_note`, `add_gap`, `review_source` |
| Обзоры исполнения и маршрутов | `review_execution`, `review_semantics` |
| Восстановление и завершение | `inspect_map`, `remove_element`, `finish` |

Основания принимаются только из реально выданных `read_file` строк. Карточка показывает файл, настоящее имя функции, смысловое пояснение и раскрываемую цитату. Статический поиск даёт ориентиры, но не заменяет чтение.

Память проекта, операции, связи, задачи и прочитанные диапазоны сохраняются отдельно от диалога. Сжатие сохраняет точные ID, условия, текущий участок и способ восстановления подробностей. При ошибке модельной сводки используется детерминированная память. Все шаги, инструменты, сжатие и сохранение относятся к одному trace запуска; Phoenix опционален.

## Выходные файлы

- `scenario_map.html` — автономная карта, плавные неподписанные стрелки, масштаб, выделение всех путей к выбранной операции и после неё, закрываемая панель операции.
- `scenario_map.json` — схема 2.0, операции, переходы, основания, задачи и публичная память.
- `scenario_map.checkpoint.json` — последнее сохранённое состояние; автоматическое возобновление пока не поддерживается.
- `audit/run_*.txt` — наблюдаемый журнал без ключей и скрытых рассуждений.
- `process_report.json` — только с `--observability` (пилотный режим): каталог мест логирования в прочитанных файлах, кандидаты связи с операциями по расположению и состояние этапов. Карта публикуется до этих этапов и не теряется при их ошибке; HTML получает вкладки «Карта», «Логирование» и «Основания и ограничения», карточка операции не меняется.

Старые JSON остаются читаемы с пометкой прежней методологии. Код возврата: 0 — завершено, 2 — partial, 1 — ошибка, 130 — прерывание с сохранением.

## Проверки

```powershell
.\.venv\Scripts\python.exe -B tests/run_tests.py
.\.venv\Scripts\python.exe -B scripts/demo_scenario_map.py
```

Демо — синтетический сценарий с заранее заданными ответами модели. Оно проверяет сборку и отображение, не качество реальной LLM. Формальные проверки и ноль ошибок не доказывают семантическую полноту. Для её оценки нужны размеченные реальные фрагменты и сравнение операций, маршрутов и исходов.

Для сопоставления сохранённой карты с контрольной разметкой есть `scripts/evaluate_scenario_map.py`; разметка известных ошибок P3283 находится в `tests/fixtures/scenario_p3283_rubric.json` и требует экспертного рассмотрения.

Подробные контракты, настройки, ограничения и устройство памяти: [docs/scenario-researcher.md](docs/scenario-researcher.md). История продукта: [docs/migration-to-scenario.md](docs/migration-to-scenario.md). Старые паспортные режимы, анализ бизнес-логов, мониторинг и рекомендации для дашбордов в текущий продукт не входят.
